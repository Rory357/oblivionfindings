## Practical approval list: guides and files

These are proposals for the parent's approval list, not authority to implement them.

1. **Make uploading a guide document easy to find — existing capability, buried entry.** Resources has **New resource**, which starts a knowledge guide. Its starter already contains Introduction, Files and Links. PDF upload is reached through the file block's **Downloadable file** control or its media library. There is no direct Resources **Upload document** action. Consider exposing this existing path with a clearer document entry and ensuring the owner/review/publication steps are understandable. Evidence: `_resource-library.tsx:243`, `HubTemplates.php:53`, `_block-editor.tsx:159`, `_media-picker.tsx:75`. Do not describe file storage/upload as absent.
2. **Allow PDF reading before download — missing reader capability.** A file block supplies **Download**; `HubMediaController::show` serves PDFs as attachments and permits inline display only for images. The application contains no Hub PDF viewer on the inspected guide, event attachment or resource path. The event prototype explicitly has an attachment preview (`community.js`, `file-preview`); a guide-specific PDF preview is a practical completion proposal rather than an explicit separate guide requirement. Evidence: `_blocks.tsx:207`, `_event-detail.tsx:239`, `HubMediaController.php:105`.
3. **Identify document results clearly — missing file details in staff projection.** Published file blocks do appear in Resources and Hub search. Their projected identity uses the authored block title, parent-page summary and generic type **File**; the result has no filename, PDF MIME/type or size. The media model/library already has these details. Showing them would let staff tell which document they are about to open. Evidence: `HubFeed.php:89`, `_resource-library.tsx:533`, `_search.tsx:82`, `HubMediaLibrary.php:120`.
4. **Make “save this file” expectations explicit — current deliberate behavior.** Saving a File/Link result saves its owning page. Saved content reopens that guide, while **About this resource** also opens the parent guide. This is explicitly covered in `reader-discovery.test.tsx:398`; it is not an accidental missing persistence mechanism. Decide whether clearer “Save guide” wording is sufficient or whether exact-file saving is wanted before expanding the bookmark model.
5. **Inspect real guide content before calling the library unfinished — content check outstanding.** Resource discovery, ownership, review dates, contents, helpful feedback, corrections, private checklist progress and saved/recent filtering exist. Source cannot establish how many useful guides/PDFs are actually published for the staff account, or whether generic starter text is still visible. Use one existing published guide plus one existing PDF to check the whole experience. No fictional live content needs to be created for this audit.

Current file support is PDF and JPG/PNG/WebP/GIF, at 10 MB per file; the library supports batches of six. Word/Excel and arbitrary uploads are not supported by these controls. Broader formats are a scope decision, not an inferred approved requirement (`_media-picker.tsx:75`, `_media-library.tsx:656`, `HubMediaController.php:74`).

## Evidence interpretation

All execution counts above were read from existing files under `storage/logs/`; they were not rerun during this audit. Their filenames identify the relevant recorded slice rather than proving every current source file was tested together. Source tests describe intended coverage; recorded passing logs establish only their recorded execution. Older logs with repaired fixture/import failures must not be presented as current product defects. Existing screenshots can support a prior visual state but do not prove all behavior on `app-BtIKs-zx.js`.

The bounded browser review should first establish guide/document discovery, the real content available to staff and the three concrete presentation gaps above. Persisted mutations and privacy denials already have focused application test coverage; a claim of full live acceptance still requires the parent to record what was actually checked and under which permitted role/site context.
