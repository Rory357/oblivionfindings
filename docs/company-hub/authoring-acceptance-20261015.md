## Practical guide/PDF items for approval

1. **Make PDF upload visible from Company Guides — present but buried.** `New resource` already starts a knowledge/guide draft (`resources/js/pages/company-hub/_resource-library.tsx:229`). Its Files block exposes a real upload dropzone and media chooser (`_block-editor.tsx:159`, `_media-picker.tsx:80`). A second route is Publishing → Media → Upload (`_editorial.tsx:81`, `_media-library.tsx:630`), where the editor chooses an owning page. Uploading there stores media; it does not itself create a guide or place the file on its page. A direct, understandable guide-to-PDF journey is a product finishing item using these existing contracts, not a missing upload service.
2. **Clarify selected-file details and replacement — present but buried.** A File block can choose or upload another file to replace its selected `media_id`; removal and a new selection are already available (`_media-picker.tsx:43–119`, `_block-editor.tsx:159`). It shows “View selected file” rather than the selected filename/type/size, and has no explicit Replace file action. Replacing a block's selection creates/uses another media record; there is no named document-version/replacement workflow. Decide the desired visible replacement experience before implementation; do not mistake metadata version counters for document editions.
3. **Decide the PDF preview experience — currently absent, additional product decision.** PDF media details render a generic file icon (`_media-library.tsx:911`); the protected endpoint deliberately returns PDFs as attachments (`app/Http/Controllers/CompanyHub/HubMediaController.php:98`). Thus “View selected file” and “Open saved attachment” download the PDF rather than showing an embedded document preview. The original family 28 mockup's Files tab offers “Use file”; it does not establish an embedded PDF reader requirement. Approve an actual preview if wanted, or make the download wording and actions clear.
4. **Finish description review in saved/publication previews — concrete current functionality gap.** Reader and authoring support optional file/video descriptions (`_blocks.tsx:207`, `_blocks.tsx:561`, `_block-content-settings.tsx:156`). `SnapshotBlock` renders only the video URL or attachment link and omits `block.body` (`_revision-history.tsx:575`, `_revision-history.tsx:581`). The same snapshot renderer is used by current saved-draft preview, historical version review and Review & publish (`_revision-history.tsx:448`, `_revision-history.tsx:985`, `_publication-workspace.tsx:327`). These views therefore fail to show part of the content being reviewed, although the saved data is retained.
5. **Complete one real guide/PDF workflow acceptance — not yet evidenced end to end.** Check create guide → add PDF → description/title → save → reopen → reader download → replace selected PDF → reopen older saved version. Also check failed upload retention and denied download. Existing media tests cover important parts, but the reviewed evidence does not establish this complete populated browser journey. Do not publish fabricated company content just to produce that evidence; use an approved test record or isolated acceptance setup.

Current file upload support is PDF/JPG/PNG/WebP/GIF, up to 10 MB each. Library upload accepts up to six files per batch and keeps successful files when another fails (`_media-library.tsx:656`, `media.test.tsx:269`); the individual block picker uploads one file. Word/Excel conversion, in-place PDF editing, global replacement of every existing use and binary document-version management are not established requirements of the original 37-family collection.
