## Minimal recently opened document design

This is a read-only recommendation, not an implemented or accepted change. A new migration is not necessary for bounded exact-document history:

- `database/migrations/2026_10_12_010000_extend_company_hub_community.php:18` makes `hub_reads` unique by page/user. `HubCommunity::trackRead` updates `last_read_at` and, only for a matching revision, marks the page update seen. Reusing that record alone cannot identify which sibling document was opened, and a file open must not accidentally mark the guide read or acknowledge required reading.
- Existing `hub_interactions` supports a twenty-character kind, actor/page foreign keys, text body and timestamps (`2026_10_11_140000_create_company_hub_tables.php:67`). Private checklist progress (`HubKnowledge::progress/update`) and delivery markers (`HubNotices::sendOnce`) already use distinct kinds there. Reserve `document_read`, with the stable document-root ID as its body and `updated_at` as the latest opening. Do not store document titles, private paths, extracted text or a new copy of the document.
- Use an authenticated POST receipt from the published document screen, carrying the displayed actor, stable root and media edition. In a transaction, use the existing user → page lock order, reject a changed actor, and re-resolve the currently published edition through `HubResourceDocuments::published(..., lock: true)`. Only the matching visible edition may update history. Draft/editor/history previews must not write staff-reading history. Natural actor/root identity makes duplicate mount receipts harmless; reading should remain available if this nonessential receipt fails.
- Upsert one record per actor/root under the user lock and cap this history at fifty records per actor. Keep `recentPages` compatible. Merge authorised page reads and exact-document records into an ordered tagged identity list, such as `page:123` and `media:123`, using `last_read_at`/`updated_at`; intersect it with the current visible page/resource projections before returning it. The tag avoids ID collisions, and the merge gives a truthful guide-versus-document chronology. Missing IDs sort after recent IDs, with a deterministic tie-break.
- Do not hide this data inside interests, shortcuts, followed pages or notification JSON. Those columns have dedicated write contracts; `HubDiscovery::saveInterests` replaces interests with only topics/teams. A later unrelated save could otherwise silently erase history. Current `HubParticipation`, `HubEditorial`, `HubInsights`, comment moderation, resource reporting, polls and notice queries explicitly project/count known kinds, so a distinct private read kind need not become a visible interaction or increment comments/reactions/helpful. Limit the new history query by the current actor before materialising it.

Meaningful focused checks: two files on one guide remain independent; repeated opens update one record; page/document numeric IDs do not collide; mixed guide/document chronology puts unopened rows last; replacement keeps the stable root; a removed/hidden/expired file drops from the projection; another actor, revoked staff/site access and draft preview do not write or expose history; file opening leaves page-update seen/required acknowledgement unchanged. Use the existing isolated harness only when the root grants the DB slot.
