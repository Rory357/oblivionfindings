## Reuse and source ownership

- Identity remains Asset, with asset id 14 / VH-014 in the synthetic example; canonical profile `/fleet-assets/vehicles/{asset}`. VehicleController and vehicles/show.tsx already expose home site, registration, odometer, equipment, work_orders and maintenance_restricted. Existing profile work links and report entry remain the destination contract. No parallel vehicle identity or task reference.
- VehicleController currently exposes a single odometer number; booking return, inspection metadata and fuel observations contain odometer evidence. MileageController is the mileage/trip expense register, not a new odometer authority. Profile provenance must be reconciled before implementation; the preview labels its selected observation explicitly.
- FleetServiceSchedule already owns interval_days/km, last_completed_at/km and next_due_at/km. Reuse `/fleet-assets/maintenance/schedules`; source-linked work and appointments remain Maintenance-owned. Its current markComplete method advances schedule dates/km, and must not be treated as safety release. No invented service interval or threshold.
- WoF/CoF and registration expiry fields live on Asset. ComplianceController currently starts from `ok` and uses hard-coded day bands even when evidence is absent; that behavior is an inspected limitation, not the proposed readiness contract. No authoritative RUC applicability/licence-range source was found in the inspected profile/model/compliance surfaces. RUC is explicitly unknown in the primary fixture; additional fixture applicability is labelled synthetic. New policy/schema is not implied.
- FleetVehicleStateSnapshot represents telemetry observations, not safety or bookability. No tracker is a supported profile state. No location collection, map tiles or tracker command occurs in the preview.
- FleetChecklistTemplate + FleetChecklistRun are canonical checklist sources. Runs already preserve presented_template_json, rule_snapshot_json/version/hash, original responses, observed/submitted time, outcome, correction linkage and request identity. MaintenanceCheckService rechecks version/current access, retains `needs_assessment` when rules are not approved/mapped, and prevents unknown from passing. Preview questions are explicitly fictional review examples, never live safety procedures.

DailyCheckController and InspectionController are existing entry points, not separate proposed check stores. Their legacy projections need scoped review before implementation.

MaintenanceReportService validates source-to-asset, approved Coordinator/backup route, authorisation and request key/fingerprint. The preview demonstrates this contract locally, not a new endpoint.
