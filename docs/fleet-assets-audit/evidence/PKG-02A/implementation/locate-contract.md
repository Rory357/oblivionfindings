## Existing contracts and the gap

`ClientController::locateNow` currently resolves resident consent and redirects through `App\Services\Queclink\LocateNowService` to Device management. Preserve that non-JSON response. The new JSON adapter will use `DeviceCommandRequestService`, `CommandRequestInput`, `DeviceCommandQueueService`, `GovernedCommandDispatchService`, `DispatchDeviceCommand`, `QueclinkTrackingCommandAdapter` and the existing provider lifecycle. There is no new command engine or command table.

The registry currently defines `tracking.location_refresh` as operate/medium, requiring real step-up, no second approver/change by default, no pre-existing fresh observation, and a 180-second expiry. These are read from the registry/configuration, never copied into a new safety policy. Future approval/change states remain visible and cannot be bypassed by this adapter.

Two gaps require explicit treatment. `CommandAssignmentFingerprint::forDevice` binds active assignment IDs/targets/time, but not the client location consent/collection fingerprint. `DeviceManagementAuthorizationService::personalTrackingIsAuthorised` checks general tracking consent and audiences, not the exact client-profile care relationship and resident-location consent gate. Moreover, `FrameRouter::claimQueuedCommand` currently checks provider identity, expiry and serial provenance but does not recheck the original requesting client before releasing command bytes. Claiming the existing command checks already cover the client workflow would be incorrect.

## Exact endpoints and response boundary

All new endpoints are under the existing approved application/Operations routes and require the existing tracker-management permission, exact `ClientLocationAccessService::resolve(..., manage: true)` and canonical Device management authorization. GET responses, denials and successful writes are private/no-store. CSRF applies to every POST. Browser-supplied device, site, actor, capability, parameters, step-up timestamp, break-glass, approval or change values are prohibited.

1. Existing `POST /operations/clients/{client}/location/locate-now`: non-JSON requests retain the current redirect. Explicit JSON accepts only trimmed reason (10–1000 characters), UUID idempotency nonce and the current 64-character access fingerprint. Fixed capability is `tracking.location_refresh`, parameters are empty. Return the exact canonical request/status envelope; queue only if the canonical result is Ready and the client guard still passes. Replayed Queued or later states return the same request without another queue job.
2. New `GET /operations/clients/{client}/location/locate-now`: read-only availability and latest request made by this actor in the current exact client context. This allows reopening after reload without persisting reason/location in browser storage. Return no other actor's request and no generic Device command. Unsupported/denied actions have a truthful safe explanation; the page does not present a misleading enabled action based only on `fleet.manage`.
3. New `GET /operations/clients/{client}/location/locate-requests/{commandUuid}`: exact UUID, requester, current client/device/site, fixed capability and server-bound context checks; 404 for another record context. Accept expected access fingerprint in a request header, not a location-bearing URL. Recheck after the read. Return only status, safe status message, server timestamps, permitted action URLs, verified provider delivery/ACK times and separately identified observation evidence. Never serialize the command model, raw provider references/ACK, credentials, signed key, full audit context or arbitrary provider summary.
4. New `POST /operations/clients/{client}/location/locate-requests/{commandUuid}/confirm-identity`: validate the same scope, then set the server-owned intended URL to this client's Location tab and redirect to the existing `password.confirm` route. A session entry may hold this opaque request UUID for reopening, never a reason or coordinates. No caller-controlled return URL. The identity form and session timestamp are the existing real authentication workflow.
5. New `POST /operations/clients/{client}/location/locate-requests/{commandUuid}/resume`: use the existing request's immutable reason/key and actual numeric `auth.password_confirmed_at` converted to UTC, repeat current checks and call canonical request/resume. Dispatch remains an explicit user action after identity confirmation; returning from password confirmation alone does not send a command. Expired requests stay expired and require a deliberate new request.

These endpoints are adapters, not general command creation/status APIs. The existing redirect's route/name and callers remain compatible. HTTP polling never enqueues, extends expiry, changes an observation timestamp or marks a request successful.

## Binding the client context on the canonical request

Compared alternatives: revision 1's `clloc1:<64-hex-context-hmac>:<uuid-nonce>` is 108 characters and fits the canonical 128-character key. It would need canonical integer/string encoding, versioned domain-separated HMAC, current exact actor/client/device/site/assignment/consent/collection binding, rejection of malformed/unknown reserved prefixes at every request entry, stable nonce through step-up, altered-reason conflicts, and verification of both signature and HMAC at dispatch and delivery. Avoiding a column is not sufficient justification for overloading a retry identifier with authorization origin. An omitted prefix could only be detected reliably at delivery by checking the canonical signature for every governed request, including apparent legacy ones.

Preferred revision 2: add a nullable `origin_context` JSON column on **existing** `device_command_requests`, declared immutable and hidden. No additional request store/lifecycle. Its sole initial permitted non-null shape is `{kind: 'client_location', version: 1, client_id: positive integer, assignment_id: positive integer, consent_id: positive integer, access_fingerprint: lowercase 64-hex}`. Existing signed request fields already bind actor, Device, Site, assignment fingerprint, capability, reason, parameters and expiry; the access fingerprint binds the exact custody/collection start, consent updated time, purpose, authority, audience and retention. Never accept a loose arbitrary metadata object, unknown kind/version, numeric strings, missing fields or extra fields.

Add a nullable typed context input at the end of `CommandRequestInput`. Only the client adapter constructs it from current server-resolved evidence; generic HTTP controllers prohibit `origin_context` and all origin subfields rather than ignoring them. Canonical request intake validates the exact context shape and current client evidence even when called outside HTTP. It signs and stores the context in the same transaction. `CommandSigningPayload::toArray` adds `origin_context` and schema version 8 only when non-null; when null its current schema 2–7 serialization is byte-for-byte unchanged, preserving existing signatures. All code reconstructing the signing payload must carry the stored context, including signature verification at provider delivery. Remove/alter the context through raw SQL and the signature fails; an ORM update is rejected as an immutable-contract mutation.

Canonical idempotency compares origin context as well as the existing reason/parameters/change/break-glass contract in both the early and locked duplicate paths. The client adapter uses `client-location:<uuid-nonce>` (52 characters) for operation namespacing, but authorization never depends on that prefix. All client-prefixed requests require valid client context; malformed/unknown `client-location` prefix variants are rejected at canonical intake. A context-bearing record remains client-scoped even if read/resumed through a generic endpoint. A generic same-key request with omitted context conflicts; it cannot overwrite or downgrade the prior contract. Batch requests retain their independent existing keys and cannot manufacture client context. A genuinely new generic request remains governed by its pre-existing permissions, as before.

For a context-bearing request, resolve the exact stored client/assignment/consent against the command's canonical Device, requester and Site; require exactly one eligible current client assignment. Resolve the original requester freshly; apply the current client policy/profile tracking section, tracker management, resident consent, collection, custody/site and access-fingerprint decisions. Constant-time compare the stored fingerprint. Assignment, consent, purpose, audience, retention or collection changes invalidate the request. Removing and recreating an assignment cannot transfer it. Changing consent within the same assignment also fails. Unknown/malformed non-null context is denied, never treated as legacy. Generic context-null commands retain their existing canonical policy and cannot be exposed through these client endpoints.

A nonce replay with a different reason/context reaches the canonical idempotency-contract rejection. A stale supplied client fingerprint fails before creating a request. Do not silently create another request after a context change. The nonce/key/context stay stable while awaiting real step-up; resume uses the stored immutable reason/key/context after current revalidation. Latest-own-request lookup first narrows Device/requester/capability, then exact stored client/assignment/consent/current fingerprint. No new lookup table is needed. Tests cover generic-context injection/omission, context removal/tampering, pending step-up retry, unknown versions and current fingerprint changes.

## Transaction and delivery enforcement

`ClientLocationLocateService` owns client-scoped intake/resume/status presentation. `ClientLocationCommandContext` owns only context binding/current evidence and is reused by the canonical dispatch and provider delivery boundaries. It must not depend on the Locate service, request service, queue service or provider adapter, avoiding a dependency cycle.

For an existing command, lock the command row before context evidence. Then use the established current-evidence order: exact consent, Device, canonical client/site through `DeviceCustodySiteResolver`, exact assignment, current RBAC/HR evidence via `AuthorizationEvidenceLockService`, and the exact current `client_user` pivot. Reuse the corrected locked-actor client resolver; ordinary REPEATABLE READ relationship snapshots are insufficient. Hold this evidence until the request/queue transaction commits. For a new key, serialize on the same context evidence; if an initially absent key becomes an existing command before mutation, roll back and restart using the existing-command lock order. Do not acquire an existing command after holding context locks. Bounded transaction retries reuse the same nonce and cannot duplicate an after-commit job. Add a deterministic two-connection test for each relevant revoke/queue ordering.

`GovernedCommandDispatchService::assertDispatchable` calls the context guard inside its existing canonical command transaction. This covers initial queue checks, worker dispatch and generic execution of a client request. Failure uses existing `CommandDispatchPreconditionException` and blocked-without-execution audit behavior. Existing canonical capability/site/assignment/signature/reason/step-up checks remain intact. Extract signature reconstruction/verification to one canonical verifier reused by dispatch and governed delivery; it verifies every linked governed request before origin classification. Thus removing context cannot cause an unguarded legacy fallback at the provider queue. Approval/retry reads preserve the stored immutable context; they cannot produce an unsigned replacement.

At Queclink delivery, add a narrow guard in `FrameRouter::claimQueuedCommand` before reading/releasing the command bytes or `markSent`. Verify exact request/attempt linkage, the canonical signature (including context), fixed client capability and context shape, current original-requester/context evidence, expiry and still-current canonical management authority. A denied unsent client request returns no command bytes. Record a safe audited failure atomically: Accepted/Running request and attempt become Failed; the still-queued provider row becomes Failed; safe reasons/completion times and audit append are in the same transaction. Preserve `sent_at`/ACK/serial provenance, and do not retransmit or rewrite already-sent records. Failure to append audit rolls back all lifecycle updates and still releases no bytes. Do not use the Ready/Queued-only `applyPreconditionFailure` on Accepted or invent Accepted→Blocked. Missing/inconsistent governed links or signature failure release no bytes. Existing unrelated commands retain their policy/serial behavior, with canonical signature verification on linked governed delivery.

Actual source lock chains and proposed ordering: intake/resume and queue acquire existing request → consent → canonical Device → client/Site → assignment → RBAC/HR → exact care pivot; dispatch preparation is request → the same context evidence, then commits **before** the adapter runs. Provider enqueue currently uses QueclinkDevice → attempt, with request as an ordinary read; it must not acquire client evidence in that chain. Provider delivery is QueclinkDevice → pending → canonical request → attempt → context evidence. Source `GovernedCommandLifecycleService::linkedLifecycle` currently locks attempt before request, while dispatch result finalization locks request before attempt. Normalize that helper to request → attempt in this bounded change and test ACK/fulfil/expiry paths that use it. No context-holding transaction may call provider enqueue/claim or acquire QueclinkDevice/pending. Dispatch result/reconciliation commits lock request → attempt as applicable and do not acquire provider rows. This avoids adding an inverse edge between provider and client locks; deterministic concurrency tests must still validate the proposed order against the actual implementation before release.

The delivery linearization point is the guarded claim/markSent transaction. A consent/care revocation committed before that point must win. After commit, FrameRouter returns authorized bytes to the socket writer; withdrawal can occur before physical socket transmission and cannot recall those already-authorized bytes. This contract proves authorization at the atomic claim, **not** revocation-safe physical delivery or recall. No transaction is held across network I/O. Tests check the real router's returned outbound list with synthetic frames, not a socket, and assert no command bytes when revocation wins the claim ordering.

## Measured location, acknowledgement and status

Render three distinct facts: request state/time, tracker acknowledgement/time, latest privacy-authorised location and its measured time. Queclink `markAcknowledged` records ACK and leaves the request running; it does not prove a new fix. `fulfilFromTelemetry` links a matching Device/vendor/unblocked location event received after delivery within expiry, and the adapter later reconciles that reference. This is a temporal provider correlation, not a command-response location identifier. Explain that limitation in concise UI copy when applicable.

Only show “New location received” when the exact linked event is still readable for the current resident assignment, its measurement time is after request creation, received time is within the actual delivery window, coordinates are valid, and the retained/current collection interval includes it. A delayed old fix received later can be shown as an older observation, never a new measured location. ACK alone and Reconciled alone do not move the marker or change battery/observation age. If canonical reconciliation and client observation evidence differ, show command completion separately and say no newer measured location is available. Extend `ClientLocationHistoryService` with a narrowly bounded exact-evidence resolver if required; preserve its post-read access recheck and retention bounds.

The dialog reads canonical statuses, including awaiting identity, approval/change, queued, delivery, uncertain, failed, expired, reconciling and reconciled. No locally manufactured success or replacement timeout. Polling may stop at the server's expiry and offer Refresh status; the displayed canonical status remains the server value. A failed status read preserves a clearly stale last result with Retry. It does not automatically submit another request.

## Frontend and cancellation

Add `LocateNowDialog` under `resources/js/components/client-location`, using the shared dialog/button/field/status primitives and workspace styles. Tracking source opens it in place. Show the exact tracker, last measured fix, reason field, real identity step, request progress and explicit Send/Continue/Refresh actions. Restore focus on close, announce status changes accessibly, retain visible validation and keyboard navigation. No mock confirmation checkbox.

One request generation and AbortController governs availability, submission responses and status reads. Closing, client change, access-fingerprint change, logout/403/404, visibility loss and unmount cancel browser work. Every response is checked after JSON parsing before applying state. A late success cannot reopen the dialog, restore withdrawn location or replace a newer request. Polling is suspended while hidden and revalidates on focus. Pre-submit Cancel closes the form. After submission, Close stops monitoring; concise copy makes clear that closing does not recall a sent request. No cancellation API or fictional cancelled state is added.

Existing map grayscale, battery animation/reduced motion, zone drafts and historical selection remain unchanged. Refreshing current location does not overwrite a deliberately selected historical point. No device is polled from browser QA.
