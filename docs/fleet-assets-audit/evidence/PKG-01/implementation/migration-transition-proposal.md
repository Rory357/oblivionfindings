# PKG-01 additive migration and transition proposal

Proposed for Designer review before operational schema writes. Source baseline `e62b569ff42ab471300fb6713a68758b647b2c32`; one operating organisation across approved sites. The additive migration has been exercised only on disposable package test/browser schemas. This is not an approved operating rule set or live activation.

## Source facts retained

`fleet_work_orders` remains the canonical WO identity and status record; `reference_number`, `asset_id`, reporter, assignee, `due_at` and existing values stay compatible with All Tasks. `fleet_checklist_templates` and `fleet_checklist_runs` remain the checklist source. `assets` remain the resource/approved-site source. `fin_bills`, Finance approval and its journal remain the only invoice posting source. No new `tenant_id` or `organization_id` is proposed. Existing legacy fields remain untouched.

## Proposed exact additive schema

All IDs below are unsigned big integers with foreign keys to the named canonical tables unless stated otherwise. `created_at`/`updated_at` are normal timestamps where listed. Immutable fact tables have no application update/delete route. Existing evidence is never cascaded away on source deletion.

1. **`fleet_work_orders` additions:** `version` unsigned integer not null default 0; `waiting_reason` varchar(64) nullable; `next_action` text nullable. Index `(status, waiting_reason, due_at)`. `status` enum meanings, `assigned_to_user_id` and `due_at` are preserved. Completion and visible Resolve both call one locked, versioned command; waiting reason is separate from resource restriction.
2. **`fleet_maintenance_policy_versions`:** `id`, `site_id` → `sites`, `asset_category` varchar(64), `rule_kind` varchar(32), `version` unsigned integer, `rules_json` JSON, `content_sha256` char(64), `approved_by_user_id` → `users` nullable, `approved_at` datetime nullable, `created_at`. Unique `(site_id, asset_category, rule_kind, version)`; index `(site_id, asset_category, rule_kind, approved_at)`. Rule kinds include check, hold, repair, retest, release and custody. No seeded active rules or inferred pass defaults.
3. **`fleet_maintenance_policy_assignments`:** `id`, `site_id` → `sites`, `asset_category` varchar(64), `rule_kind` varchar(32), `policy_version_id` → policy versions, `assigned_by_user_id` → `users`, `assigned_at` datetime, timestamps. Unique `(site_id, asset_category, rule_kind)`; index `policy_version_id`. Assignment commands must verify the referenced exact version is approved and matches site/category/kind. Absence, mismatch or stale assignment yields Needs assessment, never Ready/release.
4. **`fleet_maintenance_site_routes`:** `site_id` → `sites` primary key, `coordinator_user_id` and `backup_user_id` → `users`, `approved_by_user_id` → `users`, `approved_at` datetime, `version` unsigned integer default 1, timestamps. Unique primary site and indexes on both user IDs. No fixture-derived or migration-seeded people. New reports require a valid approved route; the Coordinator is current owner and backup is nominated cover. Proposed handover leaves current assignee accountable until recipient acknowledgement.
4a. **`fleet_maintenance_reviewer_grants`:** append-only rows `id`, `site_id` → sites, `user_id` → users, `asset_category` varchar(64), `review_kind` varchar(32), `version` unsigned integer, `decision` varchar(16) (`grant`/`revoke`), `recorded_by_user_id` → users, `recorded_at` datetime, `created_at`. Unique `(site_id, user_id, asset_category, review_kind, version)`; index `(site_id, asset_category, review_kind, user_id, version)`. The latest row is the current decision. No rows are seeded; release rechecks this decision under the asset lock. This preserves every approval and revocation, including later re-grants.
5. **`fleet_maintenance_reports`:** `id`, `work_order_id` → work orders, `asset_id` → assets, `site_id` → sites as submission provenance, `submitted_by_user_id` → users, `observed_at` datetime nullable, `submitted_at` datetime, `source_type` varchar(80) nullable, `source_id` unsigned big integer nullable, `request_key` varchar(100), `request_fingerprint` char(64), `title` varchar(255), `description` text nullable, `estimated_start_date` and `estimated_end_date` date nullable, `duplicate_of_report_id` self-FK nullable, `created_at`. Unique `(submitted_by_user_id, request_key)`; indexes `(work_order_id, submitted_at)`, `(asset_id, submitted_at)`, `(site_id, submitted_at)` and `(source_type, source_id)`. Each retry resolves the same report. Duplicate linking preserves both immutable reports and the canonical WO; a later link is an append-only action, not an overwritten report. Dates are source-owned estimates, never bookings or timed releases.
6. **`fleet_checklist_runs` additions:** `work_order_id` → work orders nullable; `source_report_id` → reports nullable; `rule_version_id` → policy versions nullable; `rule_snapshot_json` JSON nullable; `rule_sha256` char(64) nullable; `outcome` varchar(32) nullable; `check_kind` varchar(32) nullable; `corrects_run_id` self-FK nullable; `observed_at` and `submitted_at` datetime nullable; `request_key` varchar(100) nullable; `request_fingerprint` char(64) nullable. Unique `(user_id, request_key)` (multiple legacy NULLs allowed); indexes `(work_order_id, check_kind, submitted_at)` and `(asset_id, outcome, submitted_at)`. New runs have an exact approved version, full rule/question/response/evidence provenance and explicit passed/failed/needs-assessment outcome. Legacy `passed` is retained for compatibility but never treated as authoritative proof without a snapshot. Corrections create new rows linked to the original.
7. **`fleet_maintenance_actions`:** `id`, `work_order_id` → work orders, `action_type` varchar(48), `actor_user_id` → users, `target_user_id` → users nullable, `check_run_id` → checklist runs nullable, `policy_version_id` → policy versions nullable, `expected_version` and `resulting_version` unsigned integers, `idempotency_key` varchar(100), `payload_sha256` char(64), `payload_json` JSON, `occurred_at` datetime, `created_at`. Unique `(work_order_id, idempotency_key)` and `(work_order_id, resulting_version)`; index `(work_order_id, action_type, occurred_at)`. Typed validated commands write append-only handover proposal/acknowledgement, internal appointment, external response/cancellation, repair attestation, note, custody receipt and independent release decision. Provider acceptance is recorded only when actually reported; the actor cannot supply another person's receipt. `payload_json` carries validated source snapshots, not arbitrary authority.
8. **`fleet_maintenance_restrictions`:** `id`, `work_order_id` → work orders, `asset_id` → assets, `source_run_id` → checklist runs nullable, `source_key` varchar(120), `restriction_kind` varchar(32), `state` varchar(24), `created_by_user_id` → users, `created_at`, `released_by_user_id` → users nullable, `released_at` datetime nullable, `release_action_id` → actions nullable, `version` unsigned integer default 1. Unique `source_key`; indexes `(asset_id, state)`, `(work_order_id, state)`. Booking request/change/approval/checkout and release lock the canonical asset and re-read all active restrictions. Estimate end, completion or Finance state cannot release a restriction.
9. **`fleet_maintenance_attachments`:** `id`, `work_order_id` → work orders, `report_id` → reports nullable, `check_run_id` → checklist runs nullable, `action_id` → actions nullable, `uploaded_by_user_id` → users, `disk` varchar(32), `path` varchar(512), `original_name` varchar(255), `mime_type` varchar(120), `category` varchar(64) nullable, `description` text nullable, `byte_size` unsigned big integer, `sha256` char(64), `request_key` varchar(100), `request_fingerprint` char(64), `created_at`. Unique `(uploaded_by_user_id, request_key)`; indexes on each source FK and `(work_order_id, created_at)`. The application requires exactly one source parent, private storage, scoped serving and cleanup on failed submission. Current UI/API limits are ten files per report and 10 MB per PDF/JPEG/PNG; these are implementation limits pending operating review.
10. **`fleet_maintenance_effects`:** `id`, `work_order_id` → work orders, `action_id` → actions, `effect_key` varchar(150), `effect_kind` varchar(48), `payload_json` JSON, `state` varchar(24), `attempts` unsigned integer default 0, `next_attempt_at` datetime nullable, `last_error` text nullable, timestamps. Unique `effect_key`; index `(state, next_attempt_at)`. Insert in the transition transaction; a post-commit dispatcher command handles due effects with bounded retries and idempotent notification identity. Scheduler activation remains an operating gate. Calendar and Tasks use stable source projections; no second ticket/event identity.
11. **`fleet_maintenance_fin_bill_links`:** `id`, `work_order_id` → work orders, `fin_bill_id` → `fin_bills`, `linked_by_user_id` → users, `created_at`. Unique `(work_order_id, fin_bill_id)`; index `fin_bill_id`. This exposes canonical bill status/approval/journal and Finance-owned site/asset allocation only. The link does not post, approve, copy an amount or create a second FinancialEvent. An invoice can cover multiple linked work records only where Finance's existing allocation truth supports it.

Release authority uses a dedicated ungranted capability, current approved-site access and the explicit per-site reviewer grant above; no role, person or grant is seeded. Before implementing that guard, inspect the current permissions/site membership schema and take any material deviation back to Designer. A safety release requires reviewer identity different from the repair attestor and current exact policy, retest, evidence, custody where applicable and active restriction checks under one asset lock.

## Staged transitions and first protected slice

1. Add migration and focused models/services for policy versions, report identity, check snapshots, work-order version, actions and restrictions. Enforce scoped reads/counts/search/files and current actor/site/asset recheck; missing `site_id` denies. Store a report under an approved configured site route, preserving observed/submitted times and same-key retries. A check with no exact approved rule remains Needs assessment. Single and bulk status commands share the same lock/version/idempotency path.
2. Remove the observer's completion/estimated-cost FinancialEvent dispatch while retaining independently necessary H&S behavior. Assert that report, check, note, completion and estimate cannot post or release. This is the first protected evidence checkpoint, due after this slice or 45 minutes of active implementation, whichever arrives first.
3. Add handover, provider appointment/response/cancellation, repair evidence, retest, attributable custody and final reviewer commands. Then wire source-owned restrictions to booking rechecks, follow-up effects, Tasks/profile/calendar projections and canonical FinBill status link. Implement the v8 desktop UI and synthetic browser journeys only on the verified separate browser schema.

Every transition locks the current work order and asset, compares `version`, reauthorises the actual actor and current site/resource, validates the exact policy/source state, appends facts and effects, then commits. A duplicate idempotency key returns the original result; stale/conflicting input returns a safe conflict without side effects. A failed/unknown/stale prerequisite blocks release. No operational rule defaults are introduced.

For check availability, the stored approved exact check rule may explicitly set `availability_impact` to `advisory`. Only that snapshot makes a failed or unassessed check advisory for bookings. Unknown provenance or a missing impact choice remains blocking assessment; explicit restriction rows always block. Release still requires current coverage and a passing retest even when an earlier check was advisory. Booking and release use current locking reads after the canonical asset lock, so MySQL's repeatable-read snapshot cannot hide a hold committed while the operation was waiting.

The desktop flow sends exact `Pacific/Auckland` wall minutes for observation, triage target and provider plan. The server rejects nonexistent spring-forward minutes and requires an explicit offset for repeated fall-back minutes. Site Calendar projects report-owned estimated date ranges as all-day `asset` obligations; it does not create an appointment. All Tasks retains the canonical work-order ID and deep link. Site Calendar links are shown only to users with both site and calendar read capability.

## Legacy, reconciliation and rollback

Migration performs no historical fact backfill. Existing checklist booleans with no exact snapshot remain legacy provenance unknown; existing `out_of_service` assets and work orders retain their current state and holds; existing journals/bills are not reversed or reposted. The read-only reconciliation report counts unmatched work orders, unknown check provenance, out-of-service assets without a new active restriction and historical work-order financial events separately. It does not infer old rule versions from today's templates.
The implemented `maintenance:reconcile-legacy` command reports counts of work orders without a report, check runs without an exact rule snapshot, out-of-service assets without a new active restriction, and historical work-order financial events. It performs no writes or rule inference. Individual historical references still need human review before any data repair.

Only the verified disposable package database may run migration and down testing. Before data is written, migration `down()` can reverse test-only empty schema changes. After data exists, operational rollback is to stop new PKG-01 writes and preserve reports, actions, checks, restrictions and attachments for reconciliation; dropping audit tables is not an accepted production rollback. No production migration, data repair, integration or deployment is authorised at this stage.
