## Existing source mapping and future implementation contract

Read `app/Models/FleetWorkOrder.php`, `app/Http/Controllers/FleetAssets/WorkOrderController.php` and `resources/js/pages/fleet-assets/maintenance/work-orders/show.tsx`. The current controller accepts only `open`, `in_progress`, `on_hold`, `completed`, `cancelled`; the model has `due_at`, `started_at`, `completed_at`, notes/completion notes, but no structured waiting-reason or estimated-start/end fields. The design does not claim the extra waiting labels already persist.

Proposed implementation maps Open/In progress/On hold to the corresponding existing lifecycle values. Awaiting internal feedback/approval/vendor/parts/scheduling are nonterminal waiting reasons; retest/release reasons must also project governed source requirements. Completed/Closed maps to one guarded completion intent and Cancelled to the canonical cancellation path. Decide the exact lifecycle/wait-reason storage and transitions in the bounded implementation scope; do not simply send these presentation strings to the current enum validation. Progress On hold must never be used as the resource safety restriction, and Awaiting approval must not imply Finance approval.

Estimated window ownership belongs to the canonical report/work relationship and selected asset, not an unrelated calendar entry. Future fields need nullable date-only start/end, source/report and resource identity, author/version, and explicit estimate classification. Calendar projection uses the same source key and authorised scope, revalidates IDs/dates on submit, handles stale update/cancellation/retry idempotently, and derives any confirmed appointment from its separate source. `due_at` is not silently repurposed as the range. The exact backend fields/adapter and shared range-picker optional-label support remain implementation work. No new operational policy, booking block, release authority or database migration is approved here.
