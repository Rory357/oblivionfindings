# Source-to-design reuse map

All application and Rory files were read-only. The candidate preserves one operating organisation, roles, approved sites, canonical ownership, direct-object denial and privacy. Legacy organisation columns remain untouched.

- **Identity / placement:** `app/Models/Asset.php` supplies shared Asset identity, Site, legacy SiteHouseRoom and canonical SiteRoom, assignment, document, work, check and device relationships. `app/Http/Controllers/FleetAssets/AssetController.php` and `resources/js/pages/fleet-assets/assets/show.tsx` supply the observed profile projections and vehicle-document delegation. The design makes canonical room ambiguity explicit and does not create another site hierarchy.
- **Assignment / custody:** `app/Services/Assets/AssetAssignmentService.php` and `app/Http/Controllers/AssetAssignmentController.php` establish current assignment target scoping, active-assignment lock, no future effective active assignment, required release and idempotent release. The mockup retains those guard concepts. Dispatched/pending/received/disputed/incomplete loan/transfer behavior is a proposed UI contract, not claimed existing service support.
- **Checks / work:** `app/Services/Fleet/MaintenanceCheckService.php` references `FleetChecklistTemplate`, `FleetChecklistRun` and `FleetWorkOrder`. `MaintenanceReportService` and `MaintenanceRestrictionService` remain the source of work/restriction behavior. `resources/js/pages/fleet-assets/maintenance/work-orders/show.tsx` supplies the observed work detail and progress mapping. Original submissions are projected with references, never rewritten from profile edits.
- **Progress labels:** Open → `open`; In progress → `in_progress`; Awaiting internal feedback/approval/vendor/parts/scheduling → existing `on_hold` plus the corresponding `waiting_reason`; On hold → `on_hold`/other; Completed/Closed → one guarded completed intent; Cancelled → guarded cancellation intent. The prototype does not add enums. Completion and cancellation are blocked in the unresolved sample rather than manufacturing evidence or release authority.
- **Private files:** `app/Models/AssetDocument.php`, `AssetDocumentSet.php`, `app/Http/Controllers/AssetDocumentController.php` and `app/Services/Fleet/VehicleDocumentService.php` establish private/version/source/archive/access vocabulary. Existing Asset upload validation allows one file per request, 20 MB, with the shown extension family. The prototype stages one file per version, displays explicit simulated progress, retains prior versions and forbids opening unavailable/quarantined evidence. Applying the fuller vehicle document-set lifecycle to ordinary assets needs a later approved reuse contract; no competing library or storage endpoint was created.
- **Observation provenance:** `app/Models/AssetScanEvent.php` provides tag-observation source/time/site context. `app/Domain/SecurityDevices/Models/DeviceAssetLink.php` supplies canonical link/unlink ownership. Four location facts remain distinct, with no RF/RFID rollout, second device registry or live command. Optional Device context is a bounded handoff.
- **Finance:** `app/Domain/Finance/Models/FinFixedAsset.php` and `app/Domain/Finance/Presenters/AssetFinanceTechnologyProjectionPresenter.php` preserve linked operational Asset, Finance recognition/depreciation/disposal and separate technology ownership. Invoice approval/posting is projected from Finance; asset edit, work completion and evidence upload never create another expense/journal.
- **Components / kits:** master §§5/5A and WF-05/WF-06 require useful parent/component/kit histories and reconciliation. This preview demonstrates independently maintained components, preserved replacements and per-item receipt. No speculative schema, trivial-part registry or double-counted Finance model is introduced.
- **Register / Vehicle / Site:** PKG-06A owns inventory/registration/import/stocktake. `/fleet-assets/vehicles/{asset}` remains the existing Vehicle Profile. Site and room remain canonical. This profile provides clearly labelled source and return context rather than implementing their separately owned workspaces.
- **Published navigation:** `resources/js/lib/fleet-navigation.ts` is imported directly for the seven Fleet & Assets workspace labels. Navigation publication evidence ties it to `4ea64c547ed85a5b7504e59599db351f6eba7deb`.
- **Actually bundled primitives:** `components/page/page-header.tsx`, `components/page/grouped-profile-nav.tsx`, `components/ui/button.tsx`, `status-badge.tsx`, `dialog.tsx`, `popover.tsx`, `command.tsx`, `tooltip.tsx`, `file-dropzone.tsx` and `components/wizard/shell.tsx`. `build-inputs.json` records the full bundle input list. CSS reads the checkout's app token source and existing Tailwind dependencies; no source component was edited.
- **Design authority:** Main's current `DESIGN.md` and PageHeader/App shell/Navigation/Popup/Work record/List/Button/Design tokens guides. One 20px shell gutter and section gaps, ink chrome, neutral page ground, brand-ramp header, connected rail, positional sub-tabs, visible focus, private evidence and guarded completion follow those references. Desktop-only scope supersedes unused mobile guidance.
