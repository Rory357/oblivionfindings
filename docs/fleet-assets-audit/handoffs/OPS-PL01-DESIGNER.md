**Map:** large greyscale map and searchable side list, semantic markers/clusters, visible legend, fit-to-results and independently scrollable list. Person details show the latest permitted observation, address if already recorded, accuracy/source/time, device/session identity and telemetry summary. Any-address search, if required for an existing boundary workflow, uses synthetic results in this mockup. No real personal data, provider calls or spend.

**People:** operational table/list with person type, permitted site/team, monitoring/session status, last position age, battery/power/movement status and source health. Users can find stale/no-position/low-battery cases without opening every profile. Do not present “no tracker”, “no fix”, “permission ended” and “offline” as the same condition. A viewer denied even the person's identity receives no named row. Avoid a duplicate client/staff directory: link to canonical profiles.

**Person detail:** a panel with Overview, Device & activity and permitted History sections, supporting page-level deep links where appropriate. Reuse the Client Profile Location data/labels. Staff detail links to the authoritative shift/lone-worker session; client detail links to Client Profile → Location and consent/assignment controls where authorised. Show one active canonical device assignment at a time with explicit source selection for genuine multiple sources, not a merged ambiguous stream.

## Telemetry and analytics — mandatory user scope

Include the following in person detail and useful list/filter summaries, with honest state coverage:

- **Battery:** percentage, low-battery state using the approved/configured rule, measured time and unknown/unavailable state. Do not invent remaining-hours estimates from a single sample.
- **Charging:** Charging, Fully charged, Not charging (including reported stopped charging), External power connected, and Charging not reported. External power is not proof that the battery is charging. A missing/default-false power field is not a reported disconnected/not-charging state. Use actual event evidence and signal-specific time; if charging time is unavailable say so instead of borrowing the battery or contact timestamp. Old charging evidence must be labelled old.
- **Movement:** reported moving, reported stationary/rest, unknown, stale and not supported. Distinguish reported sensor motion from a conclusion derived from valid speed observations. Missing speed/GPS or a parser default is not proof of stationary. Device movement is not proof that its assigned person is carrying it or is safe.
- **Connection and positioning:** last device contact, last valid position and accuracy/source separately; GPS/no-fix, signal quality, reporting gap and device health only where capability/source supports them. A new heartbeat does not make an old position/motion/charging reading current.
- **Safety signals:** existing SOS/panic, fall report and man-down semantics where supported. Keep observation, active/acknowledged response and device capability distinct. No report/default false does not prove “no emergency”; a motionless device does not prove a fall or ill health.

**Analytics page:** operational evidence summaries for a selected permitted site/population and period: devices with recent versus stale/missing data, low battery, last reported charging states and reported movement states, each with scope, time/coverage and drilldown to the exact filtered population. Use meaningful defaults and an explicit as-of time. Show counts separately from percentages, state denominators, and exclude inaccessible data before aggregation. Clearly distinguish a current snapshot from a period summary.

Per-person analytics include recorded battery samples, charging/power-event timeline, reported movement/activity timeline, reporting gaps and permitted location history. Show gaps as gaps; no continuous movement/charging durations across missing observations, invented routes, health inference, worker productivity ranking or unapproved safety score. Any derived duration/rate must disclose its calculation, observed coverage and limits, and remains a labelled proposal if the backend does not supply it. Only include period charts for signals actually stored historically; otherwise demonstrate an honest “History not available for this signal” state and record the dependency. Do not invent stored data or new ingestion solely to make a mockup chart look complete.

## Alerts, history and Settings

**Alerts:** surface existing person/device/session exceptions with original source/time, delivery state, owner and response status. Deep-link or compose the canonical Control Room/lone-worker response; no duplicate queue, separate acknowledgement or emergency bypass. A missing position is an information problem until an applicable approved response rule says otherwise. Include relevant low battery, missing report, boundary and overdue check-in examples as synthetic configured scenarios, not newly approved thresholds.

**History:** selected person/source/date range with map/list timeline, exact observation age, gaps and original event detail. Consent, collection/session, retention and assignment windows bound the available history. Device reassignment must not disclose the previous wearer's trail. Viewing, export and locate/configuration are distinct permissions; history/export access is not implied by map access. Preserve existing export audit/private-data rules. All preview exports/requests are synthetic.

**Settings page:** separate ordinary display preferences from restricted monitoring controls. Include default site/population/layers, freshness-display rules, capability-aware reporting/check-in configuration, alert routing/threshold presentation, role/site access, history/export/retention summaries, and source/device health. Show what is inherited/read-only, unconfigured, pending device acknowledgement, applied or failed; screen refresh and device sampling frequency are separate. Save/cancel/review/conflict/permission-loss states must be interactive. Unconfigured operating thresholds remain unconfigured, not silently approved. Settings must reuse/link canonical Device assignments/configuration, client consent/authority, staff session rules, Control Room routing and shared provider settings; it must not create another policy/consent store or take over PKG-08's system-wide provider administration.

Staff being rostered/clocked-in is not automatic permission for continuous tracking. Respect the existing approved work/session boundary and show session-ended/unavailable states. Client consent, viewer permission and any family sharing are independent. Loss/withdrawal/expiry of authority clears sensitive markers, detail, counts, charts and history immediately in the preview state machine; browser Back or late polling must not resurrect them. Preserve the selected inaccessible state without leaking cached details. Do not add policy overrides by changing navigation.
