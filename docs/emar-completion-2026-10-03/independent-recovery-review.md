### R1 — P1: medication-error Tasks bypass the register's person and reporter restrictions

Owner: P08b with Main/Tasks integration. Present in WIP at `emar-p08b-errors` HEAD `899d3815f84856cdc8b0744c61317280f4c0f251`, read 2026-10-03T09:40:16Z. This is a carried-forward provider defect, not proof that the new P08b change introduced it.

- Evidence: `app/Services/Tasks/Providers/MedicationErrorProvider.php:57-70` restricts only canonical person/medicine ownership, approved Site and controlled classification. It does not apply `MedicationRecordAccess::readableClientIds` or the register's reporter restriction. Its projector at lines 75-102 returns the person's name/ID, error type, reach summary, due time, owner and error link. `TaskProviderAuthorization.php:38-43` executes that supplied query with no additional person policy.
- The package's actual error register at `MedicationErrorController.php:164-170` first limits openable people, then limits ordinary workers to their own reports. `MedicationRecordAccess.php:91-93` delegates to the canonical person gate. Therefore the claim in the provider's lines 48-52 that it mirrors the register is false.
- Synthetic trigger: give worker A `medications.view` and approved Site S, assign A only to person X, and create a non-controlled error for person Y at S reported by B. Y fails `viewMedications`/the register query, but `MedicationErrorProvider::authorizedTasks(A)` returns Y's error. Even for readable X, A can see B's report when the register exposes only A's reports. All Tasks/search/export/detail consumers using this provider inherit the omission.
- Fix: reuse the register's canonical readable-person and ordinary-reporter scope in the provider before fetching/projecting, and retain the existing CD filter. Verify list, direct ID, search, counts and export with a same-Site unassigned person and another reporter.

## Shared source API adoption review

P08a's committed foundation provides a stable unique `source_key`, retains `original_owner_id`, and records source/workflow changes within the caller's transaction. `ensure` binds type/person/medicine/administration identity on reuse; it does not overwrite the original owner or silently retime existing work. `updateSourceContext` increments revision and appends a workflow event; public requests cannot submit context. It is not a replay receipt: identical source updates still append/increment, so source adapters must deduplicate their own retries.

`completeFromSource` deliberately trusts the authorized source caller for non-confirmation types. It is not an authorization service and must not become a general public endpoint. Confirmation answers are restricted to the named nominee; a system expiry can use a null actor. A negative/expired answer creates one disputed follow-up without certifying a dose. The public transition path refuses generic completion of confirmation and other source-owned checks. Its own request UUID is bound to actor/payload, and replay is evaluated before the stale revision check. Locked transitions recheck current person/Site/RBAC/profile and CD authority.

Single-source completion acquires the chain head as its final operation. Batch callers must use `completeSources`, or correctly accumulate and flush its audit buffer once after all domain/source writes; omitting that flush would omit P09 evidence. Each caller must acquire the canonical Client/medicine/source and current authorization evidence before entering these trusted APIs. Do not perform later domain locks after an immediate completion append. The foundation's batch implementation is useful evidence of the intended contract, not proof every downstream adapter follows it.

The dose hook at `EnhancedMarService.php:1465` runs inside the dose transaction. The handover hook at `ShiftHandoverService.php:733` runs inside acknowledgement's validated aggregate transaction; it transfers eligible unfinished work and keeps the original owner. It does not mark effects/refusals complete or block handover on an overdue follow-up. Existing tests cover identical request replay, source-only denial, negative confirmation, carry-over, and recorder failure rolling back effect/history/workflow; their source was inspected, not executed. Accepted-correction synchronization (R3), changed source receipts (R4), and joined PIN/source/Tasks projections still need integrated evidence.
