- Only monitors with `affects_availability` currently emit these device events. Sustained non-availability technical faults have stored monitor/observation data, but lack the corresponding IT event adapter. Do not label such monitors healthy merely because no availability event was emitted.
- `DeviceEventObserver` maps alarm, tamper, motion, door open/closed, low battery, offline/online, firmware update, maintenance due, configuration change and generic signals into the canonical signal pipeline. This is the confirmed direct nonurgent intake gap.
- Existing tests require one active linked ticket for repeated evidence, a fresh incident for a later fault after resolution, recovery evidence without automatic resolution/closure, and no blanket conversion of security or healthcare signals. Preserve those boundaries.

## Recovery adapter implementation constraints

The following constraints guided the implemented backend adapter. The ten new Feature cases verify the listed serial/replay/scope outcomes; actual recovery-worker contention also passes the expanded 80-assertion standalone test. Downstream IT/browser acceptance remains open:

- Bind an offline episode to persisted source evidence at detection time, including its canonical device/asset link and Site when available. New offline signals now include the source event and canonical scope; earlier records may carry only last_seen_at and a deterministic key. Looking up the asset's current Site later is insufficient proof of its original scope after a move.
- Lock the snapshot before reading prior offline status during ingestion. Derive the matching offline episode from that prior state before saving the newly received event. Keep source/outbox/transition atomic and enqueue after commit.
- A newly paired replacement device must not establish recovery for the old device simply because it shares an asset. Validate previous and current canonical event/device/link identities. Legacy records lacking authoritative episode/scope evidence need an explicit unmatched/manual-verification outcome.
- Process fleet_device_online as recovery evidence, never as a new generic alarm and never through the native device_online handler. Match the exact Fleet source episode and Site, preserve audit history and require IT verification rather than automatically closing work.
- Cover recovery delivered before the offline outbox, duplicate recovery, an older recovery arriving after a later offline episode, rollback/retry, re-pairing and Site changes. Avoid cross-locking another outbox while holding an episode lock; both dispatch paths must use a consistent lock order.
- Availability projections must contain safe technical evidence, not arbitrary Fleet payloads, location, person or trip context. Current source availability and approved canonical scope must be checked before automatic IT publication.
