# W08 completion and cancellation history: next slice

Read-only design, 9 September 2026, against W08/E06/E07 and current sources. Coordinated with W01's `w08-command-and-lifecycle-contract.md` completion-table outline. This adds implementation detail to that outline; no migration, service, fixture or test changed, and no test ran. Application edits remain held until the root releases the live browser and task foundation test checkpoints.

## Preserve the current foundation

`ItWorkTaskCommandService` already binds original actor/ticket/task/operation/UUID/version, serializes writes, retains opaque receipts, fences an uncertain command with cancellation, and separates replay from fresh current-task review. `ItWorkTaskService` now advances the ticket version and requires transactional events/audit. Extend these paths; do not introduce another command ledger or task inventory.

The remaining confirmed history defects are narrow: `complete()` stores evidence and note only on the mutable task; `reopen()` clears them; completion event/audit retains only an evidence count. `update(status=in_progress)` has no prerequisite gate. Settlement reads required-task status only. Cancellation records its reason in the current `work_task_updated` event, but restoring a cancelled task through ordinary update needs no reason and has no distinct restoration history.

## Minimum additive record contract

1. Add one `ItWorkTaskCompletion` child of the existing task, with `(task_id, sequence)` unique. Store actual `completed_at`, original completed actor ID (nullable if genuinely unknown), `recorded_at`, source `command` or `legacy_snapshot`, completion note/evidence, and a bounded task-definition snapshot (title, description, required/evidence-required flags). This preserves what was completed if the task is later edited. Preserve original actor ID as provenance without a foreign-key delete action silently rewriting the snapshot; display a missing current actor honestly.
2. Record the exact prerequisite task/completion ID pairs and canonical approval request ID used by this completion. Distinguish `[]` (known no prerequisites) from `null` (legacy provenance unknown). There is no approval `version` in the present model: the existing immutable terminal approval row ID identifies the request generation. Do not manufacture an approval version or infer a prior approval from the latest row at capture time.
3. A nullable `current_completion_id` on `ItWorkTask` is the smallest explicit active-generation pointer. Validate its same-task binding in the locked service. Existing current evidence/completion fields remain compatibility projections; complete writes snapshot, pointer and projections together, while reopen clears only the current pointer/projections. History is append-only in the application, with no edit/delete endpoint or destructive rollback of populated history. New records use single-organisation task/site authorization, with no new tenant column.
4. Reuse `ItTicketEvent` plus required audit for task cancellation, restoration and reopening. New private event types `work_task_cancelled` / `work_task_restored` carry task ID, from/to state, reason and relevant completion/dependency IDs. Existing event rows stay untouched. A second generic task-transition table is unnecessary for this slice; completion payloads belong in their canonical history row, not public timeline or receipt metadata.
5. Keep `ItTicketApproval` as the canonical request and terminal decision record. A re-request creates a new row; it never resets an approved/rejected row to pending. Later approval lifetime work can add distinct request/decision reason fields and cancellation/expiry attributes. Existing overwritten `reason` cannot be reconstructed as two historical facts and must be labelled legacy if presented separately.

No historical batch backfill is proposed. Before reopening an existing completed task with no completion row, capture only extant fields and known actor/time as `legacy_snapshot`, once under the task lock; `recorded_at` is capture time, never claimed completion time. Do not reconstruct missing prerequisite or approval provenance from today's state. A capture helper must also be safe when a future completion first references an unchanged legacy completed prerequisite; its unknown prior provenance remains labelled. Whether unknown legacy bindings become a release blocker needs an explicit compatibility decision before evaluator rollout; installing the table alone must not silently invalidate every historical completed task.

## Transition and blocker semantics

- **Complete:** require all current prerequisites to have valid completions and any explicitly linked approval generation to be approved. Evaluate and snapshot under the existing ticket → ordered people → receipt → ordered task/dependency lock order. One committed command produces one history row/event/audit/version advance; replay adds none. History/audit failure rolls back the whole change. Unknown post-commit acknowledgement recovers the original result without generating another completion.
- **Reopen completed task:** require the current original-version command and reason, preserve/capture its completion, then return the task to pending. Do not mutate descendant statuses or erase their completion rows. Preview affected descendants before applying and show that their recorded prerequisite completion is no longer current.
- **Cancel optional task:** preserve current permission rules: a required task cannot be cancelled unless the reviewed proposal explicitly makes it optional. Require a reason, retain dependency links and record the transition once. A completed task must first be reopened. A cancelled prerequisite remains a blocker; it never counts as completed.
- **Restore cancelled task:** use the existing `update` command namespace with a reviewed transition back to pending and a reason. Preserve cancellation history, assignment and dependency links, and reevaluate blockers. Do not implicitly restore a prior completed state or jump past unmet prerequisites. This is task-state restoration; cancelling an uncertain HTTP command is a separate existing receipt tombstone and changes no task state.
- **Replace/remove a prerequisite:** require a reason and explicit impact review. Pending/in-progress tasks may repair their dependency set through the versioned update; a completed dependent must first reopen. Preserve the former dependency bindings in its old completion. No automatic descendant reopening or silent link deletion.
- **Canonical current verdict:** one bounded evaluator used by start, complete, settlement and read projections should compare every recorded prerequisite completion ID with that prerequisite's current valid completion, including transitive invalidity. A later completion of the prerequisite does not retroactively validate a dependent's old evidence. The dependent requires explicit reopen/recompletion; an unchanged old completion remains historical fact. Return safe blocker codes and authorized task/approval links, not private evidence in generic errors. Optional unrelated unfinished tasks still do not prevent settlement; a required task with invalid current provenance does. GET projections are nonmutating and use the same evaluator.

Approval linkage must reference the correct request rather than the current `ticket.requires_approval` boolean alone. Task-to-approval relation and catalogue creation are the W08/W15 seam. Expiry/cover/reminder defaults, approved-verdict validity after changed scope and authority for legacy unassigned requests remain the operational dependencies already recorded by W01; this history slice does not choose them.

## Focused implementation files and regressions

After release, the minimum source set is a new completion model/additive migration, `ItWorkTask` relations/pointer, narrow `ItWorkTaskService` completion/reopen/cancel/restore paths, and the canonical blocker evaluator. Integrate its verdict into `ItWorkTransitionService::guardSettlement`, `ItTicketContextPresenter`, current work panel and existing personal task providers. Keep `canWork` as the private task/history projection boundary; `ItWorkTaskPolicy::view` alone is broader and is insufficient for evidence. History IDs must be resolved through the authorized nested task, including any later governed merge handling.

Required focused regressions:

1. Complete → reopen → edit definition → recomplete retains both exact notes/evidence/definitions/actors/times; current projection points only to the new completion. Duplicate replay and identical concurrent completion create one generation.
2. Legacy reopen captures extant evidence exactly once; absent actor/time/bindings stay null and are labelled unknown. Reopen failure leaves legacy/current data intact. Removing an actor does not rewrite existing history or prevent later mechanical reads.
3. Pending, cancelled and reopened prerequisites block start and completion. Recomplete prerequisite A does not silently validate dependent B's old reference to A's previous completion; transitive dependent C also shows the current blocker. Explicit B/C reopen/recompletion repairs it without deleting old evidence.
4. Required cancellation denial, explicit optional cancellation, reasoned restore, unchanged repeated update, and dependency replacement each have the exact intended history/version count. Receipt cancellation never creates a task-cancelled event.
5. Correct approval request unlocks its linked task; rejected/pending/wrong-ticket/wrong-generation approval does not. Earlier approved evidence stays immutable when a later request is created or expires under the eventual policy.
6. Audit/history write failure rolls back task/pointer/receipt/version together; post-commit response loss recovers the same completion. Real two-worker complete/reopen/settle and prerequisite repair races cannot acknowledge contradictory current states.
7. Required invalid work prevents settlement with a current authorized corrective link; optional unrelated work does not. Presenter/personal task/settlement verdicts agree without writing on GET.
8. Requester-only, wrong Site, sensitive-scope loss, wrong nested task/history ID and in-place access revocation expose no private definition/evidence/reason. Desktop keyboard review/reopen/cancel/restore preserves entered work and original version through rejection, unknown response and renewed authorization.

These are acceptance recommendations, not executed results. The next dependency-ready implementation is immutable completion capture and typed cancellation/restoration history; full W08 remains incomplete until blocker, approval lifetime, personal-work and real browser acceptance are also verified.
