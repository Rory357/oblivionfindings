# W07 attachment capability mapping

Read-only prerequisite review, 9 September 2026. Read the exact W07/E05 requirements and `w07-interaction-prerequisite-review.md`, then inspected the canonical IT, consent-evidence, Device-document and shared private-download paths. No application code, configuration, database, provider or real attachment was changed or executed. This is an integration recommendation, not W07 implementation/verification.

## Canonical records and services to retain

`app/Models/ItAttachment.php` is the existing polymorphic IT record for tickets, comments and the W06 draft owner. Its fixed disk is `private`, directory `it_attachments`; direct download is `/it/attachments/{attachment}`. Existing limits are five files per request/draft, 10MiB per file, with the existing extension/MIME allowlist excluding HTML/SVG/scriptables. Preserve the record and approved limit contract rather than creating another upload table or public file directory.

`app/Domain/It/Services/ItAttachmentStorageService.php::store` is already called by both canonical intake and interaction services. It stores through the private disk and creates the parent's attachment rows. `storeReserved` accepts only a draft-owned opaque path and reserved/failed storage state. It confirms the returned storage path, but ordinary `store` currently retains client-provided MIME/name metadata and neither path establishes a malware verdict. `deleteStored` currently delegates deletion without checking the returned result; W07/W26 recovery should use tracked deletion intents where retained state is required, preserving W02's uncertain-commit attachment protections.

`ItTicketDraftAttachmentService` is the existing durable staging foundation. Its current contract is:

- `upload(actor, draftUuid, expectedRevision, uploadUuid, UploadedFile)` validates size/type, hashes input bytes, serializes against the current actor/draft, commits an opaque reserved path before writing, and makes retries of the same upload UUID compare original name/hash/owner. A ready retry does not create another row/path.
- The private copy and readiness transition share canonical locks. A failed or uncertain physical write retains the reservation and returns a typed recoverable error. `ready` currently means stored, **not malware clean**.
- `remove` records `cleanup_pending` before physical deletion. A successful active-generation removal leaves a tombstone, so delayed upload retry cannot resurrect it. Failed deletion increments bounded safe evidence and is retryable.
- `transfer` reassigns these same rows inside the ticket/comment transaction. It accepts only the matching intake, public-reply or internal-note target, caps combined files at five, and requires storage readiness. No path copy or second attachment system is needed.
- `authorizeDownload` rechecks current draft actor/generation/audience and storage readiness. `forResume` exposes authorized metadata and a protected URL only for ready files. Add scan readiness to these existing boundaries; do not reuse storage `ready` as a clean verdict.

`app/Http/Controllers/It/ItTicketController.php::downloadAttachment` resolves the canonical parent. Ticket files require current ticket visibility/policy; comment files additionally require `canWork` for an internal note; draft files use the current draft service. Orphans/other morph types deny. Both download and any future preview must use this same current parent/audience boundary and additionally require an appropriate scan verdict. Canonical public/internal projections must not expose an internal attachment's metadata merely because its URL will later deny.

`app/Http/Controllers/Concerns/ServesPrivateAttachments.php` is the shared hardened response primitive across IT, H&S, Privacy, HR and other modules. It checks existence and streams the private object with CSP sandbox/default-src none/frame-ancestors none and no-referrer. Its caller owns authorization; it does not scan, verify a content digest or record quarantine. `config/filesystems.php` configures `private` as a local disk rooted at `storage/app/private`, `serve=false`, with failed operations able to return false (`throw=false`). Retain explicit return-value checks. The similarly rooted `local` disk has a different serving contract and should not replace IT's explicit private disk.

## Existing executable scanner and integrity capability

The only malware-execution wrapper found in application/config PHP is `app/Services/Consents/ConsentEvidenceMalwareScanner.php::scan(UploadedFile)`. It returns `{disposition: clean|infected|unavailable, scanner: string}`. It accepts a configured executable path, validates file readability, invokes Symfony Process with an argument array (no shell), supplies `--no-summary` and optional `--fdpass`, and bounds timeout to 1–120 seconds. Existing code maps process exit 0 to clean, 1 to infected, everything else and exceptions to unavailable. This describes repository behavior; no real scanner was invoked or independently verified in this review.

`config/consent-evidence.php` currently owns the configured binary/name/fd-pass/timeout using `CONSENT_EVIDENCE_SCANNER_*`. An absent/unusable binary fails closed. There is no general-purpose scanner interface or async quarantine worker in the searched application paths. The smallest maintainable reuse is to extract the executable adapter into a neutral shared service, retaining `ConsentEvidenceMalwareScanner` as a compatibility adapter so existing consent behavior, tests and environment configuration remain intact. IT should call that same approved scanner capability, not copy the process runner or configure a second scanning provider. Any neutral configuration move needs backwards-compatible resolution and an explicit operational owner; it must not silently change deployed consent settings.

`ConsentEvidenceService::prepare` adds a reusable integrity pattern: server-detected MIME with content checks for its narrow PDF/JPEG/PNG domain, pre-scan hash, scan verdict, post-scan hash equality, private storage and stored size/hash equality. It rejects unavailable/infected scanning before producing a valid evidence record. It does not persist infected/quarantined files, offer scan retry, or support IT's broader file types. Do not call its whole prepare method for IT or reuse its consent-specific record columns, filename rules or retention policy.

`ConsentEvidenceService::openVerifiedStream` copies a bounded private stream into a verified temporary stream, checks immutable byte count/SHA256 and returns that same rewound handle. This avoids verify-then-reopen races and is a useful shared integrity primitive if extracted narrowly. The consent permission/controller remains consent-owned. Existing consent tests explicitly mock the scanner and cover infected/unavailable dispositions, changed bytes during scanning, integrity failure, rollback and authorization; they prove application behavior under those outcomes, not an installed production scanner.

## Other storage/recovery patterns and their limits

`app/Domain/SecurityDevices/Services/DeviceDocumentLifecycleService.php` uses canonical DeviceDocument rows as durable storage intents: `upload_staged → active`, `removal_pending → removed`, private staged/final/quarantine paths, immutable content hash, operation UUID, verified downloads, required audit writes, replayable move/delete and bounded reconciliation. `security-devices:reconcile-document-storage --limit=100` is scheduled every minute with overlap/server guards. Its `.quarantine` is the intermediate path for **authorized document removal**. It is not a malware disposition, and an active Device document is not thereby proved malware-clean. Its one-hour unreferenced-stage grace is Device-owned storage cleanup, not an approved IT retention period. Reuse its durable-state/reconciliation approach without passing IT files through Device records or applying Device policies.

`app/Domain/Clinical/Services/ClinicalAttachmentService.php` has an attach/attachMany helper but stores its own records on the public disk and has no scan/quarantine contract. It is not a safe canonical base for IT private evidence. No unrelated clinical rewrite is proposed.

W06 already provides `ItTicketDraftPruner` and command `it.prune-drafts`: bounded chunks, encrypted-text scrubbing on expiry, terminal metadata lifecycle, physical cleanup retry and preservation of transferred ticket/comment attachments. It deliberately requires the effective reviewed IT draft retention configuration. Exact command search across app/routes/config found no scheduler/catalog registration yet; manual pruner tests do not prove automatic recovery. Before activation, register and monitor this command through the canonical automation facilities. A future malware-quarantine retry/retention path must remain distinct from draft storage cleanup so disabling drafts cannot strand infected ticket/comment objects or label them downloadable.

## Smallest canonical IT implementation path

1. Preserve ItAttachment and its parent access rules. Add explicit scan metadata/state alongside, not in place of, the W06 storage state: unverified/pending, clean, quarantined and scan-unavailable/failed as distinct outcomes, with immutable byte digest, safe failure code, scanner evidence and attempt identity. Keep legacy files unverified until an authorized scan or documented migration policy establishes their status; do not backfill fabricated clean verdicts.
2. Reuse/extract the existing process scanner behind one neutral typed contract. Stage through IT's tracked private path before any retryable async work. A scan result must apply only to the exact current attachment/hash/attempt; stale completion after removal, transfer or replacement cannot republish a file. Separate scan success from persisted comment success and notification delivery success.
3. Gate existing download/preview, presentation URLs and draft-to-comment transfer on current audience, storage integrity and the scan result appropriate to the chosen commit policy. Keep unavailable/quarantined files visibly unavailable with a real retry/remove action. Preserve composer text and original File/UUID on known rejection or unknown transport outcome.
4. Extend existing durable IT cleanup/reconciliation patterns for scan retries and quarantine removal, with canonical permissions/audit and bounded jobs. Do not hold long provider execution inside the whole comment transaction or block unrelated text-only intake during a scanner outage. Whether a comment can commit with an unavailable attachment is a consequential delivery policy to make explicit, not infer from storage readiness.
5. Verify focused fake-scanner clean/infected/unavailable/timeout/hash-change outcomes, same-UUID retry, late-scan-versus-remove concurrency, copied public/internal/preview URL denial, revoked scope, exact comment attachment ownership and durable cleanup failure/retry. Then run an approved real scanner fixture in an isolated environment and the desktop composer/browser journeys. E05 and W07 remain open until those proofs and the full conversation/watcher/delivery slice are complete.

No tests were run for this mapping. Existing tests were read; actual results must be taken from their execution evidence, not inferred from source names. Two initial guessed filenames/glob paths did not exist and were replaced with repository searches; unrelated historical audit files denied during a text search were not needed or bypassed.
