## Current implementation and isolated verification

Confirmed old defects: Gmail recursively selected the first matching text MIME part even when it was a named attachment; decoding was permissive/unbounded and missing content could become a short provider snippet. Gmail detail did not compare its returned transport ID with the requested ID. Graph similarly used bodyPreview when content was missing. Automatic-response and delivery-report fields were not classified.

New ItEmailContent extracts only the outer message body, prefers text/plain inside alternatives, joins separate inline text portions and skips named/explicit/forwarded attachments as conversation content. It bounds100 MIME parts/depth12,1MiB per decoded part,2MiB combined decoded bodies and100000 final UTF-8 bytes. Strict base64/base64url and declared-size checks prevent partial decoding; charset conversion checks invalid input. Gmail external body references use the provider attachment endpoint for the exact message and preserve transport failures for retry. A preview is never substituted for a missing full body. Graph body shape/type/encoding is checked. These are MIME/parser bounds, not proof of a streaming HTTP response-size limit.

Auto-Submitted values other than no and MIME delivery/report types settle the canonical discovery receipt as quarantined through typed ItInboundContentException, without storing body/author/thread payload or generating a ticket notification. The normalized webhook also accepts bounded classification metadata and uses the same decision. This does not authenticate a DSN as proof of delivery failure; outbound status is not changed. Complete loop handling still needs generated-notification headers/reflected-message review.
