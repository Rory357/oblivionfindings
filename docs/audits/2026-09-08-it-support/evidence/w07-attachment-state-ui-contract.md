# W07 attachment states — bounded next-slice contract

Read-only preparation, 9 September 2026, during root's Build9/browser ownership. This document is a proposal, not implemented or browser-verified functionality. No application file, migration, helper, configuration, provider, attachment or database was changed; no test/import/build was started for this review.

Scope: W07's recoverable oversize/disallowed/failed uploads and explicit scanner failure/quarantine, E05 public/internal attachments and copied-URL denial, and E06 retained work under failure/concurrency/access loss. This does **not** decide whether a reply with a held file should commit its text or remain wholly uncommitted. The earlier scanner proposal's suggested choice is not an approved operational policy.

## Current source and defaults to preserve

- `app/Models/ItAttachment.php` remains the canonical ticket/comment/draft attachment. Preserve the private disk, opaque IT paths, five-file combined cap, 10MiB per-file cap, and existing extension/MIME allowlist. Laravel's server validation remains authoritative; client extension checks only explain likely rejection early.
- `ItAttachmentStorageService`, `ItAttachmentStorageIntentService`, `ItTicketIntakeService` and `ItTicketInteractionService` now use the durable direct-storage intent foundation. The older capability map's description of active untracked intake/reply callers is superseded. Current direct storage records server-detected MIME. Empty-file commands bypass storage-table readiness; actual files fail closed with an actionable `attachments` validation error if storage setup is missing. Do not add a fallback to untracked writes.
- `ItTicketDraftAttachmentService` already reserves an immutable upload identity before bytes, preserves uncertain writes, retries the same file/name/hash/UUID, and records removal/cleanup tombstones. Its `ready` state means **stored**, not scanned. Transfer moves the same canonical rows inside the command transaction and currently requires all staged files to be storage-ready. Keep its original generation, audience, revision and total-file checks.
- IT currently has no persisted malware verdict, scanner invocation or scan gate. Current download authorization resolves the canonical parent and current user; internal comments additionally require current `canWork`, and draft downloads require the current owner/generation/audience. Authorized stored files currently receive download URLs without a scan verdict. Preserve that default until an explicit activation and historical-file policy are agreed; never fabricate a historical clean result.
- The shared private-stream trait provides existing response hardening but no content digest or malware decision. Do not change every consuming module's behavior to implement IT policy.
- `app/Services/Files/MalwareScanner.php` now supplies the neutral executable adapter. Its typed result is clean/infected/unavailable; safe failure codes are `scanner_unavailable`, `file_unavailable`, `scanner_timeout`, and `scanner_failed`. It uses an argument-array Process and a bounded timeout. The consent compatibility adapter/configuration are unchanged. Do not make IT silently inherit consent environment settings or select/install an executable.
- Direct reply/intake commands retain their current transaction, receipt and exact-retry behavior. There is no new partial-text commit policy. A failed or unknown attached submission must not automatically drop files or send a text-only replacement.
- Keep the current effective persisted-draft enablement and reviewed retention gates unchanged. The storage-intent cleanup states and Device document removal `.quarantine` are not malware verdicts or approved IT quarantine retention.

## Dependency-ready implementation without a new operational policy

1. **Close file-validation presentation against the current contract.** Reuse the existing composer, `TicketDraftFiles` in `ticket-intake-draft.tsx`, draft recovery controls and command transport. The composer already rejects excess count, oversize files and disallowed extensions while preserving existing text/files; the server already returns `attachments` / `attachments.N` errors. Add only confirmed missing field-specific presentation/focus and recovery tests. Keep original File objects while a request is unknown. Show the existing storage-setup error as an upload availability problem, not scanner downtime. A malformed response or proxy error is not proof the comment failed; use canonical receipt recovery before another command.
2. **Introduce one additive attachment presentation contract, with scan integration inactive.** Extend canonical IT presentation rather than a second file register. Existing files project `unverified`, never `clean` or `unavailable`. `unavailable` requires an actual attempted scan with a recorded safe failure. Runtime scan invocation/enforcement stays inactive. Build components and strict parsers against fixture-provided future states so there is no production mock or dead control.
3. **Prepare the dormant scan lifecycle behind an explicit IT activation gate.** It may be implemented and tested independently using injected scanner results, but must not be called by current upload, reply, transfer or download paths until the policy gate below is resolved. Preserve exact attachment bytes, attempt identity and current ownership when recording a result. Do not schedule real work, acquire quarantine custody, or create automatic expiry as part of this prerequisite slice.

The first two steps improve current error truth and make later states representable. They do not complete W07's actual scan/quarantine acceptance. If no durable scan lifecycle is implemented yet, its actions must remain absent and its tests must be clearly labelled presentation-contract tests.

## Minimal typed projection and UI rules

Keep existing attachment identity/name/size and upload `state`. Add a separate `scan` object with `state: unverified | pending | scanning | clean | unavailable | quarantined`, `checked_at: ISO timestamp | null`, and an allowlisted `error_code | null`. Add canonical per-record capabilities for `download`, `preview`, and `retry_scan`; draft removal continues to use the existing draft capability and endpoint. Public payloads need no executable path, process output, content hash, signatures, storage path or quarantine location.

- `unverified`: “Scan not recorded.” This describes evidence, not a detected threat or failed operation. Existing download behavior remains unchanged while integration is inactive.
- `pending` / `scanning`: “Waiting for file check” / “Checking file.” Only project these from an actual durable intent/claim. No invented percentage or estimated completion time.
- `clean`: “File check passed,” based on the recorded verdict for those exact bytes. Do not promise absolute file safety.
- `unavailable`: “File check could not finish,” with a safe reason and Retry only when a real authorized retry command is available. This must not say the reply was unsent if its receipt says committed.
- `quarantined`: “File held after a security check,” only after the real infected result has established an enforced access hold and tracked custody. The adapter's `infected` result alone is not evidence that quarantine storage/access control completed. Do not offer ordinary users a release/override action without an approved permission and policy.

An availability decision must come from the current canonical parent/audience and lifecycle, not a client switch over scan status. A blocked file has no actionable download/preview anchor. Preserve the authorized filename and size in its owning audience so the failure is understandable; do not expose internal filenames through a public projection. Use the existing approved card/status/button patterns and a live status/error region; retry, remove and cancel remain keyboard reachable with stable focus.

Exact coupled extension points:

- `ItTicketController::showPayload` currently maps ticket/comment attachments to `{id,name,size,url}` and always supplies a URL. Move the duplicated scan/availability decisions into one narrow IT presenter used by this map and the draft service.
- `ItTicketDraftAttachmentService::present` currently returns `download_url` whenever storage is ready. Keep storage state separate; future enforced holds require a nullable URL even for `ready`.
- `resources/js/hooks/it-ticket-draft-contract.ts::readDraftAttachment` currently **requires** the canonical download URL for `ready`. Extend it together with the backend contract so a legitimately held ready file is accepted, while malformed states/URLs still fail closed. Do not loosen it to arbitrary URLs.
- `ticket-thread.tsx::AttachmentChips` currently always renders an anchor; its `ThreadAttachment` type needs a nullable URL and the shared state projection. Root owns this file during the current build.
- `ticket-intake-draft.tsx::TicketDraftFiles` currently distinguishes only “Saved to draft” from “Upload incomplete.” Retain that storage wording and add separate scan status. `use-it-ticket-draft.ts` retains existing exact-upload retry/removal semantics; `ticket-reply-composer.tsx` retains direct-file validation and draft/direct branches.
- The command hooks' strict validation allowlists must explicitly recognize any added safe typed file errors. Do not display arbitrary provider output or clear canonical unknown-command state on a file-status response.

## Dormant lifecycle and retry invariants

Use additive metadata on `ItAttachment`, not another attachment owner. The required evidence is the exact content digest/size, scan attempt UUID, monotonic scan revision, claim/check timestamps, safe scanner identifier/error code and persisted disposition. A scan runs outside the business transaction and any long-held ticket/draft locks. It applies only under a current lock when attachment identity, bytes, active attempt and allowed parent/generation still match. A late result must not resurrect a removed file, publish an internal file in a public audience, or change a newer result. A transferred file needs explicit reconciliation to its current canonical parent, not a stale draft write.

A future retry command binds the original actor, attachment, expected scan revision and operation UUID. It must reauthorize at the locked write, acknowledge an identical accepted attempt without starting another process, and return a stale conflict for an opposing/newer attempt. It retries the **scan of the same stored bytes**, not the upload or whole reply. Remove continues through the existing draft tombstone path; this proposal grants no submitted-file deletion entitlement. “Cancel wait” only cancels the client wait, retains uncertainty and allows status review. A separate server cancellation control requires a real persisted cancellation transition and race tests before it may be rendered.

Protected download/preview enforcement and integrity checks are coupled to activation. Reuse the existing canonical parent policy and extract only the verified-stream pattern needed to serve the same bytes whose digest was checked; do not verify a path and reopen changed bytes. Retained unavailable/infected bytes cannot be deleted by age, missing receipt, missing current attachment or the Device removal grace period. Cleanup requires canonical evidence and the separately agreed retention/custody rules.
