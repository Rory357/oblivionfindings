# W19 resource scheduling: canonical integration map

Source inspection, 9 September 2026. **Planned only; no scheduling implementation or verification is claimed.** This bounded map covers the added requirement for multiple technicians and multiple separately scheduled work blocks on one ticket, with one accountable owner. It follows W19, W08 and E18 in `implementation-plan.md` and `docs/architecture/single-tenant-application.md`. No runtime code, schema, assets, provider configuration or operational assignments changed. Current frontend sources remained frozen for the coordinated W07 build.

## Existing sources and confirmed gaps

**Ticket work remains canonical.** `app/Models/ItWorkTask.php` already owns ticket-linked work, parent/child tasks, dependencies, required work, evidence, completion and cancellation state. It has one `assigned_to_user_id` and `due_at`; it has no scheduled start/end interval or collection of separately assigned resource blocks. `app/Domain/It/Services/ItWorkTaskService.php` locks the parent ticket and task, repeats `ItWorkAccessService::canWork`, rejects merged/settled work, validates canonical technician choices and same-ticket dependencies, rejects cycles, and records ticket events plus fail-closed audit in the transaction. Its inspected mutation methods do not yet compare a submitted task version. Complete that W08 contract before extending it with W19 scheduling. Retain the ticket's existing accountable `owner_user_id`; resource participation must not create several accountable owners or repeatedly overwrite the primary ticket assignee.

**Personal work already has a projection framework.** `app/Services/Tasks/TaskAggregator.php`, `TaskItem.php`, `Contracts/TaskProvider.php` and `TaskProviderAuthorization.php` aggregate source records without persisting duplicate tasks. `app/Http/Controllers/AllTasksController.php` consumes that feed for `/tasks`; `MyTasksController::getMyAggregatedTasks` filters it to the current assignee for My Day. The current registry has no IT provider. `TaskItem` has one assignee and a stable source-plus-record identity: a work allocation can therefore be projected for its individual technician without duplicating its parent task. W08 should establish the IT task provider; W19 should extend that provider with explicitly distinguishable allocation identities and reconcile counts so one allocation is not counted again as a separate copied task. Keep generic queue assignment disabled unless `AssignableTaskProvider` can delegate the complete canonical version, eligibility and scheduling command; the current interface accepts only actor, record ID and assignee.

**Personal calendar has an existing authenticated feed.** `app/Http/Controllers/MyCalendarController.php::events` projects the current user's shifts, medication rounds, approved leave and Control Room tasks into `resources/js/pages/my-calendar.tsx`. It currently has no IT task/allocation source. Add a scoped projection from canonical allocations, with stable allocation ID, actual interval and backlink. Do not create payroll `Shift`, `ShiftTask` or `Timesheet` records to make IT work appear here.

**Site calendars already support source-backed appointments.** `app/Services/Sites/Calendar/SiteCalendarAggregator.php`, `CalendarItem.php`, `CalendarSources.php` and `Contracts/CalendarObligationProvider.php` project dated source records without writing calendar copies. `app/Models/SiteCalendarEvent.php` separately represents manual events with a start/end, owner and attendee IDs. Attendees share the event interval; they do not supply per-person work status or separately editable work blocks. `SiteCalendarService::hasConflict` checks overlapping events for a Site, not a technician across Sites, so it is insufficient as the dispatch conflict rule.

There is a material authorization boundary before adding an IT calendar provider: the current obligation contract receives Site IDs and range, not a viewer. `app/Http/Controllers/Sites/SiteCalendarController.php` also uses the aggregator for per-user ICS and token-authenticated house resource feeds. Site/calendar access does not grant IT internal-work access. Extend the projection boundary with an explicit viewer/audience, or restrict a separate agreed-visit projection to deliberately permitted fields. A raw IT provider must never expose private ticket titles, work notes, effort or staffing details through all-Site feeds. `HrCalendarEvent`/`HrCalendarAggregator` have their own HR audience and invitation lifecycle; HR attendee RSVP is not an IT allocation status.

**Availability records exist, but current routing checks are not a future booking check.** `app/Domain/It/ItStaffDirectory.php` supplies approved accounts with effective IT permission; `agentsForTicket` additionally uses `canWork`. It does not itself require employment or check leave. `app/Domain/It/Services/ItTicketRoutingEligibility.php` adds current employment, sensitivity, explicit assignable Site scope and current leave checks. W08 task assignment must reconcile that difference; W19 must use the stricter assignment boundary and additionally evaluate the proposed entire interval. Canonical inputs are `StaffAvailability` weekly slots, `HrEmployeeProfile` employment dates, approved `HrLeaveRequest` intervals and existing committed work. `app/Services/Eligibility/Rules/AvailabilityRule.php` already handles employment, weekly availability and leave but takes a `Shift`; extract/share a neutral interval reader instead of fabricating a Shift. Its missing-availability warning/override behavior is a rostering rule, not an approved IT policy.

`app/Services/ShiftConflictService.php::findBlockingStaffConflicts` already accepts user and time interval and uses strict interval overlap. It returns roster/client context: dispatch must reduce that to permitted availability evidence, not reuse its detailed HR/client-facing error text. Its default tight-turnaround buffer must not become an implicit IT travel policy. `CalendarSyncBusyBlock` represents pulled **Site resource** calendars, not proven personal technician free/busy. No provider availability, freshness or credentials were checked in this map. `WorkforceAvailabilityCoverageService::syncApprovedLeave/syncOffboarding` durably reconciles absence with roster replacement actions; use those source lifecycle seams for an IT reconciliation adapter, without creating fake roster replacement requests.

## Extension contract and integration order

1. Finish W08 task/approval concurrency, required-work blockers and personal-work provider; apply W09 settled, reopened and merged-ticket rules. Use the same canonical task and access services. `ItWorkspaceRedirectController::work` currently redirects `/it/work` to the existing tickets/My work view; this is not a completed scheduling workspace.
2. Add the missing allocation relationship to canonical IT work: stable ticket/task link, one assigned resource, one start/end interval, explicit work state and version per allocation. Many such rows represent several technicians or several blocks for one technician. Preserve task due dates and one accountable ticket owner. One allocation owns each interval; calendar and personal-work rows are read projections of that identity. Reschedule changes that same record; removal cancels it with history rather than deleting evidence. Final schema naming belongs to the implementation slice, not this map.
3. Introduce a shared interval availability verdict using current canonical people, Site eligibility, employment, leave, roster commitments and active IT allocations. Validate all resources inside the booking command. Lock/version the ticket and allocation and serialize competing bookings for a person across different tickets in a stable lock order; locking only the parent ticket cannot prevent cross-ticket double booking. Changes to leave/employment and roster bookings must participate in compatible coordination or explicit post-change conflict reconciliation; a preflight query alone does not prove absence of races. Keep source failure/unmeasured availability distinct from a free slot.
4. Add actor-bound idempotent create/change/cancel commands, expected versions, exact acknowledgement/recovery and atomic event/audit intent. Preserve the proposed interval and resource on stale conflict; review current availability/version explicitly before reapplying. Reassignment reconciles both old and new people's projections. Booking completion must not silently complete a required task or approval. W16 maintenance-window constraints feed this same command rather than creating a second calendar.
5. Extend the existing task, personal-calendar and permitted team/Site calendar readers from those allocations. Use a stable source ID for refresh, reschedule and cancellation. Apply `ItWorkAccessService::applyWorkScope` before internal rows/counts and current direct-object checks on every linked action; participant-only ticket access is insufficient for effort/dispatch detail. Requesters receive agreed visit/update information only. Recheck ICS/export audiences separately, and keep provider push or real notifications outside unapproved local verification.
6. Implement W19 effort/timer and handover against these same ticket/task identities. Planned intervals are not actual effort or payroll time. Timer sessions need persisted exact operations, overlap protection and auditable corrections. Handover retains next commitment, receiving person and acknowledgement history; cover does not silently change employment/Site assignments. W17 effort/capacity figures must reconcile the actual scoped source records and label missing coverage.

Unresolved operational rules remain explicit: missing availability treatment, permitted overlap overrides and reasons, buffers, cancellation/cover consequences and external calendar publication. This map chooses none of them and infers no credentials or real provider coverage.
