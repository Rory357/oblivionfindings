## Implemented local behavior

- Canonical `AppSetting` records `settings.sso.microsoft`, `settings.sso.google` and `settings.sso.provisioning` resolve saved configuration ahead of deployed defaults. Provider secrets are encrypted with Laravel Crypt and excluded from every browser DTO. Blank/keep preserves the current secret; replacing or confirmed removal is deliberate and audited without values. A removed secret cannot fall back to the deployment value.
- Current `settings.access.manage` and approved-account checks are repeated under the governing locks. Configuration has an expected version; stale writes return409. Configuration changes and required audit rows commit together. Invalid domains, callback origins, Microsoft directory IDs, client/secret pairs and unsupported provisioning controls are rejected. Administrator approval and canonical Support worker / Next of kin defaults remain governed.
- Fresh stateful Socialite drivers consume the current saved sign-in settings without globally changing mailbox/calendar drivers. OAuth state, provider, account surface, attempt age, current authenticated linking actor and configuration fingerprint are checked. Google requires a verified email and an authoritative Workspace `hd` claim for staff. Approved accounts require their canonical provider subject; matching email alone cannot take over an approved account. Existing MFA challenge is retained.
- Explicit portal linking uses the existing authenticated `/settings/profile` page and canonical identities. Pending portal users retain their subject through later approval. Profile linked flags now reflect actual canonical identities and provider links use the correct staff/portal route. Public login pages receive availability booleans only and render native available-provider links and callback errors.
- Root hardened `IdentityDisconnectController` with the same mapping → User → Identity locks, required atomic audit and successful-commit session cleanup. Explicit linking also binds to current identity IDs and the latest actor/provider `identity.disconnected` audit ID. Thus an already-running callback cannot reverse a disconnect, including disconnecting a provider that had no identity yet.
- Canonical group mapping CRUD is retained. Starting/changing an automatic role grant requires acknowledgement and a reason. Duplicate provider/group creation is rejected under the lock; edits/removal use a fingerprint of current editable intent and return409 after another editor changes it. Numeric role IDs are cast consistently in response and refresh. Mapping create/change/removal audits are atomic. `/settings/sso-groups` redirects to `/settings/sso?view=groups`; its JSON read supports current-rule recovery.
- Microsoft group reads validate complete pagination and trusted Graph continuation URLs. Failed, malformed or truncated evidence cannot become an empty membership set or remove roles. Only authoritative empty membership activates configured removal. Another matching group retaining the same role is respected. Current identity and actor access are rechecked before publishing directory results or synchronizing roles. No application caller currently schedules `syncUserRoles`; the UI states automatic directory synchronization is not enabled and Google group synchronization is not integrated. No automatic provider calls were added.
- UI saves require a confirmed typed response.422 keeps nonsensitive fields; secrets clear after attempts.401/419 and403 conceal the entire settings workspace and require a normal authorized reload. Unknown/malformed/failed saves freeze editing until explicit current-version review. Cancellation aborts only the browser wait and never claims server rollback. Group editor/review and removal use the approved WizardShell; role changes and uncertain outcomes are explicit. No browser storage holds credentials or sensitive drafts.

## Empty mapping concurrency correction

The old mapping-range `SELECT FOR UPDATE` was not a mutex when the mapping table was empty. MySQL permits overlapping gap locks; see the [MySQL locking reference](https://dev.mysql.com/doc/refman/8.0/en/innodb-locking.html). `SsoGroupMappingLockService` now first acquires an exclusive record lock by a unique-key no-op upsert of `internal.sso.publication_mutex` in the existing `app_settings` table, then preserves the existing mapping → User → Role order. The existing sentinel value and timestamps are untouched. This key contains no provider configuration or credentials; creation is internal coordination. Transaction commit/rollback releases the lock.

Standalone proof: `tests/Concurrency/It/SsoPublicationConcurrencyTest.php` and `tests/Support/It/sso-publication-concurrency-worker.php`, run **alone** through the isolated wrapper. With zero group mappings and no sentinel, a second real connection cannot acquire the publication lock while the first holds it. After commit it observes the disabled provider and denies admission. After rollback it can proceed and the unchanged sentinel data survives. No provider HTTP is allowed; the worker only joins the parent's random dedicated schema and cannot migrate/drop any database.
