# W08 current task and approval gap map

Source inspection, 9 September 2026. **W08 is incomplete.** This is a bounded dependency map against W08, E06/E07 and backlog B06 in the implementation plan, not a repeat audit. Runtime/frontend/schema sources stayed unchanged during the W07 build/browser freeze. No tests were rerun. “Implemented” below means the behavior exists in the inspected source; prior recorded test evidence is identified separately and does not establish full W08 verification.

## Implemented foundation to preserve

- `app/Models/ItWorkTask.php` and `app/Domain/It/Services/ItWorkTaskService.php` provide canonical ticket tasks, required/optional and evidence flags, assignment, due date, ordering, dependency links, completion and reasoned reopening. Commands lock the ticket before its task, reauthorize `canWork`, reject another ticket's task, and prohibit changes to merged/settled tickets. Dependencies must belong to the same ticket and cannot create a cycle. Completion rejects unfinished dependencies, cancelled tasks and missing required evidence. Cancelling a required task is rejected; an optional cancellation needs a reason. Changed state, completion and reopening write ticket events and `AuditLogger::logOrFail` inside the transaction.
- `Store/Update/Complete/ReopenItWorkTaskRequest` and `ItWorkTaskController` validate their current inputs and conceal inaccessible parents before mutation. `ItTicketContextPresenter::presentTasks` returns task details only through current `canWork`; `ItTicketActivityPresenter` keeps task activity outside the requester event audience. `tickets/show.tsx` already disables task mutation controls for settled or merged work. Preserve those boundaries in list, personal-work and new recovery adapters.
- `ItTicketApprovalService`, `ItTicketApprovalPolicy`, `RequestApprovalRequest` and `DecideApprovalRequest` implement a ticket-first locked request/decision lifecycle. Only one pending/approved request is admitted. A pending decision can be approved or rejected once; the requesting actor cannot decide it, and rejection requires a reason. Current scoped `it.manage` is the actual decision permission; there is no separately established manager-approval permission. Canonical approval rows and events remain the decision source.
- `ItWorkTransitionService::guardSettlement` already blocks resolution/fulfilment/completion/closure until required approval is approved and all required tasks are completed. Optional unfinished tasks do not block settlement. The task UI shows progress, dependencies, completion evidence, assignee/team and dates; the approval UI shows the current verdict and request/decision affordances. These are substantial existing features, not placeholders to replace wholesale.

## Confirmed remaining gaps

1. **Task concurrency and command recovery.** Task requests/services have no submitted expected-version check or durable create UUID. Ticket/task row locks serialize writes but permit a later stale editor to overwrite earlier fields/dependencies/order. A repeated create can create another task. The current full-form PATCH also resends unchanged fields. Approval terminal checks prevent contradictory second decisions, but there is no exact lost-acknowledgement receipt/recovery or original browser actor binding for these task/approval commands. Reuse W02/W06/W07 command and recovery patterns in the canonical services; do not make a second task system.

2. **Assignment eligibility differs from W03.** `ItWorkTaskService::guardAssignment` uses `ItStaffDirectory::agentsForTicket`: approved account, effective IT permission and `canWork`. That directory does not require an active employment profile or check leave. `ItTicketRoutingEligibility` additionally verifies employment, current leave, sensitivity and explicit assignable Site scope. Task assignment can therefore accept a choice the routing command would reject. Reuse the stricter assignment predicate for new/reassigned work while leaving historical assignments visible as historical; confirm team eligibility through canonical Site/routing rules too. Revalidate inside the lock rather than trusting old picker options.

3. **Dependency lifecycle is completion-only.** `complete` checks dependencies, but `update(status=in_progress)` does not; a prerequisite does not presently stop work starting. There is no approval-to-task prerequisite contract. Cancelling/replacing a prerequisite or reopening it after a dependent completed has no explicit downstream consequence. The task editor excludes cancelled tasks from dependency options even if one is still selected in its draft, so a blocked retained link can become invisible to remove/review. Define and persist the governed blocker/repair behavior, without silently completing dependencies or erasing history.

4. **Reopen loses prior completion evidence.** `reopen` clears `evidence`, `completion_note`, completed actor and timestamp. Its event records a reason; the completion event/audit stores an evidence count, not the prior evidence/note snapshot. There is no completion-history relation in the inspected model/service. Preserve a governed prior completion record before clearing current completion state; count-only audit cannot reconstruct the evidence being invalidated. Keep sensitive evidence out of public event payloads.

5. **Ordering exists only behind the UI.** The backend accepts/persists `sort_order` and the task relation orders by it. `ticket-work-tasks.tsx` declares the property but provides no reorder control or order payload. Add an accessible ordered-list action with a collection/version conflict contract; do not rely on unrestricted independent numeric updates for concurrent reorder.

6. **Approval lifetime, eligible cover and pending owner are absent.** `ItTicketApproval` has only pending/approved/rejected states; `approver_id` is populated at decision time. There is no named pending approver, cover assignment, expiry, reminder state or cancellation transition. The controller broadcasts a request to other scoped agents. Neither `guardActor` nor request/decision policy excludes merged/settled work. Extend the existing approval record/service with an explicit eligible assignment and lifetime, preserving the requesting-actor self-decision prohibition, current Site checks and immutable completed verdicts. Current `config/it.php` supplies category flags only; expiry/reminder cadence and cover-selection rules are configuration/policy work, not values to infer from the absence of records.

7. **Approval feedback can claim a rejected operation succeeded.** `ticket-approval-controls.tsx` unconditionally closes and shows success from Inertia `onSuccess`. Controller duplicate/decided business rejection instead returns a successful redirect with `flash.error`, so that branch loses the entered reason and emits a false success. Task dialogs inspect `flash.error`, but still accept an absent success acknowledgement and lack unknown-outcome recovery. Approval notification delivery also occurs through `ItEmailDeliveryService::send` after the canonical transaction; a delivery exception may follow a committed approval. Extend the existing transactional `prepare`/post-commit dispatch seam, returning a proven command result separately from delivery failure.

8. **Dialog lifecycle/design remains partial.** Task add/edit uses a large plain `Dialog` despite the entity-wizard rule in protected `DESIGN.md` and `POPUP_STYLE_GUIDE.md`. There is no review/success pane, dirty-discard confirmation or recoverable native navigation state. Task/approval close handlers clear entered work; no exact retry/cancel-wait/session-expiry/current-access recovery is present. Task field errors exist, but business failures use toast-only feedback; approval errors are inline only for ordinary validation. Use approved `WizardShell` for task add/edit and approved simple dialogs for bounded decisions, with real acknowledgement, focus to errors, retained proposals and current-access concealment. No mobile-specific redesign is required under the user's desktop-web instruction.

9. **Catalogue, personal-work and corrective-link integration are incomplete.** `ItCatalogSubmissionService` marks the canonical ticket `requires_approval`; it does not instantiate linked task prerequisites or unlock them on a decision. Coordinate this W08 contract with W15 catalogue/template completion. `TaskAggregator::defaultProviders` has no IT task or pending-approval provider, so `/tasks` and My Day cannot show this work. The approval summary shows who requested approval, not a responsible pending approver. Settlement rejects with a generic approval/task message; it does not return the incomplete task IDs and direct corrective destinations required by W08. Extend existing providers/presenters and the canonical settlement verdict, preserving `canWork` for private operational details.

## Dependency-ready implementation slices

1. **Task command foundation:** preserve the service/record/controller, unify assignment eligibility, add expected versions and actor-bound create/recovery, typed definitive/unknown outcomes and atomic history. Focused tests: stale field/order update, identical create race, current Site/employment/leave loss, audit rollback and terminal ticket races. Coordinate record/schema changes with the root's guarded migration/build process.
2. **Task lifecycle and UI:** add explicit prerequisite/reopen/cancel consequences and immutable completion history; finish ordering, approved add/edit wizard, completion/reopen dialogs and recovery. Verify a required dependent cannot start/complete prematurely, historical evidence survives reopen, an optional dependency cancellation has a usable repair path, and two editors retain/review proposals correctly.
3. **Approval assignment and lifetime:** extend canonical approval rows, eligibility/cover, cancellation/expiry/reminders, exact decision recovery and transactional notification intent. Reauthorize each direct decision and recipient at execution. A known business rejection preserves the reason; a committed decision plus delivery failure remains a committed decision. Cover/re-request must not mutate a prior verdict or permit self-approval.
4. **Cross-surface gate:** link approval to the correct catalogue/task prerequisites; expose pending owner and actionable blockers; add IT providers to the existing personal task feed. Test counts/detail/lookup/My Day/export and revocation parity through `TaskProviderAuthorization`, then run E07 from request through eligible approval, required evidence and permitted resolution. Finish desktop/keyboard/error-recovery browser evidence on the correct built checkout before marking W08 Verified. W19's later resource blocks reuse this task foundation; they are not part of this read-only mapping slice.
