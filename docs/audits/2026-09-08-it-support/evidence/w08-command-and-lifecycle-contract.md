# W08 dependency-ready command and lifecycle contract

Prepared 9 September 2026 against `w08-current-gap-map.md`, W08 and E06/E07. This is an implementable proposal, not implemented/verified behavior. No runtime, migration or configuration changed and no tests ran. W07 storage integration remains the current implementation priority; W08 runtime starts after the root's dependency release.

## Next vertical slice: canonical task commands

Extend `ItWorkTaskService`, its existing requests/controller and current work-panel component together. Use the existing ticket aggregate version, `ItTicketVersionService`, `ItTicketCommandReceipt` and W06 recovery patterns. Do not create a second task store, task-specific draft inventory or a second notification mechanism.

1. Every browser create/update/complete/reopen/reorder command carries original `actor_user_id`, `request_uuid` and `expected_version` (the ticket's displayed `lock_version`). Apply an allowlisted patch; never mass-assign transport fields through the current `Arr::except` calls. Require original actor and exact parent/task binding before validating or revealing private target details.
2. Lock the ticket, then current participating User rows in ascending ID order, then receipt and task/dependency rows in ascending ID order. Refresh the actor's approval/permissions inside the transaction. Keep current `canWork`, open/unmerged ticket and exact nested-task checks; missing/inaccessible objects return 404, lost current capability 403, business validation 422. Current `lockedTicket()` trusts a previously loaded actor and throws a generic domain error for denial; replace that narrow seam.
3. One actual task mutation advances the ticket aggregate version, including create, dependency changes, completion, reopening and order changes. Current task mutations never advance it. Version checking must cover **all** those writers in the first slice, otherwise later task/settlement proposals still miss collisions. An unchanged patch is an explicit no-op without duplicate event/audit; do not infer no-op success from a redirect.
4. Extend existing receipt operations with task create/update/complete/reopen/reorder. Store only original ticket ID, task ID/ordered ID references, command fingerprint, committed ticket version and safe result flags. Existing `result_metadata` can hold these opaque IDs; no new task table/receipt inventory is needed. No title, description, evidence, completion note or reason enters the receipt. Fingerprint operation, parent/task, original version and normalized exact payload; sort dependency ID sets but preserve reorder sequence. Recovery includes the operation in its route/lookup so a reused UUID across operation namespaces cannot be ambiguous.
5. Proposed exact response: `{status:'committed',data:{id,viewer_user_id,request_uuid,operation,task_id,lock_version,changed,replayed}}`, with nullable `task_id` only for reorder. A replay uses its original committed version, not today's version. Recovery/ACK is `no-store, private`; before returning it, reauthorize current record/task visibility. Fresh current-task review is separate from proving the old commit. A receipt for a missing/merged target must not become a duplicate create.
6. Add explicit same-actor command cancellation tombstones for a lost create/update/completion acknowledgement whose RAM body is gone. Cancellation serialized under the same ticket/User/receipt locks returns either the existing committed result or a permanent cancelled result; it cannot cancel a committed task. GET 404 is never proof that an earlier request cannot still finish. Reuse the W07 command cancellation invariants; no automatic timeout cancellation.
7. New/reassigned technician work uses `ItTicketRoutingEligibility::agent()` (current employment, approved leave, sensitivity and explicit assignable Site scope), rechecked after locks. Historical unchanged assignment remains visible and does not block an unrelated description edit merely because its person is now absent. `ItTeam` has **no Site field**: do not invent `team.site_ids` or infer authority from its name. Keep its active-team rule; if team membership or queue selection must constrain task assignees, expose that as an explicit additional contract, not an assumed existing Site policy.
8. Reorder accepts the complete current task ID sequence exactly once each, plus expected ticket version. Reject missing/extra/foreign/duplicate IDs. Apply stable server sort values in one ticket-locked transaction, with one event/audit and one version advance. A cancelled task remains visible in the ordered register/dependency review; a selected invalid link must not silently disappear from a form.

Frontend scope of this slice: approved `WizardShell` for task create/edit with metadata/review/confirmed panes; bounded completion/reopen dialogs remain simple. Retain exact proposal/base version through validation, unknown outcome, session expiry, close and native navigation. Adopt current access/version only after explicit review and require another explicit apply. Purge concealed private fields on access/actor loss. No persisted draft retention is enabled by this work; reuse the existing effective flag and authorized RAM recovery.

Task form recovery needs an explicit task context as well as actor/ticket/purpose. Two edit forms for different tasks on one ticket must not consume each other's `ticket_edit` buffers. Extend the shared typed recovery contract with the canonical task ID and operation-specific field allowlist; its fresh read-only candidate proof must authorize that nested task before releasing text. If persisted task drafts are enabled later, extend the existing draft slot identity with that task context under a reviewed migration rather than overloading intake `request_uuid` or creating another draft table. Keep this distinction visible in the first-slice RAM tests.

## Task blockers and completion evidence

Add one canonical blocker evaluator used by start, complete, settlement, work-panel DTO and personal task projection. It returns safe codes and exact authorized task/approval corrective links. Do not write state from a GET. Non-workers receive neither private titles/evidence nor operational blocker lists.

- Starting **or** completing a dependent requires all prerequisite tasks to have a currently valid completion. This closes the existing start-before-dependency gap. Preserve cycle/same-ticket checks under the ticket lock.
- Recommended consequence for cancelling/replacing/reopening prerequisites: preserve all original completion evidence and expose the affected descendants as requiring review, with start/complete/settlement blocked as applicable. Never silently erase links, turn cancelled prerequisites into completed prerequisites, or retroactively claim a historical completion used a later approval. Require an explicit reasoned dependency repair or dependent reopen/recompletion. Return the impacted IDs in a preview before a command changes a prerequisite. This is a task lifecycle recommendation for the root's implementation review; it is not an automatic cascade policy already present in the repository.
- Add append-only `ItWorkTaskCompletion` rows bound to the existing task: sequence, actual completed actor/time, completion note/evidence snapshot, prerequisite completion IDs and approval ID/version that actually satisfied the gate. Current task evidence fields can remain the compatibility/current projection. A new completion writes its immutable record atomically; reopening preserves it before clearing current completion fields. Reopening an older completed task with no history first captures only its extant evidence/known actor/time as a labelled legacy snapshot; unknown historical values remain unknown. No count-only audit or fabricated backfill substitutes for the snapshot.
- Task evidence remains private under current per-record work access. Structured file references, if introduced, point to existing canonical `ItAttachment` records and their W07 authorization/scan gates; this slice does not create an upload inventory. Existing bounded text/link evidence stays supported.
- Add a task-to-approval prerequisite link to the canonical approval record, not merely a category boolean. An approved catalogue request unlocks only tasks bound to the appropriate request/approval generation. Re-request/rejection/expiry cannot make a different historical approved row satisfy that link. W15 creates those links through the same service when its templates are implemented.

Settlement should return a typed `required_work_incomplete`/`approval_required` verdict with authorized corrective URLs (task anchor/work section/approval panel) rather than only today's generic `DomainException`. The same current blocker evaluator must drive that verdict and displayed readiness; optional unrelated tasks remain nonblocking.

## Approval lifetime, cover and evidence: additive requirements

Preserve `ItTicketApproval` and `ItTicketApprovalService`. `approver_id` remains **the actual decider** and must not be reused as a pending owner. Existing `it.manage` plus `canWork` and the requester self-decision prohibition remain the current capability boundary; no new role is silently granted. Extend typed original-actor/receipt/version/recovery and transactional outbox behavior to request/decision/cancel/reassign with the same task-command guarantees. Reject new request/decision mutations on settled/merged tickets; permit recovery of an already committed historical decision only after current canonical access checks.

Proposed additive record data:

- `assigned_approver_user_id`; explicit eligible `cover_user_id` and optional cover start/end bounds; assignment actor/time/reason in append-only events. These indicate responsibility, never grant ticket access. Current eligibility/self-decision must be checked again when cover acts. A recommended new-request contract is an explicitly selected eligible primary/cover rather than a fabricated automatic owner; root must settle decision authority for unassigned legacy requests before enforcing it.
- Nullable `expires_at` as an absolute instant for the **pending request**, plus `expired_at`, `cancelled_at`, `cancelled_by_user_id`, cancellation reason and superseded-request linkage. Add terminal `expired`/`cancelled` states. Do not infer an expiry for historical pending rows. Do not expire an already approved verdict unless a separately specified approval-validity policy requires it.
- Separate immutable request reason from decision reason. Current `reason` is overwritten/falls back during decision, so legacy content cannot always be confidently labelled as a distinct decision reason. Preserve it as legacy evidence instead of inventing attribution.
- Reminder cursor/sequence, last/next reminder time and a captured configured policy revision. Under the approval lock, advance the cursor and create existing `ItEmailDeliveryService::prepare` intents in the same transaction. Recovery retries the same outbox identity; it does not generate another reminder for the same sequence. Register bounded scheduling/freshness via `ItAutomationScheduleCatalog`/`ItAutomationRunRecorder` once an operational cadence is set.

Expiry reads must be truthful even when the scheduler is stopped: pending plus a known elapsed `expires_at` projects an effective expired blocker at the request's shared evaluation instant. A due decision is rejected; the bounded expiry command persists the terminal transition/event once. GETs remain nonmutating. Test exact deadline equality and before/after, UTC conversion, NZ DST and stopped-watchdog recovery.

**Operational decisions still required; do not silently default them:** pending approval duration and business/calendar clock; reminder cadence/cap/escalation recipients; who may nominate/change pending primary/cover and decide unassigned legacy requests; whether cover is manually activated or automatically substitutes during approved absence; approved-verdict validity/reapproval after materially changed scope. Configuration defaults remain unset/disabled for automatic expiry/reminders/cover where these choices are absent. Explicit per-request dates/assignments can be implemented as inputs, but they must not manufacture organisation policy. These choices do not block the task command, immutable evidence, exact approval recovery or false-success fixes.

## Existing personal work integration

Add providers to `TaskAggregator::defaultProviders`; use `TaskProviderAuthorization::siteScoped` with the owning IT module's canonical work SQL scope before projection/counts. `ItWorkTaskPolicy::view` currently permits ticket participants through `canView`, while the actual work-panel presenter deliberately requires `canWork`; new private task feeds must preserve the stricter current projection and must not use the broader policy alone. Preserve legitimate canonical assigned/team scope exceptions and the explicit organisation-wide grant without a new tenant/global bypass. Counts, direct lookup, My Day, export and detail must all use the same authorized task/approval rows and effective pending owner/blocker state.
