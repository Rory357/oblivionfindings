## Effective options contract for frontend integration

Configuration: `it.drafts.enabled` / `IT_DRAFTS_ENABLED` defaults false; `it.drafts.retention_days` / `IT_DRAFT_RETENTION_DAYS` and `it.drafts.terminal_retention_days` / `IT_DRAFT_TERMINAL_RETENTION_DAYS` default null. `ItTicketDraftService::enabled()` requires the flag plus both positive integer durations; raw flag alone is insufficient. No browser environment values or live provider configuration were changed.

`BuildsItOptions::draftRecoveryOptions()` now exposes the additive page option `draftRecovery: {enabled: boolean}` using that effective service method on the hub and canonical ticket page/JSON drawer. Focused tests verify disabled, missing-retention and configured states without creating a draft slot. Current actor ID comes from authenticated page context. Persistence is available only when both the option and purpose/canonical permissions allow it; ordinary local memory/navigation guards still apply when persistent recovery is disabled. No duration should be shown as configured before a choice is recorded. Existing canonical attachment limits are five per submission, 10MB each, with `ItAttachment::ALLOWED_MIMES`; a resolution/properties form has no attachment control and does not accept staged files.

## HTTP and client state

- Every endpoint is under existing authenticated `it.request|it.view` access and also requires `actor_user_id` matching the actual current session. A stale page cannot upload its prior actor's private buffer after another account signs in. Current account, permission, canonical ticket and retained selected-reference scope are checked by the service on every action, before decryption.
- `POST /it/drafts/context` accepts `purpose` and exactly its ticket ID or intake request UUID. Returns `{draft}` metadata; repeated context checks never hydrate or overwrite content.
- `GET /it/drafts/{draftUuid}?actor_user_id=...` returns metadata. `POST /it/drafts/{draftUuid}/resume` returns `{draft,payload:{fields,step_index}}` only after explicit user choice. Do not keep payload in Inertia remembered state, URLs, local/session storage, logs or AI context.
- `PATCH /it/drafts/{draftUuid}` accepts `expected_revision`, `fields`, `step_index` (0–20), optional `base_ticket_version`. Fields are partial, purpose-specific and allowlisted; unknown fields, secrets/binary fields, >64KB aggregate and inaccessible selected references are refused. Intake has no base ticket version. File bytes are never embedded in this payload; use the dedicated canonical staging endpoints below.
- `DELETE /it/drafts/{draftUuid}` accepts expected revision, scrubs content and leaves a terminal generation. Same discard replay returns the same revision. `POST /it/drafts/{draftUuid}/start-new` compares the terminal UUID/revision, rotates a server-issued UUID and advances revision. A lost start-new acknowledgement is recovered through metadata-only context lookup, never by issuing blind save/create. An old UUID cannot read, write, discard or consume the new generation.
- Normal success is `{draft}`. Metadata contains `draft_uuid`, `purpose`, `context_key`, `audience`, `ticket_id`, `request_uuid`, `revision`, `state`, `has_content`, `saved_at`, `expires_at`, `base_ticket_version`, `current_ticket_version`, `files:{ready,pending,cleanup_pending}`, `capabilities:{read,save,submit,discard,start_new}` and nullable `blocker`. State is `active|consumed|discarded|expired`. `submit` describes workflow/access eligibility, not field completeness or permission to bypass canonical business validation. `has_content` includes acknowledged text or reserved/ready files. A file revision acknowledgement alone never proves the current unsent text buffer was saved.
- `draft_conflict`409 includes only current metadata. Identical last-revision/payload save retry returns the saved revision; changed stale input requires explicit review/reapply. Separate current ticket versions still govern actual mutation. `draft_terminal`409 never returns expired/consumed/discarded text. Same actor authorized settled/merged work may recover/save its text while submission stays blocked.
- Canonical committed intake receipts suppress draft editing/submission and provide the existing actor-authorized receipt URL. Generic receipt404 is still not proof a ticket was never committed. Existing W02 uncertain-command recovery takes precedence over editable draft hydration.
- 401/419 is `session_expired`, 403 is `access_unavailable` (conceal/purge), missing/foreign/owned-inaccessible UUID404 is `draft_unavailable` with identical generic text. Never reinterpret an internal draft denial as public. All endpoint responses, validation, routing, auth and unexpected failures are forced JSON with `Cache-Control: no-store, private`; no old-input redirects or private debug/SQL exception text.

## Domain and transaction boundary

Purposes: `requester_intake` (public), `technician_intake` (internal), `public_reply`, `internal_note`, `ticket_edit` (internal), `public_resolution`. Intake uses the existing W02 request UUID as context; existing-ticket purposes use the canonical ticket ID. Public/internal records and buffers remain independent. Technician purpose requires current `it.manage` plus canonical `canWork` for a ticket; public purpose uses current canonical visibility.

Lock order: intake current User → command receipt → draft → attachment; existing ticket → fresh current User → draft → attachment. Save never initializes a row. Scope bindings are checked before changing or clearing fields; clearing a selected private reference cannot erase its prior access requirement. A valid explicit replacement may replace the old binding after both are authorized.

Content is encrypted using the repository encrypted-array cast and hidden from model serialization; equality uses HMAC, not persisted text. Audit save/resume/terminal records contain actor, purpose, opaque draft identity/revision/state only. Persisted revision and audit write share a transaction. `consume` requires an enclosing canonical business transaction; no public consume endpoint exists.

## Canonical commit acknowledgement

Create, property update and public resolve accept optional **all-or-none** `draft_uuid`, `draft_revision`, `draft_actor_user_id`. The latter must match the current authenticated actor. The expected revision is the exact saved generation being submitted, separately from `expected_version` for an existing ticket. A consumed generation cannot authorize a new business write under a later ticket version. Existing command receipt replay is resolved before repeating consumption; omitted draft fields do not change existing W02 command fingerprints.

`POST /it/tickets` retains its established W02 `{status:'committed',data:{id,reference,request_uuid,replayed,...}}` contract. Draft/file consumption now shares its canonical ticket/receipt transaction. A changed draft reference under the same request UUID is an idempotency conflict. Pending files prevent commit. Failure rolls back ticket, receipt, reparenting and draft scrub together; current ready files remain recoverable. A committed retry returns the original ticket without consuming or copying again.

`PATCH /it/tickets/{id}` and `POST /it/tickets/{id}/resolve`, when requested as JSON, return `{status:'committed',data:{id,lock_version,draft?:{draft_uuid,submitted_revision,revision,state:'consumed'}}}`. `revision` is the terminal revision immediately after the confirmed submitted revision. Clear only the matching local generation/snapshot; a later local edit remains unsaved. JSON business rejection returns422 with `code: ticket_update_blocked|ticket_resolution_blocked` and the actual domain message. Existing version-conflict responses remain authoritative. Legacy Inertia redirects are preserved for callers without the new JSON contract; their `onSuccess` alone is not proof that a private draft was consumed.

Public/internal **comment submission is still W07 integration work**: the current comment service has no typed idempotent commit receipt. The draft backend supports independent reply/note recovery and has a canonical transfer target contract, but the composer must not clear/consume those drafts from an Inertia redirect callback. Resolve now has the explicit JSON acknowledgement above.

## Staged file routes and durable lifecycle

- `POST /it/drafts/{draftUuid}/attachments` is multipart: `actor_user_id`, `expected_revision`, `upload_uuid` (client-created immutable UUID for this exact file), and `attachment` (one actual file). Returns `{draft,attachment:{id,upload_uuid,name,mime,size,state,download_url}}`. Metadata `state` is `reserved|ready|failed`; only `ready` has a download URL. Only requester/technician intake and public/internal reply purposes accept files.
- A new upload reserves a canonical `ItAttachment` row and an opaque private path in one committed transaction before the physical copy. The bounded copy then holds the same current draft/attachment locks; a second revision records confirmed readiness. Normal first upload advances revision twice. Same upload UUID/name/content retry resolves the existing reservation or ready row without another file. Same identity with changed bytes/name gives409 `draft_upload_conflict`. New upload with stale expected revision gives409 `draft_conflict`.
- Storage/ready-commit failure returns503 `draft_upload_unconfirmed`; retain the selected file in memory and retry the exact upload UUID. The reserved row/path stays tracked and is not counted ready. Metadata `files.pending > 0` supplies blocker `draft_files_pending` and disables submit; remove or finish the file before commit. Reload cannot recreate missing local file bytes: resume shows the actual reserved status and offers removal/reselection, never a fabricated saved attachment.
- `DELETE /it/drafts/{draftUuid}/attachments/{attachmentId}` accepts actor and expected revision. Returns `{draft,removed_attachment_id,cleanup:{deleted,failed}}`. Logical removal is versioned and repeated removal is idempotent. If physical deletion fails, `cleanup.failed` and metadata `files.cleanup_pending` expose that fact; the row remains tracked and inaccessible. Active generations keep removed upload-identity tombstones so delayed upload retries cannot recreate a removed file.409 `draft_attachment_removed` requires a deliberately new selection/upload identity.
- Explicit `POST .../resume` now returns `{draft,payload,attachments:[...]}`. Metadata-only context/show/save responses contain counts, **never names or private paths**. The attachment list contains actual rows/states; no persisted filename-only mock stands in for a durable upload.
- Downloads use the existing `/it/attachments/{id}` route. Draft parents require current owner, canonical ticket/selected bindings, exact generation and ready state on every request. Missing/foreign/expired/removed/inaccessible stage URLs return404. After canonical intake commits, the same attachment ID/path belongs to the real ticket and uses its ordinary audience policy. No file is copied and no public storage URL is created.
- Intake transfer is inside the same ticket/receipt commit. The combined staged plus direct-file count cannot exceed the existing five-file cap. Reply/note transfer validates the exact comment ticket and internal/public audience, but its live comment hook remains W07. Resolution/properties purposes reject uploads because those forms currently have no attachment input.
- Discard and explicit start-new invoke generation cleanup after their state transaction and return `draft.cleanup:{deleted,failed}`. Cleanup matches the exact draft parent/generation and never deletes already transferred ticket/comment files. A failed old-generation cleanup cannot reappear as files on the new generation.
- `it.prune-drafts` calls `ItTicketDraftPruner`: effective flag false means no queries/mutations; configured expiry first scrubs text, audits metadata and retains a terminal slot, then attempts exact owned-file cleanup. Pending cleanup is retried on later runs; failed physical removal keeps the locator/attempt count/error category. Expired terminal slots are removed only once their canonical attachment rows are gone. The command returns nonzero when cleanup fails. **No scheduled production prune or retention/ownership policy is enabled by this slice**; root must record the operational choice before enabling persistence.

Nullable canonical attachment extension fields in migration000007: `draft_generation_uuid`, `draft_upload_uuid` (unique), `draft_content_hash`, `draft_storage_state`, `draft_cleanup_attempts`, `draft_cleanup_error_code`. They are hidden from ordinary model serialization. Draft uploads use the existing private disk and canonical `ItAttachmentStorageService::storeReserved`, not a duplicate file store. Scanner/quarantine lifecycle remains W07.
