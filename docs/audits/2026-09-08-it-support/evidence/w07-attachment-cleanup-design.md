# W07 attachment cleanup — bounded design

Read-only source review, 9 September 2026. Implements nothing and runs no PHP/database tests. Scope: W07/E05 file recovery, separate from unanswered scanner/outage/retention policy. The earlier [lifecycle map](w07-remaining-lifecycle-map.md) is revalidated only for these paths.

## Confirmed boundaries

- [ItAttachmentStorageService](../../../../app/Domain/It/Services/ItAttachmentStorageService.php) writes direct uploads, then creates canonical `ItAttachment` rows inside the business transaction. `deleteStored()` ignores `delete=false`; a thrown storage error can also replace the original business exception. After a rollback, the attachment row is gone and a failed physical delete has no durable retry owner.
- The only application callers are the rollback catches in [intake](../../../../app/Domain/It/Services/ItTicketIntakeService.php) and [interaction](../../../../app/Domain/It/Services/ItTicketInteractionService.php). Their same-PDO/transaction-depth checks and fresh-primary receipt reconciliation deliberately retain potentially committed bytes. Preserve these protections: a missing receipt, timeout, dead worker or inaccessible record is not proof of rollback.
- [Draft attachment cleanup](../../../../app/Domain/It/Services/ItTicketDraftAttachmentService.php) already retains exact path/generation rows, `cleanup_pending`, attempts and safe error codes. Its active-generation `removed` tombstone prevents delayed upload resurrection. Transfer moves the same attachment to the canonical ticket/comment. Both cleanup and the [draft pruner](../../../../app/Domain/It/Services/ItTicketDraftPruner.php) currently stop when draft persistence is disabled.
- Focused searches found **no submitted ticket/comment attachment removal route or deletion observer**. Closing/resolving/merging a ticket is not deletion authority. Release-fixture cleanup is test infrastructure, not an application deletion path. Do not introduce record deletion or invent attachment retention to cover this gap.
- No generic whole-app blob cleanup owner was found. [DeviceDocumentLifecycleService](../../../../app/Domain/SecurityDevices/Services/DeviceDocumentLifecycleService.php) demonstrates durable removal states, retry and audit; [MonitoringRetentionDeletionIntent](../../../../app/Domain/Monitoring/Models/MonitoringRetentionDeletionIntent.php) demonstrates immutable intent identity and terminal evidence. Reuse these principles, not their domain records/policies. IT remains on `ItAttachment::DISK = private` and [ServesPrivateAttachments](../../../../app/Http/Controllers/Concerns/ServesPrivateAttachments.php).

## Recommended canonical contract

Extend `ItAttachmentStorageService` with a small **technical storage-intent outbox**, not another attachment inventory. A narrowly named `ItAttachmentStorageIntent` owns one immutable opaque path and operation UUID; `ItAttachment` remains the sole submitted-file metadata/authorization record. Why an outbox: the existing attachment schema requires a ticket/comment/draft morph parent, and its new direct-upload row rolls back with that parent. Reusing `draft_storage_state` for submitted files would couple cleanup to the disabled draft programme and misstate ownership.

Proposed additive intent fields: UUID, fixed private path, content SHA256/size, safe operation kind (`direct_upload`, `authorized_removal`), nullable canonical attachment ID, original actor ID as audit provenance, state (`reserved`, `attached`, `cleanup_pending`, `deleted`, `reconciliation_required`), revision, cleanup attempt count, last/next attempt time, safe error code and completion time. No file name, body, recipient, provider response, new tenancy field or configurable disk. Unique UUID/path; immutable identity; completed tombstones are not immediately removed. A future purge duration is a separate policy, not part of this slice.

Exact service seams:

1. `reserveDirect(UploadedFile, actor, commandIdentity): StorageIntentReference` **commits the intent before writing bytes**. A reservation failure means no physical write. Prefer reservation before the outer business transaction. If an existing adapter is already inside an outer transaction, a reviewed independent connection to the same primary is required for this technical row; it must not insert/update FK-dependent actor/ticket rows held by the caller. A normal nested transaction is not durable. This ordering needs a real transaction test before integration.
2. `storeReserved(reference, file, parent)` locks the intent inside the business transaction, verifies its immutable identity/state, writes only its reserved path, creates the existing attachment, and associates/marks the intent attached in that same transaction. All writers and cleanup workers lock the same intent before storage access. An intent marked for cleanup can never be written again.
3. `requestRollbackCleanup(references, confirmedRollbackEvidence)` persists `cleanup_pending` independently of the rolled-back business transaction, then performs a bounded best-effort pass. Preserve the original exception; return structured cleanup outcomes separately. If the process/database fails before this state transition, the pre-existing reservation remains visible for reconciliation rather than becoming an untracked object.
4. `retryPending(limit): {processed, deleted, failed, reconciliation_required}` locks each exact pending intent, rechecks state/path and canonical attachment ownership, then deletes. False, throw or uncertain existence checks retain the row and increment a safe error code. A confirmed already-missing object completes idempotently. If storage succeeds but DB completion fails, the next retry safely observes absence and records completion. Never complete or erase the intent before physical deletion is confirmed.

An unknown business outcome stays `reconciliation_required`/reserved until a fresh-primary canonical attachment/receipt check proves it attached, or an authorized reconciliation proves cleanup is safe. **Absence alone must not trigger deletion**: an original worker can still commit, and a delayed writer must be fenced by the same intent state/revision. Do not scan `it_attachments/` and delete by age or missing DB rows. Killed-worker reconciliation needs an explicit fenced lifecycle; this design does not claim an orphan expiry policy.

For a future authorized submitted-file removal, the canonical mutation must first mark the existing file unavailable and persist its exact cleanup intent plus required audit in one transaction. The download presenter/controller must deny it immediately; the physical cleanup follows commit. Retain the canonical tombstone/audit on storage failure. That removal entitlement/reason/UI remains a separate reviewed change because no existing submitted-file deletion action was found.

## Dependency-ready slice and verification

The next independent implementation can add the bounded intent model/service foundation and pure path/result contracts, then integrate **proven direct rollback** cleanup once W01 releases the transaction-test slot. It does not require a scanner, a retention duration or a new removal permission. Do not claim complete crash recovery until pre-write reservation and fencing are integrated through intake, typed comments and legacy comments.

Use [ItAutomationScheduleCatalog](../../../../app/Domain/It/Services/ItAutomationScheduleCatalog.php) and [ItAutomationRunRecorder](../../../../app/Domain/It/Services/ItAutomationRunRecorder.php) for one bounded pending-intent retry command and freshness/count evidence, independent of `drafts.enabled`. Choose/record technical retry cadence during implementation; it is not permission to expire evidence. Keep false/partial deletion non-successful and report safe codes/counts rather than storage exception text. Register the existing `it.prune-drafts` command separately before draft activation; expiry continues to require the existing configured policy. The current catalogue has no pruner registration.

Required tests: false/throw delete survives process restart; missing object retries idempotently; audit/DB failure cannot falsely complete; pre-write intent survives outer rollback and connection loss; successful/postcommit-exception ticket/comment attachments remain; unknown receipt is never deletion proof; two workers cannot race late upload/transfer against cleanup; duplicate cleanup intent is idempotent; removed-file copied URLs deny before physical cleanup; recovery still works with drafts disabled; bounded scheduler counts/failed freshness are truthful. Extend [draft cleanup tests](../../../../tests/Feature/It/ItTicketDraftAttachmentTest.php) and existing standalone [IT concurrency fixtures](../../../../tests/Concurrency/It), using unique isolated schema/private storage only. No tests were run for this design.

Scanner verdict/quarantine/download-of-verified-bytes, attached-reply outage semantics, historical evidence retention and actual provider/engine access remain explicit W07/DP07 gates. No migration name is reserved, no schema/helper changed, and no working database/provider/storage mutation occurred. Await root's implementation coordination.
