## Existing behavior worth preserving

`ItServiceIdentityCredentialService` hashes an opaque reusable secret and atomically audits creation/revocation. Delegation intersects current manager and execution-account site/capability authority. `AuthenticateItServiceIdentity` checks current approval/employment, expiry/revocation, optional timestamped HMAC and per-identity rate limit. `ItApiWorkItemService` and `ItApiFieldPolicy` enforce work type, active approved Site, explicit organisation-wide/sensitive authority, linked asset/service scope and field allowlists. `RecordItApiRequest` binds an idempotency key to request hash, persists only minimal successful result IDs, and reprojects replay results using current authority. Transitions call the canonical lifecycle service. None of this calls for another ticket or asset system.

Existing `tests/Feature/It/ItSecureApiTest.php` contains8 cases covering ordinary issuance/one-refresh secret behavior, create/read scope, sequential duplicate/conflict, signature denial, sequential expiry/revocation/rate limit, comment/transition audit, current authority and replay projection. Those are source observations; this review did not rerun them. They do not prove rotation, update/link, parallel revocation, crash recovery or failed-intent replay.

## Confirmed implementation gaps and narrow fixes

1. **No rotation or update/link API lifecycle.** `routes/api-hr.php:30` exposes only create/read/comment/transition. `routes/web.php` exposes only identity create/revoke. `ItServiceIdentity::ABILITIES`, allowed fields, request classes and credential service have no rotation, update or link contracts. Extend those canonical records/services with explicit allowlisted capabilities and current version requirements; do not treat existing create-time asset/service fields as a verified link operation. Device links must resolve through canonical device/source authorization, not an arbitrary supplied ID. Test issue/use/rotate/old-secret denial/revoke, least authority, and read/update/link positive and forged-scope denial.

2. **A lost response after commit can leave an unrecoverable pending API intent.** `RecordItApiRequest::handle` inserts the request row before `$next`, while `ItApiWorkItemService` commits domain work separately, then the middleware stores result and audit. A process loss between domain commit and ledger completion leaves `completed_at` null forever; `existingResponse` always returns409 `idempotency_in_progress`. A completed500 is replayed as the same500 forever. There is no authorized failed-ingress recovery action or attempt metadata. Extend the existing API request record into the governing transaction/command outcome so result binding and domain commit are atomic, with current-scope recovery. Reuse W02 intake/receipt behavior instead of adding a parallel ledger. Preserve uncertainty where commit cannot be established; never advise a new key for unknown work. Test rollback then authorized retry, post-commit lost response, simultaneous same key, changed payload, revoked replay, and exactly one ticket/comment/transition audit result.

3. **API comments bypass lifecycle rules; API creation bypasses the common intake/outbox seam.** `ItApiWorkItemService::addPublicComment` directly inserts a comment/event. Compared with `ItTicketInteractionService::addComment`, it lacks merged/settled-ticket denial, agent first-response stamping and requester-wait resumption. `create` directly constructs/stamps/routes an ItTicket rather than using W02 `ItTicketIntakeService::createCommand`; no ticket-created notification outbox preparation is visible in that adapter. Adapt the canonical commands with service-identity provenance and field policy. Test settled/merged denial, first response and SLA history, waiting-party behavior, event provenance and deferred notification invariants. Do not create a separate API-only lifecycle.

4. **Credential and current-authority checks are not serialized with API publication.** `executionAccount` refreshes identity/current User, but create/comment do not hold that identity/User/evidence lock through commit; revoke uses a different manager→identity sequence. Source permits revocation between authorization and a domain write. The middleware's final404 can conceal the result after the write; it does not undo it. `create` also locks manager then execution User without deterministic ID ordering. Establish the repository's shared authorization/evidence→ordered actors→identity→ticket order, including rotation generation binding and current delegated scope. This is a source-confirmed missing lock boundary; the race has not been reproduced in this review. Prove it with a standalone guarded two-worker test, not sequential mocks alone.

5. **API transitions have no concurrency token and SLA reads use the old cached projection.** `TransitionItApiWorkItemRequest::FIELDS` excludes expected version; the controller omits `ItTransitionInput::expectedVersion`, so the canonical version service intentionally skips comparison. `ItApiWorkItemResource` omits `lock_version` and reads raw `sla_state`/due timestamps instead of the W04 authoritative verdict. Add a safe current version DTO and explicit expected-version mutation contract with actionable409; present W04 verdict only when `sla` is allowed. Test stale callback cannot overwrite current state and paused/unmeasured/breached API evidence agrees with browser/reporting at one instant.

6. **The one-time secret currently travels in the normal Setup/list page response.** `storeIdentity` flashes `it_api_credential`; `index` includes it as `oneTimeApiCredential` beside the identity list. The React component renders it in the list workspace. No explicit history-encryption/clearing or no-store behavior is configured for that result. The next fresh GET hides it, as the existing test proves, but that does not prove history/session-loss secrecy. Use an authorized issue/rotation response confined to a transient approved flow; ordinary list/review responses must exclude the token, including a pending flash. Clear secret state on close/unmount/access loss; handle clipboard rejection without a false Copied message. Test JSON/Inertia list exclusion, back/history handling, revoked access and ambiguous issue/rotation recovery without repeating an unknown issuance.

7. **Operations evidence is a global error count, not actionable ingress health.** `ItServiceManagementSetupController::index` counts every `it_api_requests.response_status >= 400`, while identities are filtered through `canManage`; the aggregate is not scoped to those authorized identities. `last_used_at` is updated before request processing, so it is not last success. The request model has no attempt/error-category/recovery metadata, and no review/replay route exists. Extend existing Operations audit with scoped identity/intent views, real last-success timestamps, safe categories/counts/age and guarded permitted actions. Join the canonical mailbox/delivery/monitoring records when W11–W12 contracts are ready. Do not promote the current global count into a verified health metric or expose raw bodies/credentials.

8. **Recovery ownership and identity editor lifecycle need deliberate completion.** `canManageLoadedIdentity` requires creator/execution identity ownership plus all current delegated sites/exceptional capabilities, including for revoke. A creator that loses scope can no longer list/revoke that credential, and an unrelated current administrator has no canonical recovery path. Preserve normal boundaries and agree an explicit audited recovery capability/path; do not silently broaden ordinary managers. `it-api-identities.tsx` uses a long plain Dialog, can close pending/dirty input, treats any Inertia success redirect as creation success, and offers no unknown-outcome review or rotation. Replace only this flow with approved WizardShell/typed outcome/review patterns already used by Setup/W10, with keyboard and desktop browser acceptance. Lost access must conceal secrets and cached identity details.

## Further verification rather than assumed defects

- Current HMAC binds timestamp, method, path, idempotency key and body; query is not signed. Existing routes have no query-based mutation. Bind canonical query if new update/link semantics introduce meaningful query parameters.
- The rate limiter uses separate `tooManyAttempts` and `hit`; a concurrency/load proof and the deployed shared-cache configuration are still needed. Local array cache is an isolation setting, not production rate-limit evidence.
- Invalid credentials/signature/rate-limit responses happen before the request recorder. Decide bounded nonsecret operational counters/category evidence; do not persist bearer tokens, signatures or arbitrary unauthenticated payloads.
- Legacy tenant columns remain storage compatibility only. No tenant selector, queue, transport or fixture boundary is proposed.
