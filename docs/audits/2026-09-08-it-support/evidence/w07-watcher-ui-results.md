# W07 watcher management UI

Implemented and focused-test verified, 9 September 2026. **Browser verification remains pending Build8.** This slice adds the existing canonical watcher operation to ticket People & feedback and the drawer; it does not change permissions, backend records, migrations, providers or production configuration.

## Contract and implementation

- New `resources/js/hooks/use-ticket-watcher-command.ts` sends `PATCH /it/tickets/{ticket}/watchers/{watcher}` with the original `actor_user_id`, displayed `expected_version` and explicit desired `watching` value. A committed acknowledgement must match actor, ticket, person and desired membership. A changed result must advance exactly one version; a no-op may acknowledge the same or a later current version. No-op copy says no change was needed.
- `resources/js/components/it/ticket-watchers.tsx` reuses approved buttons, select, status badge and a bounded confirmation dialog. Eligible options are exclusively the server's `watcherOptions`. Existing ineligible watchers remain visible with paused-update status and can be removed. Self-watch and managing other people require `can.manageWatchers`; requester-only access receives no new subscription permission. The UI does not infer eligibility from a name, staff role or general Site visibility. Removing a watcher is described as ending that subscription, not as revoking other legitimate notification audiences.
- `pages/it/tickets/show.tsx` replaces the old unversioned self-watch transport and passive watcher chips with the shared command/panel. Header self-watch opens the same confirmation. `components/it/ticket-drawer.tsx` presents the same People & feedback controls; its canonical payload type in `hooks/use-it-ticket-peek.ts` adds only the watcher capability/options/receipt-state fields.
- Unknown submissions retain exact actor/ticket/person/version/desired-state metadata in bounded application RAM. No names, content or private browser storage are used; no background send or automatic retry occurs. Same-document remount requires explicit recovery, and a pending-intent unload warning covers reload/tab close. Session expiry conceals watcher details until a fresh matching-actor review; confirmed denial purges the affected pending context. Drawer loading does not falsely revoke an as-yet-unconfirmed context.
- Retry resends the exact original command. Current-state GET is read-only and validates actor, ticket, capability, version and watcher/option shapes. Adoption never submits. An unchanged-version GET showing the opposite membership cannot prove an earlier request finished, so neither adoption nor “Keep current watchers” discards that uncertain original. Cancel wait aborts the local wait and ignores late callbacks; it never claims to cancel the server command. Business rejection and malformed acknowledgements produce no success.
- A command acknowledgement contains one membership result, not the whole register. Fresh equal-version page props replace that incomplete local projection. An explicit GET review temporarily supplies a full projection without silently adopting its version for the pending command. This preserves concurrent watchers and current eligibility flags.
- New `ticket-watcher-activity.ts` provides the shared event wording. Only the watcher cases in `ticket-thread.tsx` and `it-overview.tsx` changed: explicit `self:false` says who was added/removed; self and historic events retain started/stopped-watching wording. No generic raw payload rendering was introduced.

## Delivery refresh follow-up requested by root

`hooks/use-ticket-page-refresh.ts` reuses the existing Inertia partial reload in the show page. It provides pending state, exact actor/ticket/component acknowledgement, a bounded 20-second wait, cancellation/scope cleanup and an inline failure with Retry refresh. It does not show a refreshed success message or remount entered drafts. Show passes `refreshingDelivery` to the root-owned Thread; drawer passes its existing `loading` state and retains its existing refresh error UI. Watcher commit uses the same canonical page refresh. A refresh failure does not reclassify a confirmed watcher write as failed.
