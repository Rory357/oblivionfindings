# W14 human handoff and automatic monitoring coordination

12 September 2026. W14 / F06 / B04 / E13; source privacy also supports W01. This is a partial implementation record, not whole-package or release acceptance.

## Current implementation

- Native and Fleet delivery can bind to an actual human handoff before automatic intake. Binding requires a canonical source link, human actor, matching Site and committed command receipt. Fabricated human-looking context without a receipt cannot redirect delivery.
- Human intake provenance and submitted title remain intact. A distinct `monitoring_handoff_bound` event identifies automatic episode evidence, without inventing `created_from_monitoring`. Source links retain the human author and original handoff context.
- Existing monitoring snapshot, recovery, replay and later-episode rules apply. Recovery records evidence and leaves IT work open. The next fault after closure creates the next canonical episode. Fleet evidence uses the actual Fleet source and never fabricates a DeviceEvent.
- A merged handoff target produces a durable unroutable result, rather than an additional ticket. Following the merge destination automatically is not implemented; operator reconciliation remains necessary.
- Alert evidence presentation includes genuine human handoffs before automatic binding and preserves owning source/content and ticket permissions.
- MySQL current reads are required inside nested link/event queries and when persisting a link after waiting for the alert mutex. An outer ticket lock alone does not refresh a nested consistent read.
- Guarded HTTP preview, create/link, recovery and cancellation endpoints are implemented and covered by the tests below. They use canonical services and the existing private-response guard. Missing receipts return an actor/alert/UUID-bound `unconfirmed` response only after source authorization. No operator UI is mounted yet.
