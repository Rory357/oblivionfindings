## Implemented, awaiting backend verification

Already-served legacy forms without any tuple retain the canonical adapter; partial tuples and JSON without the tuple fail validation. Complete current ID order is required for reorder.
- Actor/operation UUID receipts reuse `ItTicketCommandReceipt.result_metadata`. They store references/flags, never title, description, evidence, completion note or cancellation reason. Recovery returns the original committed version separately from fresh task review. Same-hash retries do not repeat tasks/events; explicit cancellation serializes with the original command and returns either a tombstone or the existing commit. A missing GET is never absence proof. Receipt storage readiness fails actionably.
- Postcommit exceptions use a fresh primary connection for current-access receipt proof, preserving uncertain outcomes when proof is unavailable. No task store or schema is duplicated.
- `POST /it/tickets/{ticket}/task-candidates/validate` gives only an opaque authorization proof for task-scoped RAM work while persisted drafts remain disabled. It checks original actor, ticket, task, operation, base, latest/pending fields and every historical assignment/team/dependency/order binding. Current changed/settled/merged state is a separate submit blocker; it never silently replaces the original base. No private response payload or DB write is intended.

## Stable transport contract

Mutation tuple: `actor_user_id`, `request_uuid`, `expected_version`. Existing paths remain canonical; new `PATCH /it/tickets/{ticket}/tasks/reorder` precedes the nested task route. Recovery is `GET /it/tickets/{ticket}/task-commands/{operation}/{requestUuid}`; explicit cancellation is `POST` to its `/cancel` suffix. Short operations are create/update/complete/reopen/reorder. Existing-task recovery/cancel supplies the exact `task_id`; create/reorder omit it.

Committed response has `status: committed` and data `{id, viewer_user_id, request_uuid, operation: task.<operation>, task_id, lock_version, changed, replayed}`. Only the first actual create is 201; other results are 200. A no-op retains the current version. A cancellation has `status: cancelled` with the same identity, nullable task ID for create/reorder, `cancelled_at` and `replayed`; it does not claim a business write. ACK and proof are `no-store, private`. Stale conflicts keep canonical `stale_ticket`/current-ticket shape; changed UUID payload is `idempotency_conflict`; business failures are 422 `task_validation_failed`; denied/foreign contexts remain 403/404.

RAM purpose is `task_work`, context `ticket:<id>:task:<taskId|new|order>:operation:<short operation>`. Candidate and pending command retain their original versions. The existing browser nonce registry binds the frozen candidate and rechecks before adoption; the server returns the existing memory proof envelope with current version, authorized flag and submit blocker, without another hash protocol. Four-step wizard indexes are 0–3. Existing current-ticket JSON supplies current task review and canonical eligible `assignees`; historical unchanged owners remain separately visible.

### Corrections and constraints for the completion proposal

- **Legacy definition truth:** a new completion can snapshot the definition actually completed. For a legacy snapshot, current title/description/flags are only the definition observed at capture; no evidence proves an older definition. Keep `source`, `recorded_at` and actual nullable `completed_at` distinct. This refines the proposed bounded definition snapshot; it does not justify a historical backfill.
- **Unknown provenance stays unknown:** keep known-empty prerequisite bindings separate from unknown historical bindings. Capturing a completed legacy prerequisite for a new command must not populate its own historical prerequisite/approval bindings from today's graph. Create at most one capture for the extant legacy completion under the same task lock; GET never captures. Metadata capture must not pretend that task was newly completed, emit a duplicate completion event or advance the aggregate twice.
- **History needs deletion and rollback protection:** the existing task parent uses cascade deletion and completed actor uses null-on-delete (`2026_07_18_200001_create_it_service_management_core.php:100–104`); approvals also cascade from tickets (`2026_07_10_100001_create_it_ticket_approvals_table.php:21`). New immutable completion rows must not silently cascade away with a task or lose their original actor scalar. Use restrictive history references/current-pointer consistency, and refuse a lossy new migration rollback when history exists. This is evidence preservation, not a new retention/deletion policy. Any later authorized erasure needs its own reviewed lifecycle.
- **Same-task and current access:** a current completion pointer and each prerequisite completion ID must belong to the named task and correct current ticket graph; sequence uniqueness alone is insufficient. Historic identity never grants present access. Resolve history through an authorized nested task. Current merge moves comments and watchers, not tasks (`ItTicketMergeService.php:49–61`); do not claim task-history merge behavior exists. W09 must decide and verify its governed handling without rewriting immutable identity.
- **A verdict is not a historical status rewrite:** transitive invalidity must be a current evaluator result separate from stored completed status and immutable evidence. Re-completing A cannot silently validate old B; an explicit B reopen/recompletion creates new provenance. B/C remain readable history. If a future approval request expires, it cannot rewrite an earlier approved decision into an expired one.
- **No nonexistent approval version:** the W00 correction is sound. The earlier command/lifecycle proposal's phrase “approval ID/version” should be read as exact canonical request ID until an explicit versioned approval contract exists; no field or inferred historical version should be invented.

### Operational decisions versus routine implementation

Safe work can proceed without asking for a policy: append-only evidence, truthful unknown labels, exact current authorization, fresh actor checks, original command identity, no duplicate work on retries, required reasons for explicit reversal/repair, canonical blocker links, isolated tests and read-only personal-task projections. Preserve today's `it.manage` plus `canWork` authority and the ban on the approval raiser deciding their own request (`ItTicketApprovalPolicy.php:20–25`). New assignment/cover labels confer responsibility only; do not silently tighten or broaden who may decide.

The following decisions remain explicit dependencies for behavior that would change organisational policy:

- Whether unknown legacy prerequisite/approval provenance should hard-block existing completed work, and the authorized reconciliation/exception route if so. History capture and an honest “legacy provenance unknown” projection can ship without making that decision. Do not silently grandfather it as verified or invalidate every historical completion.
- Default pending approval duration, elapsed versus working-time clock/calendar, and whether an explicit per-request expiry is mandatory. Do not assign a default deadline to historical pending rows. A supplied absolute expiry can be implemented with exact-boundary enforcement, while automatic defaults remain unset.
- Reminder frequency, maximum/escalation behavior and recipients. A bounded idempotent scheduling/outbox mechanism can be implemented disabled/unconfigured; no real reminders or invented escalation chain.
- Whether designated primary/cover restricts today's otherwise eligible deciding population, who may reassign that responsibility, and whether cover requires explicit activation or automatic approved-absence substitution. Merely adding an eligible named primary/cover does not answer these authority questions. Preserve current authority for legacy unassigned requests until a stricter policy is approved.
- What material request/catalogue/asset/Site change invalidates an already approved verdict and demands a new request generation. Pending expiry is distinct from approved-verdict validity. Do not expire approved decisions or repoint completed evidence to a newer request.
- Whether “self-approval” additionally forbids the original ticket requester/requested-for beneficiary when that person differs from the approval raiser. The current enforced rule forbids the raiser; do not silently remove it or claim a broader conflict-of-interest policy already exists.
