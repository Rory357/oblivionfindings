Owner split
Control Room produces the canonical server-derived source-aware reporting decision, source policy provenance, decision commands/audit and operational resolution eligibility. It owns matching list counts and filters. H&S consumes that projection in its reserved response-page/next-action/linked-journey files, owns incident/governance access and page foundation, and changes the universal incident/H&S copy. Coordinator reviews the proposed DTO and minimal controller seam before integration. H&S retains current controller navigation/detail-return and access fixes; Control Room must not overwrite them. Implement the producer in a bounded service/presenter and deliver a small payload/controller patch for semantic combination.

Required semantics for a permission-shaped projection
reporting.state: decision_needed | required | not_required | linked.
reporting.basis: machine-readable reason/policy code plus safe explanation and available authoritative source-policy reference/version; unknown policy must be visible, not fabricated. No sensitive source fields merely to explain a decision.
reporting.decision: relevant persisted actor/time/reason/version where a human decision exists; expose only authorised detail. An existing source policy can determine a state without inventing a human actor. Linked state means a canonical record exists; it does not mean the record is complete or readable by this user.
reporting.canDecide / canCreate: server-calculated exact permissions, with server-side revalidation and race protection on the real commands. A user cannot override mandatory source reporting merely by choosing not_required.
Keep the existing privacy-shaped linked incident and H&S objects. Never reveal forbidden IDs, titles, references or URLs. A restricted linked record is not equivalent to no record.
Operational completion: use or extend the canonical lifecycle eligibility result, with canResolve and safe blockers/required next action; do not compute it from presence/absence of incident IDs in React. Keep source recovery, operational resolution, incident submission and governance closure separate. Any replacement names/types must preserve these semantics and be agreed before wiring consumers.

Behaviour
- Active immediate response/confirmation stays prominent; creating a report must not eclipse urgent action solely because no incident exists.
- required: offer the applicable canonical report creation/link/source action where authorised. ClientIncident is the target only when that source rule calls for it; only the real applicable reporting rule may block the relevant completion transition.
- decision_needed: expose the authorised reporting decision/review action. It is not the same count as required. Unknown/legacy state remains honest; avoid blanket not_required or compulsory H&S.
- decision_needed or null policy alone is not a universal operational resolution blocker. An actual applicable source/closure rule determines whether a decision/report must precede that transition. Preserve an accountable reporting follow-up when appropriate; never waive a real mandatory obligation or recreate the funnel as a compulsory decision modal for every alert.
- not_required: continue/complete operational response under its own rules, preserving any other domain follow-ups. Record the authorised basis; do not imply false alarm merely because no incident is needed.
- linked: show the permitted canonical record and its actual outstanding work; link is not closure.
- H&S handover is a separate conditional action/state, not a side effect promised by Create incident for every source. Show H&S only when linked or applicable; no universal three-stage completion rail. Where existing creation combines actions for genuine safety events, preserve legitimate behaviour with explicit labels and conditions.
- IT ticket, staffing cover, Fleet maintenance and other source responsibilities remain linked operational/domain work. Awaiting H&S acceptance must not universally block alert resolution; real required acceptance/retained ownership rules still apply for applicable transfers.
- Current next-action.ts 'Create incident and hand over' for every unlinked alert and LinkedJourney 'one alert -> one incident -> H&S' are confirmed defects, not approved universal product requirements.

Acceptance
Test required safety reporting, operational-only technical issue, urgent staffing cover, undecided legacy alert, linked-but-restricted record, genuine H&S transfer, revoked permission and concurrent decision/close. Prove shared counts use the same decision as record pages. Prove neither missing DTO nor hidden record permits bypass of server closure checks. Prove operational resolution does not falsely complete outstanding incident/governance/source work. No fabricated policy table by source name alone; trace real policy obligations first and surface unresolved configuration honestly.
