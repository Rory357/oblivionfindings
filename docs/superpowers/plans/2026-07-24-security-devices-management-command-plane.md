# Security & Devices Management Command Plane Implementation Plan

**Goal:** Turn Security & Devices from an observation-led workspace into a governed desktop management platform that can safely operate supported access-control, alarm, camera, networking, tracking, healthcare-technical, facilities, firmware, and remote-management capabilities from the canonical Device profile.

**Architecture:** Keep `app/Domain/SecurityDevices/Models/Device.php` as the only device register and treat every management action as an expiring provider-neutral command request. The control plane resolves one canonical active Site, validates the viewer and capability, applies risk policy, step-up, independent approval, IT Change, or break-glass rules, signs an idempotent envelope, and dispatches it through the central runtime or the Device's approved collector. Provider adapters execute only declared capabilities. A command is successful only after a fresh observation reconciles the expected state; uncertain high-risk results never retry blindly. Audit records contain safe summaries and secret references, never reusable credentials or raw sensitive payloads.

**Tech stack:** PHP 8.4, Laravel 13, MySQL, Redis queues, ext-sodium, existing monitoring runtime envelopes/outbox/inbox, existing IT Change and ticket approvals, Inertia 2, React 19, TypeScript, Pest 4, Vitest 4, Playwright desktop web.

**Design source:** `docs/superpowers/specs/2026-07-18-it-support-native-monitoring-platform-design.md`, especially sections 11-13.

**Completion ledger:** `docs/it-support-security-devices-completion-goal.md` requirements A04, M01-M06, E07, E09, V04, V09, and V10.

**Runtime dependency:** `docs/superpowers/plans/2026-07-21-native-monitoring-runtime.md`.

> **Mandatory single-tenant boundary:** Oblivion Findings serves one operating organisation across many approved Sites. New command records, envelopes, queues, permissions, fixtures, and acceptance criteria must not add tenant identity or switching. Authorisation is based on roles and capabilities, canonical Device ownership, one resolvable active Site, approved collector/network scope, direct-object concealment, and privacy rules. Existing legacy partition columns are compatibility storage only.

> **Desktop/web-only boundary:** This plan adds desktop web management at 1440x900 and 1280x800. It does not add or claim mobile, native-app, or WebView support.

## Locked product and safety decisions

- Main navigation remains the approved Security & Devices information architecture. Management appears inside the relevant workspace and canonical Device profile; do not create one top-level page per provider or one crowded all-actions screen.
- `Observe`, `Operate`, `Manage`, `Control`, and `Admin` are explicit permission/capability levels. Higher module access never bypasses approved-Site, ownership, privacy, sensitive-domain, or target-state checks.
- Provider and collector adapters declare exact command capabilities. The UI must never infer support from a device category or show an inert command.
- Low-risk diagnostics may execute with a reason. State-changing management requires a reason and current state. Safety, security, privacy, availability, or destructive actions require recent step-up plus an approved change, independent approval, or a fully governed break-glass declaration according to policy.
- The requester cannot approve their own command. Approval does not bypass expiry, Site access, capability, current-state, or IT Change window checks at dispatch time.
- Break glass has a short expiry, a named reason, designated reviewer notification, an immutable post-use review, and no secret reveal. It is not a general approval shortcut.
- High-risk `uncertain` results never auto-retry. Operators see the last confirmed state, uncertainty evidence, and an explicit reconcile-before-retry next action.
- Bulk commands create one child request and result per Device. Partial success is shown per target and never collapsed to blanket success.
- Parameters persisted in the application are an encrypted execution payload plus an allowlisted safe summary. Secret-manager references may be named; tokens, passwords, private keys, raw commands, CCTV media, and clinical readings must not enter summaries, logs, tickets, alerts, exports, or notifications.
- Existing Queclink command records remain a compatibility execution detail until migrated behind the provider-neutral adapter; new UI and authorisation must not write directly to provider queues.
- Control Room consumes reconciled command events and immutable context where relevant, but it does not own command requests or become a second management console.

## Canonical lifecycle

`draft/requested -> awaiting_step_up | awaiting_approval | awaiting_change | ready -> dispatching -> accepted -> running -> succeeded | failed | expired | cancelled | uncertain | blocked -> reconciling -> reconciled | mismatch`

Terminal execution success and reconciled success are deliberately distinct. UI wording must say `Execution reported success; verifying actual state` until reconciliation completes.
