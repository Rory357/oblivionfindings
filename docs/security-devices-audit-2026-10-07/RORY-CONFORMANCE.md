# Rory's rules: Security & Devices acceptance

7 October 2026 · The user explicitly reminded this audit to follow Rory's rules. [DESIGN.md](../../DESIGN.md) is the authoritative entry point; its linked guides define the applicable details. This document applies those existing requirements to the proposed scope. It does not edit the rules or certify current UI conformance.

## Required product patterns

1. **Shared page header and shell.** Reuse PageHeader/PageHeaderRail and Home-rooted breadcrumbs. Keep search, primary filters and linked truthful meter blocks in the header. Preserve the shell's single 20px gutter and standard section gaps. Do not add a legacy hero, decorative statistics or duplicate body KPI cards. [Header guide](../../design_styles/PAGE_HEADER_STYLE_GUIDE.md), [shell guide](../../design_styles/APP_SHELL_STYLE_GUIDE.md).
2. **Grouped navigation.** Group related equipment/workflows into useful hubs; the 24 equipment families are catalogue filters, not 24 sidebar links. Reuse connected main tabs, the shared overflow/Find behaviour and meaningful tier-two profile tabs. Preserve canonical URLs and server permissions. Do not rebuild rails or use hidden navigation as access control. [Navigation guide](../../design_styles/NAVIGATION_STYLE_GUIDE.md).
3. **Device/asset lists.** Use EntityCard/EntityTable and shared cells. Kebab and right-click actions use the same permission-aware action set. Use scoped totals, shared pagination and a contained wide-table scroll region. Missing data is not a green zero. [List guide](../../design_styles/LIST_STYLE_GUIDE.md).
4. **Configuration/add/edit.** Reuse WizardShell for entity or multi-section forms: device enrollment, provider setup, response policy, permissions, evidence rules and attendance policy where applicable. Add/edit share the same prefilled flow, review, retained draft/error and explicit success behaviour. Single-section actions use the shared simple dialog. Avoid browser prompt/confirm forms. [Popup guide](../../design_styles/POPUP_STYLE_GUIDE.md).
5. **Searchable choices and custom catalogues.** Growing device/site/person/staff/provider directories use scoped searchable pickers with canonical IDs and clear loading/error states. Offer Add custom only for genuine configurable catalogues. A fixed supported protocol or security permission is not an arbitrary text value.
6. **Dates and time.** Reuse the shared calendar/date-range and clock/manual-time patterns, exact-minute entry, Cancel/Apply, visible timezone and explicit overnight/daylight-saving handling. Review must show the actual selected range. Attendance corrections and evidence windows must not silently round or shift time. [Popup guide](../../design_styles/POPUP_STYLE_GUIDE.md).
7. **Calendars.** Any device maintenance, response-cover or work calendar reuses SiteCalendar with a domain adapter. Keep the full date anchor, shared views/source filters and owning-domain actions. An incident evidence timeline is an ordered investigation record, not a reason to clone a calendar. [Calendar guide](../../design_styles/CALENDAR_STYLE_GUIDE.md).
8. **Maps and geofences.** Reuse the Client Location interaction contract with greyscale base tiles and semantic overlays, visible source time/freshness, keyboard alternatives and shared canonical boundaries. Assignment and monitoring activation remain separate. Historical/stale positions cannot be labelled live. Do not create separate incompatible vehicle/person/site geofence stores. [Map guide](../../design_styles/MAP_GEOFENCING_STYLE_GUIDE.md).
9. **Owned work and incident detail.** Reuse the work-record hierarchy: identity/source, concise summary, accountable owner/next action, compact notes, supporting evidence and guarded completion. Preserve each domain's lifecycle; do not rename all records Ticket or treat device recovery as care/incident closure. [Work-record guide](../../design_styles/WORK_RECORD_STYLE_GUIDE.md).
10. **Evidence uploads and file previews.** Use FileDropzone/StagedFileCard and the shared FilePreviewDialog for supported PDF/image evidence. Display actual permitted content and download the original authorised version; retain context and failures. Video sessions need a supported media implementation and must not masquerade as the PDF/image viewer. [File-preview guide](../../design_styles/FILE_PREVIEW_STYLE_GUIDE.md).
11. **Tokens, status and accessibility.** Use semantic tokens, shared StatusBadge, typography helpers, buttons, loaders and error/empty/loading components. Brand-independent safety status colours, light/dark/brand contrast, reduced motion and labelled keyboard controls are required. Keep shared desktop geometry; use the proper frontline hit-area helpers where applicable. [Tokens](../../design_styles/DESIGN_TOKENS.md), [buttons](../../design_styles/BUTTON_STYLE_GUIDE.md), [loaders](../../design_styles/LOADER_STYLE_GUIDE.md).
12. **Plain NZ English and truthful outcomes.** Lead with device/person/site names and useful action labels. Avoid raw enums and developer/audit terms in user flows. Say “Some evidence is missing”, “Waiting for the monitoring company” or “This device does not support remote restart” with a useful next action. Distinguish saved configuration, sent command, provider acceptance and verified outcome. Keep vendor/API details in appropriate technical detail views.

## Surface-by-surface acceptance

- Devices catalogue/profile: shared header, lists, menus, searchable assignments, real totals and action availability.
- Network monitoring/topology: the same shell/navigation; graph nodes and ports expose accessible names, scope, source/freshness and permitted record links.
- Security/CCTV/access: standard filters and actions around the media surface; Live now is distinct from incident-time playback; stream errors and unavailable provider actions are readable.
- Care/tracking: approved maps, historical provenance, consent/access rules, ordinary care language and separate monitoring activation.
- Control Room/H&S reconstruction: source-linked work-record layout, visible ownership, compact notes, explainable missing evidence and source-specific permissions.
- Collectors/downloads: real versioned downloads, enrollment wizard and truthful service/update states, with no “installed” success from merely clicking Download.
- Endpoint management: compatible shared device profile and commands; OS/ownership/provider differences remain visible and understandable.
- HR/My Day: existing worker experience, dedicated HR authority, shared date/time controls, clear proposed/confirmed/corrected states and recoverable submission.
- Settings: reuse the established settings pattern and controls; versioned policy changes have a readable effect/review, with effective-policy preview.

## Verification before the one final release

Run the applicable DESIGN.md conformance probes and inspect each changed view/dialog in the actual running build. Compare approved references at the same viewport; include 1440px and a narrower desktop, keyboard/focus, long names, errors/empty/stale states, light/dark themes and changed branding. Frontline surfaces additionally need their applicable touch/viewport checks. Verify source permissions and actual action outcomes as well as appearance.
