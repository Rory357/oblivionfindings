# C2.6: the Chat message model

Written 31 October 2026 for plan item C2.6 ("Message model, one migration"). It gives the stage 4 screens (C3.7–C3.18) and stage 6 (C5.1, C5.6) the storage they need. No screen changes here, and every new column is empty or at its default for existing messages, so today's Chat behaves exactly as before.

## What already exists (kept)

- `ops_messages`: `message_type` ('text', or 'attachment' for files), `content` (plain text, max 10,000), `reply_to_id`, `edited_at`, `chat_edit_version`, `is_pinned`, `pinned_by`, `pinned_at`, `mutation_id`, soft delete.
- Mentions (`chat_message_mentions`) point into `content` by offset. Edits keep the earlier version, encrypted, in `chat_message_revisions`.
- Files are in `chat_attachments`. Calls are in `chat_calls`. The sync feed is `chat_message_changes`.

## Decisions

1. **`content` stays the plain-text copy of every message.** Search, notification text, reply previews, the old pages and mention offsets all read it. The server writes it from the formatted document, never the other way round.
2. **Formatted text is a document, never HTML** (plan C2.6, C3.12). It is stored in `ops_messages.body_document` (JSON), in Oblivion's own small format (below). The server checks every document against the format and refuses anything else (422). The browser renders it as elements, never as HTML.
3. **Kinds use `message_type`:** `text`, `card`, `poll`, `sticker`, `call` and `system`. The old 'attachment' value stays valid, so the old Messages pages keep working. It is not rewritten.
4. **Threads** (C3.8): `thread_root_id` points at the message a thread hangs from. `reply_to_id` stays the quoted reply inside a conversation or thread. Each person's thread state (following, muted, last read) is in `chat_thread_states`.
5. **Priority** (C5.6): `priority` is 'normal', 'important' or 'urgent'. `confirm_requested` asks every member to confirm they have read it. Confirmations go in `chat_message_confirmations`. An urgent label never overrides phone or system Do Not Disturb (spec line 209).
6. **Sharing one message** (C3.7; bulk forwarding is ruled out): `shared_from_message_id`. The source preview is rechecked for access on every view. If the reader can't see the source, they get a placeholder, never a stored copy (spec lines 154 and 157).
7. **Scheduled send** (C3.18) is not a message until it is sent. A waiting one lives in `chat_scheduled_messages`, encrypted like drafts, and becomes a normal message when it goes, with `scheduled_message_id` pointing back. "At the start of my next shift" is stored as a flag and resolved against the roster when the shift is known.
8. **Polls** (C3.17): `chat_polls`, `chat_poll_options` and `chat_poll_votes`, one poll per `poll` message.
9. **Stickers** (C3.13, D6): `chat_stickers` holds Oblivion's own set and the organisation's uploaded library. There is no outside GIF service. A `sticker` message points at one with `sticker_id`.
10. **Calls in the conversation:** a `call` message points at `chat_calls` with `call_id`. The call record itself stays in the call tables.
11. **System messages** ("Ana added Kiri"): `system_event` is a fixed code, and `system_params` holds ids only, never names. Names are looked up when shown, so a renamed or removed person reads correctly.
12. **Care cards** (C5.1): `chat_message_cards` stores which Oblivion records a message links to (type and id only). Permission is checked on every view, and the card never stores record details.
13. **The link cache** (C3.10, D7): `chat_link_previews` holds one row per address, keyed by its SHA-256. It is fetched by the server behind a guard that refuses internal addresses, oversized pages and redirects to either. `chat_message_links` links a message to its previews. The sender can hide a preview (`hidden`). The reader's browser never contacts the site.

## The document format (version 1)

```json
{"v": 1, "blocks": [
  {"type": "paragraph", "content": [
    {"type": "text", "text": "Ring ", "marks": []},
    {"type": "mention", "user_id": 12, "label": "Ana Rēweti"},
    {"type": "text", "text": " before ", "marks": ["bold"]},
    {"type": "link", "href": "https://example.org/x", "content": [{"type": "text", "text": "the form", "marks": []}]}
  ]},
  {"type": "list", "ordered": false, "items": [[{"type": "paragraph", "content": []}]]},
  {"type": "quote", "blocks": [{"type": "paragraph", "content": []}]},
  {"type": "code", "text": "plain text, shown as code"}
]}
```

- **Blocks:** `paragraph`, `list` (ordered or not; each item holds paragraphs), `quote` (holds paragraphs) and `code`.
- **Inline:** `text` with marks from `bold`, `italic`, `underline`, `strike` and `code`; `link`, whose `href` is `https://`, `http://` or an Oblivion path starting with `/`; and `mention`.
- **Limits:** at most 200 blocks, lists and quotes nested at most 3 deep, and 10,000 characters of text, as `content` today. Unknown types, unknown marks, other link schemes, extra keys and control characters are refused.
- **Plain text:** paragraphs and list items each go on their own line. List items start with "• ", or "1. " when numbered, and quote lines start with "> ". A mention becomes "@" plus its label. The mention offsets stored in `chat_message_mentions` point into that text, as they do today.

## Not in C2.6

- The screens (stage 4).
- The link fetcher and its guard (C3.10).
- The scheduled-send runner (C3.18).
- The confirmation reminders (C5.6).

C2.6 only gives each of them its storage, models and checks, so each stage 4 item can start without a further migration.
