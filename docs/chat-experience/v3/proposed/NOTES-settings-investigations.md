### Design decisions to check

- **Template.** These are Settings pages: the 220 px settings menu and a compact Event Horizon header (title row, filters, rail). There are no meters in the header (PAGE_HEADER H1). The overview's numbers lead the body as a Tally instead. Fleet Settings still has header meters; I followed the newer H1 rule.
- **Rail.** The 7 tabs are General, Messages, Calls, Family, Notifications, Privacy and records, and History, plus the Find chip. Each view has sub-tabs, and the first sub-tab is always Overview. Only General › Overview is drawn as the page overview.
- **Scope.** The first filter chip in the header is the scope ("Whole organisation" or a Site). It replaces the "Policy scope" dropdown. The second chip filters to All settings, Changed, Can't switch on yet, or Set for a Site. I dropped the "Organisation" title chip because the scope chip already says it.
- **Groups and rows.** Each group is a card with an icon lens, a title and a caption. Each row has a label and a one-line hint on the left, the control on the right, and any choices underneath.
- **Switches.** Every on/off is a switch followed by its On or Off word. Segmented controls are used only for 3+ options or two named modes: text size, spacing, Enter key, digest days, link expiry and access period.
- **Row states.**
  - "Changed — not saved" uses the info badge plus the kit's warm row tint.
  - "Can't switch on yet" uses a neutral badge, a disabled switch, the reason and who can fix it ("your IT provider", "your privacy officer").
  - "Kōwhai House only" shows the organisation's value and a way back.
  - "Always on" uses a lock, for things nobody can turn off.
- **Loosening.** A change that loosens a safety check is marked on its row, called out in the review, and saved with the red button. Drawn example: switching off "Check messages before family see them".
- **Review dialog.** It groups changes by area, strikes through the old value and states who is affected, with counts. It ends with "Saved changes are recorded in Change history".
- **Conflict.** This follows eMAR's "Refresh and review", with a 3-column compare table (Rohan saved / Your draft). It does not use Fleet's "Keep my edited channels".
- **Service health.** Plain names: Messages, Live updates, Push notifications, Uploads and virus scanning, Calls. "Not set up" replaces "Not configured".
- **Plain words.**
  - "Policy scope" became the scope chip.
  - "No response expectation configured" became a switch, "Show families a reply time".
  - "Edit/removal window (minutes)" became "Edit for up to" and "Delete for everyone for up to".
  - Reply time shows "working hours", although the backend stores minutes.
- **Settings menu.**
  - Labels are in sentence case. The live layout still has Title Case, for example "Role Defaults".
  - "My Chat preferences" sits under General.
  - "Chat investigations" shows only for investigators.
- **Settings I proposed that have no backend or decision yet.** Keep or drop each one:
  - Show "Edited" and "Removed" to everyone.
  - Senders can remove a preview.
  - Ring on this computer.
  - Unread count in the browser tab.
  - Hold messages until the next shift, as a switch (C1.4 does it today with no switch).
  - Digest days.
  - Call link expiry options.

4. **Overview tabs.** Should each view also get its own drawn Overview sub-tab, or is the page Overview enough?
5. **Edit and delete windows (D9).** The backend has one field, `message_change_window_minutes`. The drawing has four rows: edit on/off, edit minutes, delete for everyone on/off, delete time. Agree?
6. **Site settings.** Which new settings can a Site set for itself? The code allows 13 today. D5 (family video) and D10 (AI helpers) are per Site; link previews, stickers and video are not decided.
7. **AI helpers (D10).** Where do the switches go? They aren't drawn. I suggest a "Helpers" sub-tab under Messages, with every helper off and a switch for each Site.
8. **Chat notices.** Should Settings › Chat show role defaults for Chat notices, as drawn with the "Everyone" filter? Or should it only link to Settings › Notifications › Role defaults, so there is one place?
9. **Saving personal choices.** The live My Chat preferences saves each choice at once. The drawing uses a save bar, as Fleet does. Which?
10. **Retention.** When a retention period is approved, what control sets it, and who approves it?
11. **Urgent help number.** It is drawn as an organisation setting that a Site can override. Is that right, or should it be per Site only?
12. **Push.** After the server is set up, is there one organisation switch and then each person allows push in their browser?
13. **Quick reactions.** The "Change" pop-up for the quick six isn't drawn. It also needs to go on the pop-up kit (C1.0e).

## Board 2: ChatV3-Investigations.html (M22)

### Scenes drawn

1. **Cases list** (full page). The page sits in Settings › Chat investigations with Mere Tūhoe signed in. It shows the D11 note (investigators open access themselves, and everything is logged) and a Tally. The table has 4 cases with conversations, access end time, exports and status. The ⋯ and right-click menu offers Open case, Export PDF, Add conversations, Place a hold and End all access.
2. **Quiet states.** These are: no investigator access, no cases yet, and access that ended (refused and logged).
3. **One case** (full page). It has a record header: back chip, "Open" chip, 4 meters, the tabs Conversations, About this case, Access log and Exports, and Export PDF as the white button. The case's conversations sit beside the read-only view of one of them. That view has a tinted "Investigation view · read-only" bar and no composer. It shows a removed message (red dashed edge, "Removed by sender · 2:33 pm") and an edited message with its earlier version. The attachment is listed by name only, and a preservation hold badge shows.
4. **Finding conversations.** "Open a case" (720) has the case reference, the access period (1 hour to 7 days), the reason (at least 10 characters) and the finder. In the finder you search by staff name and tick several, and search again to add people. It shows who is in each conversation, never the messages. Family conversations aren't listed, the case holds up to 20, and the dialog has the D11 note. "Add conversations to an open case" (480) and four finder states are drawn too.
5. **Access log and case details.** The Log reads time first, then the state ring, then the words. Each export is logged for each conversation with a short check code. Refused attempts show a red ring. "About this case" includes the reason and "Second person approval: not needed (organisation setting)".
6. **Export pop-up** (480). Five states are drawn:
   - ready, with a choice of this conversation or both open ones (the ended one isn't included);
   - done, with the file name and the full SHA-256 and a copy button;
   - rate limited ("export again at 3:24 pm");
   - refused because access ended;
   - refused because there are more than 5,000 messages.
7. **A page of the PDF.** Two A4 pages, always on white. Each has the label, the stamp line (case, investigator, NZ time), a diagonal watermark, the summary, the "complete record" note, the conversation heading and members, messages with the Removed and Edited tags, the earlier version, the attachment line, and the footer with the export reference and "Page 1 of 3".

### Design decisions to check

- **Layout.** The investigations page uses the same settings layout as the code. The case page is drawn as a record (back chip, status chip, meters) inside it, because it belongs to one case.
- **Conversations tab.** It puts the case's conversations and the selected conversation side by side. The code has a separate page for each conversation, with a list of the others; the URL can stay `/settings/chat/investigations/{grant}`.
- **Who is shown where.** The investigator isn't a member, so both people's messages sit on the left with their names.
- **Earlier versions.** They are always visible under the message. The live code folds them into a "details" toggle.
- **Wording.**
  - "Log and open authorised scope" became "Open read-only access".
  - "Authorised scope" became "Conversations".
  - "Grant" and "revoke" became "access" and "end access".
  - The export dialog's "fingerprint" became "Check code (SHA-256)", because DESIGN.md lists "fingerprint" as a word to avoid.
- **PDF attachments.** The drawing shows "roster-week-44.pdf (PDF, 84 KB)". The Blade template prints the raw MIME type, for example "application/pdf, 84.2 KB". I suggest the template uses a plain kind and a rounded size.
- **PDF colours.** The page uses the app's light palette and critical red. The real template has its own grey and dark-red hex colours, and it uses DejaVu Sans, not Instrument Sans.

### Open questions for Stephan

1. **Adding to an open case.** Today every request makes a new case batch, so an added conversation becomes a separate case with its own end time. Should "Add conversations" join the open case (same reason, same end time), which is a small backend change? Or should it be dropped, so you always open a new case?
2. **Case titles.** There is no case title today, only the reference. DESIGN.md says codes aren't names. Add a short "Case title" field, or show the reason's first line in the list? The list call doesn't return the reason now.
3. **Second-person approval (C1.12).** When it's switched on, what does the investigator see while waiting, and who approves? This isn't drawn.
4. **The case Access log.** The backend's investigation log returns the latest 100 events for everyone. The case tab needs them filtered to the case.
5. **Rate limit time.** The rate-limited state shows when you can export again. The 429 response must pass Retry-After to the dialog.
6. **Unbuilt parts.** "Download the log" and the "Exports" tab have no backend. Keep or drop?
7. **Preservation holds.** The tab isn't drawn here (it exists in code). Should it get its own drawing?
