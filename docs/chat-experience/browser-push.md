# Chat browser push delivery

This is a staged backend and service-worker implementation. `CHAT_BROWSER_PUSH_ENABLED` defaults to false, and the application rollout remains disabled. Device/account binding, settings enablement and real-browser acceptance are still required before enabling it. No native iOS/Android notification work is included.

## Authority and delivery

The application is single tenant. A delivery is scoped to the current user, permitted conversation history, approved site/client access and exact browser subscription. It does not use legacy tenant fields as an authority boundary.

Message acceptance and per-device push work commit in the same database transaction. Only browser subscriptions enabled at acceptance and an explicit personal/role push opt-in are included. A retry does not add new devices or backfill old messages. In-app and push preferences are independent; a push-only notice can open its authorised message without creating an in-app notice.

The scheduled `chat:deliver-notifications` command and message notification job recover pending work. Each device has a separate receipt and a two-minute claim lease. Network I/O occurs outside conversation/delivery locks. Each pass selects at most 100 receipts and stops starting new attempts after 20 seconds; a current network request has a ten-second timeout and a three-second connection timeout. A stale worker cannot acknowledge a replacement worker's claim.

Before dispatch, both the claim and the immediate preflight recheck current conversation/history access, unread state, mute, push opt-in, quiet time and the subscription fingerprint. The fingerprint binds subscription ID, owner, provider, endpoint, keys, worker protocol and the server-generated registration ID. A changed/removed/disabled subscription suppresses old work. Expired provider subscriptions are disabled only if their exact fingerprint still matches; a newly rebound account is not disabled by an old response.

Retries use exponential delays from one minute to one hour. Unsent browser notices expire after 24 hours; this suppresses stale delivery without deleting messages or records. Provider TTL is 60 seconds. Provider acceptance is not proof of device display. Ambiguous responses can already have reached the device: retries reuse the same opaque notification ID, provider topic and service-worker notification tag. `renotify: false` prevents replacement tags requesting a repeated alert. This is not an exactly-once network guarantee.

Push previews contain generic wording and an opaque notification link, without names, care details or record IDs. Diagnostics retain bounded categories only, never provider bodies, subscription endpoints or encryption keys. Clicking a Chat notice opens an authenticated, current-authority route. An existing exact receipt tab is focused; otherwise a new tab preserves unfinished work in existing tabs. Notification sounds follow the current preference. Chat pages and APIs are not added to offline caches.

## Transport and configuration

Since 23 October 2026 the transport sends through Oblivion's own push sender (`App\Services\Push\WebPushSender`, clean-room plan item C2.3): RFC 8291 `aes128gcm` encryption, an RFC 8292 VAPID token per push service and Laravel's HTTP client. No outside push or JWT package is installed for it; see [clean-room/provenance/push-sender.md](clean-room/provenance/push-sender.md). The same sender, and the same host allow-list, now serve medication alerts and the other PushChannel reminders.

Browser push uses the endpoint assigned by the browser's push service. It does not change the approved self-hosted calling design. The default exact-host allowlist is `fcm.googleapis.com`, `updates.push.services.mozilla.com` and `web.push.apple.com`; other browser endpoints require an explicit server-side allowlist review. Arbitrary user-supplied hosts, HTTP, IP literals, credentials, fragments, non-443 ports and redirects are rejected. This does not establish a complete browser compatibility matrix. Provider references: [Firebase service endpoint](https://firebase.google.com/docs/reference/fcm/rest), [Mozilla Web Push endpoint example](https://blog.mozilla.org/services/2016/02/20/webpushs-new-requirement-ttl-header/), [Apple Web Push endpoint guidance](https://developer.apple.com/documentation/usernotifications/sending-web-push-notifications-in-web-apps-and-browsers).

The existing `services.webpush.subject`, `public_key` and `private_key` provide VAPID configuration. Keep private keys in deployment secrets. Host overrides use server-only `CHAT_BROWSER_PUSH_HOSTS`, never form input. Keep `CHAT_BROWSER_PUSH_ENABLED=false` until the outstanding device lifecycle and browser checks below are complete. No settings, secrets or rollout flags were changed during implementation.

The local PHP CLI required Herd's existing `C:/Users/steph/.config/herd/openssl.cnf` supplied through `OPENSSL_CONF` for its test process to generate EC keys (Herd's `bin/php84/extras/ssl/openssl.cnf` also works). The sender makes a fresh key pair for every message, so this applies to sending too, not only to the tests. The first encryption run failed before assertions without it; the rerun with that process-local setting passed. Confirm working OpenSSL key generation in the actual worker runtime before deployment; do not infer it from key strings being present.

## Verification and remaining gates

### Browser account status checkpoint

The shared notification settings hook now checks an authenticated, no-store status endpoint against the current account, browser endpoint and exact encryption keys. Looking at settings does not register a device, request browser permission or transfer its ownership. Returning to a tab refreshes this status. Unknown, disabled, differently owned and changed-key subscriptions all report disabled without exposing the other owner.

Browser registration and disable requests require the expected actor from the rendered page; the server compares it with the authenticated session and rejects stale-account requests before mutation. Native subscription requests retain their existing contract. Explicit registration can transfer the current browser subscription. Disable is scoped to the authenticated owner and exact keys under a row lock; it does not destroy the browser-wide subscription, which may have been rebound in another tab. The hook ignores old-account responses, serialises repeated actions and waits up to ten seconds for first worker activation.

This is a settings/account-check improvement, not the complete shared-device lifecycle. Sign-out cleanup, suppression of already queued/displayed notifications after an account change, and real browser acceptance remain required. Chat push stays gated off. Existing browser tabs using the old request contract need a refresh before changing web push settings.

### Display-time authority checkpoint — 18 October

Provider payloads now carry an opaque device fingerprint. The service worker retrieves a fresh generic preview from an authenticated, no-store display endpoint before showing Chat. That endpoint requires the current person to own the receipt, an attempted browser delivery, its exact current subscription fingerprint and current conversation/history authority, unread/mute/preferences/quiet-time eligibility and delivery lifetime. It returns no care content, names or device credentials. The read-only check changes neither delivery acknowledgement nor message read state. It does not refresh the session's idle-activity timestamp; idle expiry still applies.

An unverified, signed-out, offline, redirected, mismatched or malformed result never falls back to the queued provider wording. Other notification types retain their existing behaviour. This chooses privacy when the browser cannot establish current authority; the canonical message and in-app notice remain available subject to their own channel preferences. A provider acknowledgement alone still does not prove that a browser notification appeared.

The worker invalidates pending display checks during observed sign-in/sign-out requests, forwards the original authentication request unchanged and removes displayed Chat alerts. It handles a display operation that resolves after logout cleanup. A shared invisible app component asks the worker to revalidate existing notices after account changes, tab focus, reconnect and controller replacement; the worker also revalidates on activation. A stale tab cannot assert an account: each recheck uses the server session. Checks run at most four concurrently; unrelated notices and medication cache restrictions are preserved.

These are implementation and automated race-test results, not proof that every OS can retract a notification already shown. Worker upgrade/capability gating remains a release requirement: do not send Chat push to legacy registrations whose installed worker lacks this display check. Persistent protocol-version capability and verified registration handshake are still needed before enabling the gate. Real browser/OS behaviour, session expiry with all background app activity, offline recovery and provider/device acceptance also remain open.

The settings hook challenges the actual active worker over a MessageChannel and requires protocol version2 with the matching nonce before registering. Missing/old/replaced/unresponsive workers produce a retry message; ports and timers are cleaned up. The registration request carries `chat_protocol_version: 2`. Server persistence and enforcement are now implemented, with database verification pending: only supported browser registrations with a valid server-generated registration ID can enqueue, dispatch or display Chat notices. Legacy requests default to protocol0; native requests retain protocol0 and no Chat registration ID. Unknown protocol versions are rejected before mutation. Authenticated status returns `chat_ready` only for the current enabled owner and exact keys.

Every explicit browser registration rotates its server-generated registration ID. This prevents a downgrade/re-upgrade or same-key re-registration from reviving old queued or displayed receipts. New registrations never backfill earlier messages. Reading status does not rotate or upgrade anything. The existing device card offers Update this device when general alerts are enabled but Chat readiness is false; a failed upgrade retains those alerts and the retry action. The handshake is compatibility evidence, not a substitute for authenticated user/device authority. Migration2026_10_18_110000 is saved only and must precede deployment of these model/controller changes; no application database has been migrated. Collect the current feature-run result before considering this gate verified.

Real browser evidence on 18 October: an isolated loopback fixture imported the actual handshake helper, rejected an activated protocol1 worker, updated the same registration to the unmodified application worker, and accepted protocol2. No notification permission, provider send or push subscription was involved. The registration and its isolated shell cache were removed afterwards. Screenshot: `storage/app/chat-review/worker-protocol-browser.png`. This complements the race tests without claiming OS-display or provider acceptance.

Transport tests use the real installed encryption library with an in-memory HTTP handler. No live provider is contacted. They cover encryption, TTL/topic, 2xx/expired/rejected/retry/configuration outcomes, connection failure, redirect refusal, malformed keys, native tokens and untrusted endpoints. Service-worker tests run the actual `public/sw.js` with stubbed browser globals and retain the existing medication-cache protection checks. These do not prove OS notification display or real-device delivery.

The isolated database tests exercise per-device acknowledgement/retry, private links, push-only preference, quiet time, lifetime, lease recovery, stale acknowledgements, rollback, current membership/history/staff/family authority and subscription reassignment. See `IMPLEMENTATION-STATUS.md` for the latest run outcome; pending runs must not be treated as passes.

Outstanding before enablement: bind browser subscriptions to the current signed-in account across sign-in/sign-out and shared devices; expose validated push preferences and device status; verify real browser permission/denial/revocation and delivery; add operational failure metrics and accurate health diagnostics; verify the full browser/network matrix. Invitation, callback and missed-call alerts, email delivery, preference audit/concurrency and native mobile work are separate incomplete requirements in the approved full scope.

## Local Windows (Herd) note

Herd's PHP on Windows has no default OpenSSL configuration, so EC key export used by Web Push encryption fails with "Unable to create the key". Set `OPENSSL_CONF=C:/Users/<you>/.config/herd/bin/php84/extras/ssl/openssl.cnf` for Pest runs and local queue workers. Linux servers ship a default configuration and need no change.
