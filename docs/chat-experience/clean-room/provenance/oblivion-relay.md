## Decisions taken while building

The spec left these to the builder, or they needed a reading of the spec:

1. **Nonce input.** The HMAC input is the 4-byte issue time, then `"\n" transport "\n" client IP "\n" client port` as text, so the parts can't run into each other (4.3 writes them as a concatenation).
2. **One TLS path.** Every stream listener is a `net.Server`; TLS is added with `new tls.TLSSocket(..., { isServer: true, secureContext })`. When bytes were already read (a PROXY header, or the `tcp+tls` first byte), a small duplex stream puts them back in front of the socket. A reload swaps the held secure context for new connections; existing ones carry on. This does what 8 asks of `server.setSecureContext()` without a second code path.
3. **TLS settings.** `minVersion: 'TLSv1.2'`; ciphers limited to the TLS 1.3 suites and, for 1.2, ECDHE with AES-GCM or ChaCha20-Poly1305; `SSL_OP_NO_RENEGOTIATION`, plus `disableRenegotiation()` once the handshake completes.
4. **Integrity key for requests other than Allocate.** The allocation's own key when the username matches; otherwise the class secrets, so that a correctly signed request under another username gets 441 (3.3 step 7) rather than 401, and a request with no allocation gets 437.
5. **Unknown attributes.** Checked after authentication (RFC 8489 6.3). For Allocate, after the REQUESTED-TRANSPORT check, following 5.2's order; DONT-FRAGMENT is deliberately not "known".
6. **Response cache.** Kept for responses to authenticated requests on every transport (5.7); 401 challenges and 438s aren't cached. A repeat that arrives while an Allocate is still binding its port is dropped; the client's next retransmission gets the cached answer.
7. **Limits.** "After N failures" silences on the Nth failure (20 per minute for TURN, 10 for the control channel). The unauthenticated-reply bucket per IP refills at 10 a second and holds 20; the per-allocation request bucket holds 50 and starts full.
8. **Stream framing.** A STUN message over 2,048 bytes or a ChannelData payload over 1,500 bytes on TCP or TLS is skipped by its length (the stream stays in step); wrong first bits, a wrong cookie or a length that isn't a multiple of 4 close the connection. The framer parses as bytes arrive and keeps at most one partial message, so the 64 KiB unparsed cap is a backstop that only a lowered test limit reaches.
9. **Ending a stream allocation.** Revoked, denied and secret-removed allocations destroy their TCP or TLS connection at once; refresh-zero, lifetime and grace endings end it after queued responses.
10. **Dual allocations.** A Refresh REQUESTED-ADDRESS-FAMILY matching either family of a dual allocation refreshes the whole allocation. IPv6 is off on the test server.
11. **Expiry at the boundary.** An Allocate whose credential expiry plus grace has already passed (only possible with grace 0 inside the clock allowance) gets 401.
12. **Stricter settings.** Any unknown `RELAY_*` setting stops start-up, so a typo can't silently switch a class off. Chat's `MAX_CREDENTIAL_SECONDS` may not exceed 3,600 and `GRACE_SECONDS` may not exceed 14,400, so configuration can't stretch the user's five-hour call. The relayed range may not contain any listener, health, control, STUN/TURN or denied port.
13. **Emptied secret files.** An empty secret file means "not set". That is how rotation step 3 ("clear the previous one and SIGHUP") works with the `_FILE` form; the install creates the previous-secret files empty.
14. **Log safety by construction.** Each log stream writes only an allowlist of fields. The operations log also replaces anything address-shaped in a platform error message. Security lines in the allocation log (`auth_limit`, `rate_limit`) are written at most once a minute per address and kind, so a flood can't fill the disk.
15. **Event names.** Beyond the list in 9: the operations log has `stop`, `refusals` (the per-minute summary) and `auth_limit` with `reason: control` (control-channel refusal counts, no addresses). Allocation-log reasons: `auth_limit` is `failures`, `denied_id` or `control_auth`; `rate_limit` is `unauthenticated_replies`, `connections_per_ip`, `connections_total` or `control_failures`. `revoked` carries `ended` (the count). `bytes_in` is client to peers, `bytes_out` peers to client. Control-channel lines use `source_ip`.
16. **Log retention.** A day's file is deleted once its last possible line is older than `RELAY_LOG_RETENTION_DAYS` (its start plus one day is at or before now minus the retention). New files are opened with `wx` and `fchmod 0640`.
17. **Control channel details.** 401 bodies are `{}`. A revoke must be `Content-Type: application/json` (400 otherwise) and its JSON has exactly the keys the spec lists. `previous_key` in `/control/status` is the previous key id, or null. Silencing is checked on every request as well as on connect, because kept-alive connections outlive it. The nonce store size is an internal override so the 503 test doesn't need 10,000 requests.
18. **The test-only peer policy.** `startRelay(config, { peerPolicy })` takes a function `(family, address, port)` consulted before section 6; `relay/server.mjs` never passes one. Only the network-path test in 16 uses it.
19. **Test certificates.** Made at run time by `relay/test/certs.mjs`, so no private key is committed.
20. **App: where the status comes from.** The spec's `relay` keys don't say how the app knows the relay is beside it. `CHAT_RELAY_HEALTH_URL` (loopback only, empty by default) does: set, the app reads `/health` there; empty, it reads the signed `/control/status`.
21. **App: revokes.** Skipped when the control channel isn't configured, so today's unconfigured app writes no rows. Sent from `DB::afterCommit`, then after the response in a web request (`app()->terminating()`), at once in console and queue code. The `chat.relay.revoked` audit row is written after the first attempt, with `nodes_confirmed` and `nodes_waiting`; retries log but add no rows. `expires_up_to` is the later of now plus the credential lifetime and one second past any earlier revocation of the id, so a second revoke covers credentials issued after the first. Retries are re-signed at send time, so the queue never holds a signed request. On a `sync` queue retries are not dispatched (they would run at once, forever); the waiting count and the 5-minute error still show them.
22. **App: hooks.** Also in `ChatCallController::leave()`, because leaving a call yourself, and ending it there, bypass the reconciler. "Admitted to the call" is read as any participant row of that call: revoking an id that never had credentials is harmless. The leaver rule skips its own revoke when Chat offboarding calls it, since offboarding sends one for the same person. The suspension hook listens for `approved_at` being cleared, as Oblivion Live's does.
23. **App: URLs.** Sorted UDP, then TCP, then TLS. Any invalid URL, or more than four, means no relay entry.
24. **Service health.** The new row needed its label in `chat-service-health.tsx`, because the screen accepts only the known set of rows. `ChatServiceHealth` takes its three new collaborators as optional constructor arguments so existing direct constructions keep working.
25. **Control key ids reload too (the user's answer, 1 November 2026).** The spec had an inconsistency. Requirement 9 says rotating a secret never drops a call, and 3.7's rotation step 1 ends with SIGHUP. But `RELAY_CONTROL_KEY_ID` and `RELAY_CONTROL_PREVIOUS_KEY_ID` are plain settings, and 10.1 says environment values need a restart. Asked in a pop-up, the user chose "Reload key ids too". Each key id may now also be given as `RELAY_CONTROL_KEY_ID_FILE` and `RELAY_CONTROL_PREVIOUS_KEY_ID_FILE`: value or file, never both. They are re-read on SIGHUP with the secrets, and an empty file means not set. The env example and `oblivion-relay.md` use the file form, so rotating the control key is file writes and a reload. These are the only two settings beyond the spec's table.

## Open questions

1. **Offboarding someone who is still staff.** As the spec says, `ChatOffboarding::complete()` always calls `revokePerson()`. For a person who stays on staff and only loses some memberships, that ends relay use for all their live calls; they reconnect with fresh credentials (which the relay accepts). Followed the spec; the checker may want to confirm that's intended.
2. **Not verified on this Windows PC:** the allocation log's 0640 mode and directory group (that test is skipped on Windows and runs on Linux); SIGHUP and SIGTERM through systemd (tests call `reload()` and `close()` directly; Windows can't send SIGHUP); the systemd unit, nginx line and firewall steps (installed by Stephan, checked by spec section 12).
3. **CI.** No workflow step runs `npm run test:relay` yet; Oblivion Live's equivalent CI step is also still waiting.
4. **Merging with Oblivion Live's branch.** Both add a subscriber to `EventServiceProvider` (a two-line conflict) and both touch `ChatOffboarding::complete()` near the audit row.
