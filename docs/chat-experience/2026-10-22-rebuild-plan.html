In short

The headline findings and what happens next.

  1. Chat works, but it was built safety-first and finish-last. On a 1440 × 900 screen the messages get 191 px, about a fifth of the height. Banners, an owner row and a reply-status row take the rest.
  2. Everyday chat features are missing. The emoji button only adds 🙂. You can only react with 👍. Photos show as file chips. There is no read status, typing indicator, copy, forwarding, formatting or video calling. The old Messages page had some of these, so switching over loses them.
  3. No open-source code was pasted into Oblivion's files. The licensing you saw is four outside engines Chat runs on: LiveKit (calls), Reverb and Pusher (live updates) and a web-push library. All use permissive licences. On 16 October you chose to keep LiveKit; this plan replaces that decision if you agree.
  4. Under the hood it won't hold beyond a small team. The conversation list runs thousands of database queries per refresh, every open tab polls about 25–30 times a minute, and one lock per conversation queues every read and write.
  5. The plan keeps what is Oblivion's (named-worker cover, the family inbox, the reply promise, callbacks, privacy rules, investigations), rebuilds the rest on Oblivion-owned engines, and adds care-only features no chat app has: live care cards, shift-aware mentions, read-and-confirm safety messages and a privacy check before anything goes to family.
  6. Nothing gets built until you approve the mockups. I've drawn the proposed screens in the design viewer next to the existing chat boards, in the same Slate style. All fifteen decisions at the end were answered on 22 October.

What I found clicking through it

  • Emoji: the smiley button adds " 🙂" to the end of the message. There is no picker (chat-thread.tsx:2550).
  • Message actions open a pop-up dialog instead of a hover bar or right-click menu. "React" is only "👍 Acknowledge", which also uses an emoji as an icon. Copy, Forward and Message info don't exist. Edit and Remove are greyed out with "An administrator must configure the edit/removal window first", because the default edit window is empty.
  • The "Latest messages" button covers the last bubble. A floating "Callbacks" button sits over the thread.
  • Voice notes show as the text "🎙️ Voice note". Recording opens in a pop-up, not inline, and has no waveform. Photos show as file chips, not pictures.
  • No photos or online status on people, no grouping of a sender's messages, and only one tick that means "Sent", although who has read what is already stored.
  • Calls open a "Call history" pop-up per conversation. There is no Calls page, no video and no screen share, and calls need a voice server that isn't set up.
  • Family inbox is a plain list beside an empty panel. Settings › Chat has its own two-column menu instead of the Fleet settings pattern, with lines like "A policy setting never adds someone to a conversation."
  • Plain-language slips: "No response expectation configured", "Files stay in this conversation until separately published with permission", "Policy scope", "Reassign / release", "Staff coordination".
  • Touch-sized controls: the composer buttons are 44 px touch targets on a desktop-only screen.

Look and feel

What makes it look unfinished, measured against DESIGN.md and against WhatsApp Web and Teams.

Grey on grey

The workspace, thread, composer and details all sit on the grey page colour instead of white cards. Other people's bubbles are a faint grey and yours a faint purple, so nothing stands out.

About 150 px per line

Every message has a name row (even "You"), a padded bordered bubble, a separate time row and an always-visible 44 px ⋯ row. About three messages fit on screen; WhatsApp fits ten to twelve.

Banners and pop-ups everywhere

Up to seven strips stack above the messages and recovery cards stack above a 200 px composer. Almost every action, from reacting to attaching a photo, opens a pop-up.

The approved mockup is part of the problem. Codex's revision 2 (M01, M03, M06) is a basic Teams-like design, and the build drifted further from it. Building it faithfully would not fix the look, so the rebuild needs a new approved mockup. The new boards are in the design viewer.

Already right

No raw colours or hex in chat code, every pop-up uses the approved widths, and /chat has a Home › Chat trail. Those stay.

How the screens are built

  • chat-thread.tsx is 2,937 lines with about 45 pieces of state: 1,400 lines of logic and one 1,400-line block of markup. It splits into a thread hook, a send hook, a draft hook and about ten small parts (header, notice, message list, day chip, message group, bubble, attachment grid, message menu, composer).
  • chat-workspace.tsx uses one "compact" switch to serve four different places. It becomes three explicit versions: full page, single conversation for sheets and drawers, and family.
  • Six widgets each pair a button with a pop-up that loads its own data (saved, call history, invitations, invite people, manage, callbacks). Each splits into a data part and a body that can also sit inline.
  • The calling provider (about 1,740 lines) also owns the app-wide unread count; that moves out.
  • The server doesn't send photos of people, the last sender, presence, typing, read state, image thumbnails or a name for one-to-one calls. Stage 2 and 3 add them.
  • Worth keeping as they are (tested, no screen code): the API layer, sync, send session and journal, upload coordinator, drafts, mentions, the file preview dialog and the incoming-call card's logic.
  • 68 chat test files (about 18,500 lines) assert today's wording; 192 checks in the thread test alone. They are rewritten with the screens.

Outside code and licences

Everything Chat brought in from outside Oblivion, what it does, and what replaces it.

What the audit found

  • No pasted code. None of the 542 chat files carries an outside copyright notice, an "adapted from" note or copied snippets. The call-token, server and webhook code was written from LiveKit's public documentation, not copied from its kits.
  • Two config files follow upstream templates: config/reverb.php (Reverb's own published config, MIT, meant to be copied) and livekit.yaml.example (a 38-line subset of LiveKit's sample). Both are rewritten in the clean room.
  • Codex read the source of the libraries it used (livekit-client, Reverb, Pusher, the web-push library) while debugging. For a strict clean room, those engines are rebuilt by sessions that never saw that source.
  • No copyleft code is linked into Chat. ClamAV (GPL) and ffprobe (LGPL/GPL) run as separate programs. The PDF export uses dompdf (LGPL), which 20+ other screens already use.

Gaps to fix whatever you decide

  • Three small MIT parts bundled inside livekit-client and pusher-js (ts-debounce, @stablelib/base64, @stablelib/utf8) are missing from the notices file.
  • The libraries compiled into the LiveKit server program were never listed.
  • composer.json still names the project laravel/react-starter-kit with "license": "MIT", from the starter kit. For "fully Oblivion's" it becomes oblivion/care, "proprietary".
  • firebase/php-jwt is used directly but only installed because sign-in needs it.
  • The ws package is unused and can go.
  • The spec and status file say "no clean-room engine replacement is authorised" (your 16 October choice). That line is updated once you decide D1.

Under the hood

What the server side does well, and what has to change before Chat can be switched on for everyone.

Won't scale

  • The conversation list loads every conversation and runs about 100–200 queries for each 20-person group, so thousands per request. It is refetched every 10–30 seconds and on every live update.
  • One database lock per conversation covers sending, reading, marking read, drafts, uploads and deliveries. One message in a 200-person channel queues hundreds of jobs on one row.
  • A live update says only "refresh", with no conversation, so every open tab refetches everything.
  • About 25–30 requests a minute per open tab; at 300 staff that is 125–150 requests a second. The presence heartbeat locks the user row every 15 seconds.
  • Two background jobs run every 10 seconds even with Chat off: about 17,000 runs a day.
  • Search scans text with no index. Nothing is ever pruned: the change log, deliveries and one bell entry per message per person grow forever.
  • The live-update server is a single node capped at 1,000 connections, files sit on the web server's disk, and virus scans run inside the upload request for up to 30 seconds.

Bugs and risks

  • Reactions: the database treats most emoji as the same character, so a person can only hold one reaction and removing one can remove another.
  • Off-duty messages are pushed back every 5 minutes forever, then arrive in a burst.
  • The bell floods: one entry per message, and reading the conversation doesn't clear them.
  • Cover staff see the whole history counted as unread.
  • One member moving Site can hide a whole group from everyone else, so organisation-wide channels can't work.
  • Hard-coded limits (20 MB, 7 call invites) ignore the settings.
  • Investigators grant themselves access, with no second approver.
  • Set-up traps: files silently fail without the virus scanner, voice notes vanish without the voice checker, edit is off, calls are off.
  • Too much machinery for the value: about ten separate duplicate-request schemes, four near-identical delivery queues, unused columns and about 4,700 lines of the old chat kept alive.

What to keep

These parts are already Oblivion-specific and well built. The rebuild keeps their behaviour and gives them the new look.

Family care

  • Named worker with care-team cover
  • Family inbox: needs reply, assigned to me, waiting on family, callbacks, resolved
  • Claim, reassign and hand over family work
  • Reply promise that follows working hours and holidays
  • Callback requests from request to done
  • Urgent help with "Chat is not for emergencies"
  • Relatives agree before another relative joins

Records and privacy

  • Messages stay tied to the right client and history limits
  • Check of who will read a family message before the first one
  • Call record saved to the client's notes
  • File saved to the client's photos or documents
  • Edit history kept encrypted
  • Investigations, preservation holds, offboarding
  • Push carries no message text or client details

Reliability

  • Sending can't create duplicates; "checking whether it sent"
  • Delivery queue written with the message
  • Virus scan that fails closed; safe file serving
  • Call rules: first available care-team member answers, people who lose access are removed
  • Session timeout that ignores background checks
  • Settings per Site with an audit trail
  • The test suite

Making it Oblivion's own

Features that only a care platform can offer, because Chat sits next to the roster, the client record, eMAR and incidents. Each one has a plan item in stage 6 or 7.

1Live care cards

Paste or attach an Oblivion record and it shows as a small live card: client, incident, shift, handover, medication round, task, open shift, leave request, vehicle booking, maintenance job, IT ticket, risk assessment, checklist, calendar event or family note. Each reader sees only what they're allowed to; a restricted card says "You can't open this record".

2Turn a message into work

From any message: create a task, start an incident report, add a shift note or family note, log a maintenance job or IT ticket, or add a calendar event. The new record links back to the message and the message shows the card.

3Shift-aware mentions

@on-shift Kōwhai House reaches whoever is rostered or clocked in right now; @house-lead and @on-call use the on-call rules eMAR already has. Before sending, a chip shows exactly who it will reach.

4Read and confirm

Important safety updates ask each person on shift to confirm they've read them. A ring closes as people confirm; anyone who hasn't is reminded, then their lead. Urgent messages can reach people on shift during quiet hours.

5Privacy check before family

Before a message goes to family, Chat checks it: does it name another person supported, attach a photo without photo consent, or share health details the family's portal access doesn't include? The writer can edit or send with a reason, which is logged. Built for the Privacy Act 2020 and the Health Information Privacy Code.

6Shift handover in chat

At clock-out, a card lists open family threads, unanswered mentions and tasks to hand over. At the next shift, the site channel shows "Since your last shift": what was said, decided and still open.

7Roster-driven channels

Site channels add and remove people from the roster and Site assignment, so nobody has to manage membership. Announcement channels let managers post and staff react, confirm or ask in a thread.

8Te reo Māori and NZ identity

The chat screens in te reo Māori (the app already has the language switch), emoji search in te reo ("aroha" finds ❤️), an easy macron helper, and an Oblivion sticker set drawn in the Journey style: Kia ora, Ka pai, Ngā mihi, Mōrena, Kia kaha.

9The signature, not a WhatsApp clone

Rings tell the state: a ring for on shift, dashed for on leave, and delivery shown as a ring that closes from sending to read, always with a word beside it. The horizon line on floating panels, lenses for file types, and the islands only for empty chats.

10Family who can see who's caring

Family conversations show who's caring for their person today and next, "Seen by care team", and the reply promise as a ring that closes. Visit and callback requests appear as cards with their status.

11Lone-work check-in

On an outing, a worker can share their live location in a chat until they tap "I'm back", using the lone-worker rules already in the app.

12Careful helpers (optional)

Off by default, with a switch per feature: catch-up summary of a long thread (only what the reader may see), a warm plain-language draft reply to family that staff must review, voice-note transcripts, and translation for families who prefer another language. Uses the app's existing AI settings.

Clean-room rebuild

How the outside engines are replaced with Oblivion's own code without carrying anyone else's code across.

What "fully Oblivion's" covers

  • Oblivion owns: every part of Chat in Oblivion's code: the screens, the chat server logic, the live-update engine, the call engine, the push sender, the voice-note checker, the emoji list and the stickers.
  • The platform it runs on stays, as it does for every product: PHP, Laravel, React, Tailwind, Radix, lucide, MySQL, Node.js and the browser's built-in calling and push. These use permissive licences; their notices stay.
  • Standard separate tools stay separate: the virus scanner, the push services run by Google, Mozilla and Apple, and (unless D4 says otherwise) a firewall relay for calls.
  • Code written by AI tools: ownership of AI-written code isn't settled law everywhere. Ask a lawyer to confirm Oblivion's position before you rely on it commercially.

The method

  1. Register: one list of every outside part, its licence and where it's used, kept in the repo.
  2. Specs from public standards only: WebSocket (RFC 6455), web push (RFC 8291, 8292), calling (W3C WebRTC, RFC 8445, 8829), firewall relay (RFC 8656), Unicode emoji data, plus Oblivion's own behaviour specs written from today's tests and screens.
  3. Separate builders: the sessions that write the new engines get the specs and Oblivion's code only. They may not open the replaced libraries' source or repositories, and each one writes a provenance note.
  4. Independent check: a different session compares the new code with the replaced libraries' source and records the result.
  5. Remove and guard: uninstall the packages, update the notices page, and add a check that stops them coming back.
  6. Sign off each engine in the register.

Decisions for you

All fifteen were decided on 22 October. Two differ from my recommendation: outside link previews are on by default (D7), and second-person approval for investigators is a setting that starts off (D11).

D1

How far does "Oblivion's own" go?

Recommended: replace every chat-specific outside engine (live updates, calls, push, voice checker) with Oblivion's own code through the clean room; keep the platform (Laravel, React and the rest) and standard separate tools.

Other options: also build Oblivion's own firewall relay; or keep the permissive libraries and only fix the notices.

Decided 22 Oct Replace the chat engines; the platform and virus scanner stay.

D2

Live updates

Recommended: Oblivion Live, Oblivion's own gateway. Alternative: keep Reverb (MIT, made by the Laravel team) and only write our own client and event model.

Decided 22 Oct Oblivion Live (part of "replace the chat engines").

D3

Calls

Recommended: Oblivion's own calls on the browser's built-in calling: voice up to 8 people, video up to 4, screen share. Alternative: keep LiveKit behind the new call layer and add video there.

Decided 22 Oct Oblivion's own calls with video and screen share.

D4

Firewall relay for calls

Recommended: run coturn (BSD licence) as a separate standard server, like the virus scanner, now; decide later whether to write Oblivion's own. Alternative: build our own relay from the start (much more work and a network service to secure).

Decided 22 Oct coturn as a separate standard server (you chose not to build our own relay).

D5

Video with family

Recommended: yes for one-to-one family video calls with the care team, off by default per Site. The October spec ruled video out.

Decided 22 Oct Yes, one-to-one with the care team, off by default per Site.

D6

GIFs

Recommended: no outside GIF service (they see who is chatting and can show unsuitable content); Oblivion stickers plus a library the organisation uploads. Alternative: allow a GIF service, off by default.

Decided 22 Oct Oblivion stickers and the organisation's own library; no outside GIF service.

D7

Previews of outside websites

Recommended: off by default, admin switch; Oblivion links always become care cards.

Decided 22 Oct On by default; an admin can switch it off. Oblivion's server fetches the preview behind a guard that refuses internal addresses, oversized pages and redirects to them, so the reader's browser never contacts the site.

D8

Read status

Recommended: per person for staff; family see "Seen by care team" rather than which worker read it.

Decided 22 Oct As recommended.

D9

Edit and delete windows

Recommended: edit for 15 minutes, delete for everyone for 1 hour, always kept in the encrypted history; admins can change both.

Decided 22 Oct As recommended.

D10

AI helpers in chat

Recommended: plan them, off by default, a switch per feature and per Site, using the existing AI settings; nothing sent for family translation without consent.

Decided 22 Oct Plan them, off by default.

D11

Investigator access

Recommended: a second person approves each grant (today the investigator grants themselves).

Decided 22 Oct A setting. The default keeps self-grant with the separate audit log; an organisation can switch on second-person approval.

D12

Signature on chat

Recommended: draw chat with the signature (rings, horizon line, lenses) as the boards do; it ships when you approve the signature for the whole app.

Decided 22 Oct As recommended.

D13

Microphone test before calls

Recommended: one-click calls; the microphone check runs only when the browser reports a problem, and stays available in My Chat preferences.

Decided 22 Oct As recommended.

D14

A full-height Chat page

Recommended: add a DESIGN.md exception: Chat uses the page kit's Workspace template at full height with the breadcrumb strip, and no Event Horizon header band, as in every chat app.

Decided 22 Oct As recommended.

D15

Answer and decline buttons

Recommended: Answer in the primary colour with a phone icon, Decline in the destructive red, as DESIGN.md asks (green is a status colour, not a button colour). Codex's mockup used green.

Decided 22 Oct As recommended.
