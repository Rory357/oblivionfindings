# Effective operating-policy contract

Prepared 11 October 2026 as package-1 implementation guidance. This contract consolidates accepted configuration requirements; it is not a claim that all policy previews, schedules or response adapters exist. [CAPABILITY-COVERAGE.md](CAPABILITY-COVERAGE.md) locates existing owners. Later verified implementation must record which rows are operational.

## Ownership and authority

Each deployment serves one organisation across approved sites. Configuration scope is the approved Site, canonical device/person/vehicle, event family and action. Permissions, current ownership, source privacy and consent determine authority. A policy can restrict an available action or choose an operational arrangement; it cannot grant permission, identify a person from proximity or create an unsupported vendor capability.

21 October script policy owner: `EndpointScriptPolicy` now implements per-computer, immediately committed configuration with append-only revisions and actor-bound authoring receipts. Its supported dimensions are the canonical computer and its captured current assignment; there is no organisation/Site inheritance, future schedule or occurrence-effective historical resolver in this API. The fallback is disabled/attended, including after reassignment. Current authority and mandatory script MFA are checked separately for show/save/replay/recovery, and unattended use remains a distinct grant. The recorded configuration never creates execution authority; the script executor remains unavailable. The shared-wizard editor now has original native-policy HTTP interoperability and same-tab reload-recovery checks. Opaque account/computer references persist without private form values; a recovered receipt must reproduce the exact retained intent digest, and reload cannot resubmit the original form. Missing requests and dismissed local reminders do not cancel server saves. New-session recovery and real browser acceptance remain outstanding. SCRIPT-CONTRACT-DRAFT.md and the latest CHECKPOINT.md contain exact implementation and verification status. Broader inheritance, history/preview and command integration requirements remain open.

Reuse Monitoring profiles/coverage/dependencies/maintenance/retention for technical monitoring; endpoint policies for native actions/remote assistance; HR for attendance; Control Room for response; H&S for incident windows and preservation; care/Fleet for their person/vehicle purposes. Shared UI displays the actual owner and effective rule. Do not introduce a second execution or policy engine into Devices to override these owners.

## Resolution, revisions and preview

An owning domain may offer organisation defaults and authorised Site/event/severity overrides. It must explicitly declare supported dimensions and precedence; missing runtime support remains an implementation gap. A device exception is allowed only where the canonical domain already defines or explicitly implements it.

The owner resolves the most specific applicable approved rule for the event/action instant. Schedules use the Site timezone and explicit start/end instants, with an inclusive start and exclusive end. Preserve UTC, local offset/precision and the attributed revision when available. Ambiguous/nonexistent NZ daylight-saving input needs an explicit selection/correction; no silently shifted time. Equal-priority conflicting rules must return a configuration conflict before saving/activation, rather than selecting whichever record is read first. Expired/disabled rules cannot apply. When no valid rule exists, show the owner's documented fallback or unavailable state.

For late/buffered observations, retain the occurrence-effective rule and historical assignment used to interpret the event, plus received time and clock uncertainty. Current access, consent and execution authority are separately rechecked when processing, reading, delivering, retrying and exporting. Historical policy does not restore a withdrawn grant or silently execute a delayed destructive action.

Editing uses the owner's expected revision, actor, reason and effective date; validate referenced source/device/Site authority inside the write transaction. Audit old/new revision and any superseding relationship. An uncertain save uses that owner's safe recovery/readback; no blind repeated mutation. Accepted/executed facts retain the original attributed rule. A future revision must not rewrite an immutable command, reference, approved time or incident occurrence.

Preview, where implemented, takes a scoped example and event/action time and returns the winning owner/rule/revision, applicable schedule/timezone, explicit override/fallback explanation, supported capability, permission/consent constraints and actionable unavailable/conflict reason. Preview does not issue a command, disclose another person's source, activate a provider or prove a successful outcome. Actual operations must resolve/recheck again; no preview-token authority bypass.

## Interface with H&S

Devices owns the immutable reference and current authorized projection through the instance method CctvRecordingReferences::resolve(Request $request, string $uuid): array. Supply a query-free source Request carrying the same current authenticated actor: the reader rejects any query keys, including incident filters or return_to. The private recovery route is separate and explicitly requires expected_actor_id; its query must not be passed to the UUID reader. H&S owns its proposed attach_recording_reference command, incident revision and evidence-window policy. The proposed POST /incidents/{incident}/recording-references is not a callable contract until the H&S owner implements/registers it.

The H&S proposal uses idempotency_key, expected_version, reference_uuid, evidence_window_revision and purpose. The consumer must independently authorize the incident and evidence operation, resolve the exact captured camera/recorder/Site binding, and validate the effective selected window. It stores the immutable source snapshot and attributed link receipt atomically through an explicit H&S evidence revision/storage seam. ClientIncident.owner_revision versions ownership and cannot be reused as the global incident/evidence expected_version. The reviewed current-source binding does not prove camera/recorder assignment at the incident instant: resolve occurrence-effective assignment separately or show uncertainty. Legacy free-text cctv_bookmark items are not canonical UUID receipts and must not be silently backfilled or treated as those receipts. Exact authorised replay precedes stale-version rejection; changed actor/input/source authority cannot reuse it. Failure retains the existing Devices reference and incident draft. Unlink/supersede preserves history; it does not delete a recording.

Reference-only means footage not verified or preserved. recording_verified_at and vendor_retention_until remain null until supported provider evidence establishes them. Live now, reference, preservation requested, provider-confirmed preservation and retained evidence are distinct. Retained evidence requires real bytes and the owning storage/integrity receipt; a source/configuration hash is never a clip hash. H&S/Control Room closure does not release hardware, end retention or complete preservation.
