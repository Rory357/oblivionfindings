## Approved scripts: gaps before execution can be switched on

Script execution is off. `EndpointScriptPolicy::available()` is hard-coded
false, dispatch throws `script_executor_unavailable`, no runtime is allowlisted
and the agent has no executor. None of the items below can happen today. Every
one must be closed before execution is enabled.

### Server

1. **One script locks the computer for good.** `EndpointMutationGuard` treats
   any claimed delivery with `mutation_started=true` (every `completed` or
   `exit_failed` result) or an uncertain result as exclusive forever. After one
   script, every later service, restart, software or script claim on that agent
   gets 409. Needed: the owned-job quiescence contract, or an explicit operator
   release, mirrored on the agent.
2. **Nothing expires script attempts.** `ExpireEndpointServiceActions` sweeps
   service, restart and software attempts but not scripts. An unclaimed expired
   delivery stays Dispatching. A claimed one whose agent never reports stays
   Accepted and never becomes Uncertain. A withdrawn script or a changed policy
   after approval is skipped by `poll()`, but the request is never marked
   blocked.
3. **One cancellation can block the agent's script queue.** `poll()` returns
   only cancellations while any is pending. `cancel()` is accepted after a
   completed result, those deliveries never leave the pending set, and there is
   no acknowledgement route. The server also writes a new lease row and audit
   event every hour, forever.
4. **The whole permission table is locked exclusively.**
   `AuthorizationEvidenceLockService::lockForUsersWithoutWaiting(..., ['*'])`
   uses `FOR UPDATE NOWAIT` on every `permissions` row. While a script
   candidate or approval transaction is open, every other module's
   `lockForUserWithoutWaiting` caller fails with MySQL 3572. Use share locks,
   or lock only the keys actually checked.
5. **Results depend on intact catalogue evidence.** `result()` and `output()`
   re-run the catalogue integrity check (`requireCatalogue=true`). Damaged
   evidence makes an executed script's result unstorable for good.
   Cancellation already skips this check; results should too.
6. **The dispatch fallthrough is a trap.** `GovernedCommandDispatchService`
   sends any non-software, non-restart endpoint command to
   `EndpointServiceCommands::prepare`. Only the `script_executor_unavailable`
   throw stops a script being prepared as a service action. Add an explicit
   script branch.
7. **Approval and request paths don't map lock errors.**
   `DeviceCommandApprovalService` (the script branch) and the request path let
   MySQL 3572 surface as a 500. The catalogue controller now returns 503.
8. **Some script routes aren't protected.**
   `ProtectRemoteSupportResponses::applies` doesn't cover the agent `scripts`
   poll, claim, result and artifact routes, or the catalogue routes. Those miss
   the issuer-host check and the 8 KiB body cap.
9. **Reading output skips identity confirmation.** Reading private output
   doesn't require fresh identity confirmation, unlike reading script material.
10. **The release flag does nothing.** `endpoint_management.scripts.release_enabled`
    is never read, and `reviewed_runtimes` is a literal `[]`.
    `safe_result_summary.output_received` never updates.
11. **The identity check runs on a GET.**
    `GET /security-devices/scripts/confirm-identity` (and the script-policy
    version) clears the session's password confirmation. Make it a POST.

### Windows agent (Go)

The building blocks exist and pass: the signed contract, the TLS transport, the
output collector and the journal state machine. Since 22 Oct, all 30 script
tests run by default from the committed fixtures. Nothing calls them yet.

1. **No executor.** There is no CreateProcess or job object, no timeouts or kill
   logic, and no PowerShell 7 runtime, wrapper `.ps1`, staging or installer
   support. `runner.go` binds no script controller.
2. **The journal isn't wired in.** Install and upgrade must call
   `createScriptJournal`, the runner must load it and bind a controller, and a
   `scriptReady` hook must advertise the capability.
3. **Reboots break unclaimed entries.** After a reboot their results carry the
   old `boot_id`, and the server's unclaimed-result check requires the current
   boot, so they 409 forever. Add a boot refresh, or have the server accept the
   historical boot. There is also no terminal "server refused" state.
4. **Output isn't durable.** Only its digest and size are journalled, so a crash
   between the result acknowledgement and the upload loses it. Needed: a
   protected spool of up to 64 KiB plus an upload-receipt state.
5. **Clock skew isn't handled.** Claims allow +1 s and last at most 30 s, so a
   slow or fast PC clock rejects every claim. Use the server time from the
   heartbeat acknowledgement.
6. **The journal outgrows the secure writer.** `scriptJournalLimit` is 16 MiB
   but `securefs.WriteAtomic` caps writes at 2 MiB.
7. **Cancellations aren't journalled.** They have no durable state.
8. **Re-enrolment or key rotation poisons the journal.** No archive or
   migration exists, and a partial install needs manual cleanup.
9. **Recovery is blind.** It doesn't check whether the recorded process is
   still alive or terminate its job, and the job-object name isn't persisted.
10. **No mutation gate.** The journal never takes `Store.mutationGate`, so a
    script could overlap a software, restart or service action.
11. **Some uncertain results could be definite.** A failure to start, or a
    crash in the "claimed" phase with no JobID, could be reported as a definite
    failure.
12. **Transport timeouts are too tight.** Every request has a hard 3 s timeout,
    including the 256 KiB artifact download. All non-200 responses collapse
    into one error. `scriptHTTP.Result` doesn't return the acknowledgement
    bytes that `journal.Acknowledge` needs.
13. **The journal is plain text.** It holds the full signed command
    (technician, purpose, inputs) protected only by file permissions; there is
    no DPAPI.
14. **Journal not bound to its server.** It records the agent identity but not
    the deployment server it came from (Codex's handover follow-up).
15. **No second-claim rejection.** A new claim isn't refused while earlier
    work still holds exclusion. This overlaps item 10.
16. **No unique job identity check.** Job identities aren't checked for
    uniqueness across entries.
