## Verified source identity and credentials

Official [integration overview](https://www.hikvision.com/content/dam/hikvision/vn/webinar/Thang3_Hikvision_Tich_Hop_He_Thong_Overview-of-3rd-Party-Integration.pdf) recommends querying `/ISAPI/Streaming/channels` or `/ISAPI/ContentMgmt/StreamingProxy/channels` before choosing channels. [ISAPI developer guide](https://enpinfo.hikvision.com/unzip/20201110210551_77443_doc/pdf.pdf) demonstrates Digest-authenticated DESCRIBE. No automatic camera reconfiguration or transport weakening is proposed.

Prefer read-only bounded HTTPS ISAPI verification of recorder serial/model/firmware and its actual channel mapping; ONVIF GetProfiles/GetStreamUri is an alternate versioned discovery adapter, not an arbitrary returned-URL proxy. Preserve exact channel ID/profile token, canonical camera/recorder relation, verified camera identity where exposed, selected H264 substream and credential revision. Disable XML DTD/entity resolution, bound XML/body/count/time, and restrict all discovered service/stream/control authorities before authentication. No unbounded WS-Discovery or browser-supplied SOAP target.

[Official ONVIF setup](https://supportusa.hikvision.com/support/solutions/articles/17000128730-how-do-i-enable-onvif-on-a-hikvision-camera-) supplies a Media User role for real-time streaming and read-only capabilities/configuration. Separate ONVIF accounts and model-specific enablement are documented; do not assume an ISAPI password is automatically the ONVIF credential. Provision least privilege through existing protected Site secrets, seal to the enrolled collector, and keep credentials out of browser/URLs/argv/env/logs. Viewer setup never automatically enables protocols or creates privileged accounts.

## Bounded HTTP-wrapper Digest transport — 11 October 2026

The internal source helper `endpoint-agent/internal/cctv/https_tunnel.go` fills the separately identified HTTP authentication gap without enabling Hikvision in the production source/grant/provider/parser. Production remains UniFi-only. The pinned gortsplib dependency and prior RTSP-only fixture remain unchanged. The helper must be called only by a future independently reviewed signed and verified Hikvision mapping; it accepts no public/manual source URL.

- Both receive GET and send POST use separate TLS connections pinned to one numeric IP, exact port, verified TLS name/trust and SHA256 leaf certificate. Channel paths are bounded to the explicit Streaming/channels grammar. There is no DNS dial, proxy, redirect, cross-authority retry or plaintext fallback.
- Each connection permits one initial challenge plus one authenticated attempt. The supported wrapper profile requires HTTP/1.1, Digest qop auth with MD5 or SHA-256 (preferring SHA-256), at most four challenges, unambiguous bounded parameters and 8 KiB aggregate/4 KiB line headers. Basic, unsupported algorithms/qop, duplicate parameters and control characters are rejected. GET and POST each require authenticated HTTP 200; the GET media type must identify the tunnel. A vendor POST that provides no acknowledgement is not supported by this profile.
- Digest hashes the HTTP method and exact request target rather than the full RTSP URI. Nonce counts are shared by exact algorithm/realm/nonce identity. Both connections use one random session cookie; credentials are never returned in protocol errors.
- The entire opening budget is three seconds and is bounded further by the caller's dial deadline. The short dial context is detached only after successful establishment, because gortsplib cancels it after connecting. The separate media lifetime closes both sockets. Explicit Close and lifetime cancellation also deny any buffered video/control afterwards.
- The POST body is base64 and bounded to its declared 30,000 encoded bytes; overflow closes the session. Unsupported wrapper body framing is rejected. This profile does not implement chunked framing, no-qop Digest, auth-int, session algorithms, unchallenged tunnels, proprietary recorder encryption or silent transport negotiation.

Verification uses real loopback TLS sockets and an independent RTSP server in `https_tunnel_test.go` and `https_tunnel_media_test.go`. Published [RFC 7616 examples](https://www.rfc-editor.org/rfc/rfc7616.html#section-3.9.1) supply external MD5 and SHA-256 expected vectors. The server independently verifies HTTP Digest on both connections, cookie/path/authority, multiple padded base64 RTSP writes, RTSP-layer SHA256 Digest and actual H264 RTP. Lifetime cancellation closes the actual RTSP client. No hardware, browser decode, video preservation or signed producer-consumer interoperability is established by these fixtures.
